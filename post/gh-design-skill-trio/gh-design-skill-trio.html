01 · 这件事

三个仓库都在治「AI 味界面」，下手的时刻不一样

Nutlope/hallmark 2026 年 4 月 27 日建库，经 api.github.com 核对是 49,902 星、2,645 个 fork、98 个订阅者、44 个未关闭 issue，MIT 协议，主语言 CSS，仓库 233,716 KB，最后 push 停在 2026 年 11 月 5 日，主页 usehallmark.com。它的 description 一句话交代了立场：Anti-AI-slop design skill for Claude Code, Cursor, and Codex.——一个反 AI slop 的设计技能。

体量最大的是 pbakaus/impeccable，2025 年 11 月 16 日建库，三者里最早，105,105 星、6,245 个 fork、222 个订阅者、71 个未关闭 issue，Apache-2.0，主语言 Rust，仓库 897,762 KB，2026 年 11 月 7 日当天还在 push，主页 impeccable.style，topics 里挂着 agent-skills / anti-slop / design / slop。description 把动作写全了：Steer with polish and bolder, review with critique and audit, catch AI slop before it ships.

最晚也最小的是 jakubkrehel/skills，2026 年 7 月 10 日建库，11,380 星、441 个 fork、41 个订阅者、11 个未关闭 issue，MIT，主语言 Markdown，仓库只有 747 KB，同样在 2026 年 11 月 7 日 push 过，主页 jakub.kr/skills。description 没有承诺流程：A collection of agent skills that help you build great interfaces.

三家解决的是同一件事——让编码 agent 把界面做好——但下手的时刻根本不在一处：hallmark 把规矩喂在生成之前，impeccable 把审查放在发布之前，jakubkrehel/skills 干脆不做时序，直接摊开一包可挑的技能。三者在积压队列里同属 design-skill 一族，所以这篇是横评，一次消耗三条。下面按「作用点落在哪一刻」把三段拆开，最后给什么情况下选 A / B / C 的判断表。

02 · 核心机制

一个管生成前，一个管生成后，一个只管给工具

hallmark 卡在生成前给约束这一段。按 README 自述，它先从一个五十套材料的目录里发三套主题，围绕「访客来办什么事」搭页面，再用三级 gates 把结果按在机器味的 tells 上：标题上方千篇一律的 eyebrow、全大写的 tracked-caps 标签、标题里唯独一个上色的词、满屏空框或只有照片、hero 撑不满屏、每页末尾都挂邮件订阅、表单只道谢不真发。Floor 永不放行（对比度、焦点、reduced motion、编造事实、手机布局坏掉），Reflex 是模型默认会犯、有理由可以申辩覆盖的默认项，Finish 是不挡发布的工艺细节；末尾还有 real-browser lint 和一个 fresh-context reviewer 收口。README 另记了五十套主题、755 张开放许可照片、/hallmark redesign <path> 与 /hallmark audit <path>，并署明 Made by Together AI。这些是作者自述，不是仓库元数据；本次用 /contents/skills 只数到 1 个目录 hallmark。它的形状是「先把不许出现的东西钉死，再让 agent 生成」。

impeccable 卡在生成后做审查。它也有 polish / bolder / quieter 这类生成前引导，但 README 自己把主战场写死了：Impeccable is strongest on interfaces that already exist: point it at a page or a component and iterate. 按自述，critique 按可用性启发式打分并把该改的排出来，audit 查无障碍、性能、主题与响应式并按 P0 到 P3 分级，62 条确定性规则做 slop 检测、No LLM, no API key，命令行侧还能 npx impeccable detect src/、--json、--list-rules。/impeccable init 先读代码写出 PRODUCT.md，/impeccable document 把既有视觉系统记进 DESIGN.md。它不轻：Rust、Cargo.toml、crates/、cli/，根目录二十多个点号开头的配置目录（.claude / .cursor / .codex / .gemini …），/contents/skill 下是 SKILL.src.md 加 agents / reference / scripts 等 5 项。审查要跑规则引擎，这份体积是代价。

jakubkrehel/skills 卡在直接给素材。它不规定流程，只把 15 个技能目录摊开——本次 /contents/skills 数到 better-interface、better-ui、better-typography、better-colors、better-accessibility、better-layout、better-writing、interface-review、explain-interface、break、build-design、teardown、state-machine、variant、away 共 15 个。按 README 自述，better-colors 管生成色板与对比度，better-typography 管字号阶与换行，interface-review 按分支或 PR 审界面回归，break 把组件在所有场景下压测。纯 Markdown、747 KB，是三者里唯一没有编译产物的仓库：它给的是一把把随手可用的工具，不是一条流水线。

按时序排：约束在生成之前，审查在生成之后，素材在两者之外、随时可取。但要先把话说在前面——这是主战场的切分，不是能力的边界，三个仓库都在往对方那一段伸手，这一点留到 05 节具体质疑。

03 · 关键细节与数据

建库差约八个月，星差九倍，订阅比却几乎一样

把本次 api.github.com 核对的元数据并排看。建库时间依次是 2025-11-16（impeccable）、2026-04-27（hallmark）、2026-07-10（jakubkrehel/skills），最早与最晚差约八个月；星标 105,105 / 49,902 / 11,380，fork 6,245 / 2,645 / 441，最大与最小星标差约九倍。协议是两个 MIT（hallmark、jakubkrehel/skills）夹一个 Apache-2.0（impeccable），主语言分别是 CSS、Rust、Markdown，三者 default_branch 都是 main，pushed_at 分别停在 2026-11-05T13:16:31Z、2026-11-07T03:10:10Z、2026-11-07T05:39:03Z。

更该看的是订阅与星标之比：222 / 105,105 约 0.21%，98 / 49,902 约 0.20%，41 / 11,380 约 0.36%。三个都是「先收藏」的量级，最轻的 jakubkrehel/skills 反而比例最高。换句话说，105,105 星描述的是分发广度，不是有多少人真把它装进了项目；用星数直接给三者排座次，量的其实是同一种东西。

体量差反过来印证了三段。impeccable 897,762 KB 的 Rust 仓要装规则引擎、CLI、二十多种 agent 的 hook 适配；hallmark 233,716 KB 的 CSS 仓带 site/、docs/、eval/、skills/，按 README 自述还压着五十套主题和 755 张图；jakubkrehel/skills 747 KB 只有 skills/ 加 AGENTS.md、CLAUDE.md。要跑确定性审查就得背一个编译器，只发 Markdown 技能就几乎不占地方——体积不是偶然，是各自那一段的成本结构。

有一处口径必须挑明。选题里给 hallmark 的「本周 GitHub Trending 增 6,900 星」和给 jakubkrehel/skills 的「本周增 1,921 星」，本次无法从 GitHub API 复核：API 只返回累计 stargazers_count，不返回周增，所以这两个数只能写作「本周 Trending 标注」，不能当实测写进正文，impeccable 没有给周增数，本文也不替它编一个。同样，五十套主题、62 条规则、755 张照片都是 README 自述，本文只核到仓库元数据与 /contents 的目录条目数，没有逐个打开 SKILL.md 去数规则条数。

04 · 怎么用

先定位你被卡住的那一刻，再挑安装通道

三条安装命令都取自各自 README（作者自述，非本次实测）。hallmark 是 npx skills add nutlope/hallmark -g，单装一个 harness 加 --agent claude-code；当 Claude Code 插件用是 /plugin marketplace add nutlope/hallmark 再 /plugin install hallmark@hallmark；从克隆装则跑 node skills/hallmark/scripts/install.mjs，它会先校验主题再拷贝，install-hook.mjs 给 Claude Code 加一个编辑期的 Floor 检查。改页面用 /hallmark redesign <path>，只出报告用 /hallmark audit <path>。

impeccable 在项目根目录跑 npx impeccable install，重载编码工具后执行 /impeccable init（Codex 上是 $impeccable init）；命令行审查是 npx impeccable detect src/、npx impeccable detect --json .、npx impeccable detect --list-rules，还能 --github 出 GitHub Actions 注解。jakubkrehel/skills 最省事：npx skills add jakubkrehel/skills，插件通道是 /plugin marketplace add jakubkrehel/skills 再 /plugin install interfaces@interfaces。注意最后这个 plugin 名是 interfaces@interfaces，不是仓库名 skills，照仓库名敲会装不上；手动拷贝那类路径也各有讲究，impeccable 给的是 mkdir -p your-project/.claude/skills && cp -r .claude/skills/impeccable your-project/.claude/skills/。

判断表如下，A 是 hallmark，B 是 impeccable，C 是 jakubkrehel/skills：

  • 页面还没生成，你最怕一上来就是紫蓝渐变、卡片套卡片、每个标题顶一条 eyebrow——选 A。先把 Floor 硬底线钉死再让 agent 动手，是它唯一在做的事；代价是接受五十套主题定死的风格、233,716 KB 体积和 Together AI 那条产品化路线。
  • 页面已经在了、要在合进去之前把 P0 挑出来，或团队想把「AI 味」变成机器可判定的规则——选 B。62 条确定性规则、P0–P3 分级、--github 注解能直接进 CI，主战场就在发布前那道关；代价是 897,762 KB 的 Rust 仓和 npx impeccable install 铺开的整套 hook。
  • 你不想要一整套流程，只想做配色时调一把、改 PR 时调一把——选 C。15 个纯 Markdown 技能按需取用，747 KB 最轻，判断权还在你手里；代价是「什么时候该调哪个」没人替你决定。
  • 只想要方法论，或要一条完整链路——前者三份 SKILL.md 读一遍就够，一个都不装；后者可以 A 打底、B 验收，两者通道不同（npx skills add nutlope/hallmark -g 对 npx impeccable install），不冲突。
05 · 冷思考

「卡在哪一段」是主战场，不是谁的能力边界

先质疑星标。105,105 对 11,380，差了约九倍，可订阅比是 0.21% 对 0.36%，反倒是小的那个更高；三个仓库 pushed_at 挤在最近两三天，created_at 却横跨约八个月。这更像同一波 agent skill 风口的收藏，不是三次分层验收。impeccable 建库早、README 里列了一长串支持的编码工具、官网有完整 docs，这些分发投入会放大星数；把星最多直接读成「三段里最好的一段」，量的其实是曝光。

再质疑三段划分本身，这是最该拆的一处。hallmark 的 README 里明明写着 /hallmark audit <path>、real-browser lint 和「A fresh-context reviewer gets the last word」——它也做生成后审查；impeccable 的 description 头半句是 Steer with polish and bolder，README 还说能 build new pages，并不是只会审；jakubkrehel/skills 那 15 个目录里，interface-review 是审查、build-design 是生成、break 是压测。所谓三段，是各自重心，不是互斥的能力清单，三家都在往全链路长；拿「卡在哪段」当永久标签，过两个月就会贴错。

第三处是成本的换法没进账。impeccable 的 62 条规则标着 No LLM, no API key，看着最省，换来的是 Rust 编译器、二十多个 agent 配置目录、每个工具一套 hook；hallmark 用五十套主题和 755 张图把审美打包给你，也把风格锁死；jakubkrehel/skills 747 KB 最轻，却把「何时该调哪个技能」的判断全留给人。三者都在把一种开销换成另一种：约束换自由度、审查换体积、素材换判断力。还有个更琐碎的现实——README 列「支持」和真装对是两件事，jakubkrehel 的插件叫 interfaces@interfaces，impeccable 每个工具的 skill 路径都不同，光是把 hook 指对就得照文档逐项核。

第四处是数字的边界要按字读。除了仓库元数据，本文写进来的五十套主题、62 条规则、755 张照片、一长串支持工具，全部出自 README 自述；周增 6,900 与 1,921 只是「本周 Trending 标注」，API 复核不了；/contents/skills 数到的 15 个目录、hallmark 的 1 个目录、impeccable /contents/skill 下的 5 项，是本次唯一逐项数过的「文件数」，且数的是目录条目，不是 SKILL.md 里的规则数量。把作者自述当实测、把周榜标注当增长曲线，是这类横评最容易滑出去的一步。
