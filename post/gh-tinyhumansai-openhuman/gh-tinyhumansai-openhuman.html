42,802 星、7/10：OpenHuman 的快和省都有前提

42,802 星的 OpenHuman 说 500 个 agent 能装进 10 美元 VPS，任务 19.8 秒完成，token 省 2.6 倍。公开基准里它只解出 7/10 道题，Jev 的 86.8% 是候选召回率。前提都写在文档里。

expectopatronus 2026-11-22 约 6 分钟阅读 原创 · AI 编程

01 这件事

它把 agent 从「一人一进程」压进一个 Rust 进程，再把压缩后的数字放在 README 首页：19.8 秒、省 2.6 倍 token、500 个 agent 上 10 美元 VPS。三个数字都有出处，也都带前提。

tinyhumansai/openhuman 在 2026-02-18 创建，截至 11-22 有 42,802 星、4,229 fork，许可证 GPL-3.0，主语言 Rust，最近推送停在 11-20。11-12 入池时是 78 分的 pending，第 10 天复核仍活跃，不标 stale。

README 首页的三张牌排得很整齐：

  • 快：七种工具里任务耗时约 20 秒，冷启动十分之一秒
  • 省：token 用量为常见工具的四成，账单最低
  • 密：单进程跑 500 个 agent，10 美元服务器装得下

README 同时挂着 early beta 徽章，正文写明「expect rough edges」。这是自述与实测混排的一页，分开读才不会把前提丢掉。

02 核心机制

它省的不是模型调用本身，而是每次调用前送进去的文本，以及每个 agent 都要付一遍的进程固定成本。架构围绕这两处做减法。

机制做法可核对的数字
RLM 压缩大工具结果先压缩，超大的给句柄供搜索基于 arXiv 2512.24601
Jev 工具检索小模型从目录中挑工具，再直接调用目录 1,215 个工具
统一 Rust 总线功能按需加载，一个卡住不影响其他11 个可加载模块名
内建记忆每轮按预算挑内容，带引用交给模型可换记忆引擎
浏览器与桌面控制用真实 Chrome 与桌面 App，付款前停顿按屏幕按钮点选
可嵌入核心一个进程编译成库，无 sidecar冷启动 102 ms（mock）

压缩这一环不是删结果。README 说大段工具输出先压缩，超大的给模型一个可搜索的句柄，「什么都没扔掉」，依据是 arXiv 2512.24601 的 Recursive Language Models。省的是送进上下文的 token，不是把证据丢了。

记忆也不是外挂。每轮开始前，核心按 token 预算从文件、仓库和 App 里挑出相关片段，带引用交给模型；换引擎只需改配置。搜索、文档、语音挂在同一条总线上，按需加载，一个模块卡住不会拖死整个进程。

Jev 的 1,215 不是凭空来的。docs/plans/jev-tool-search-baseline.md 写清了拆分：

  • 编排会话已注册的核心工具：215 个
  • Composio 目录记录的延迟加载动作：1,000 个
  • 测试意图：160 条，其中 66 条标注 Composio 动作、63 条核心工具、31 条不该调工具

仓库里 crates/ 下有 8 个 crate 目录：app、cli、core、embed、modules-linked、rpc、tinyhumans、tui。桌面、终端和可嵌入库共用同一个 core。

工具检索比关键词命中的提升，发生在「短名单」这一层。产品默认是 embedding 先取 20 个候选，Jev 再决策一次，整条链只消耗一轮代理请求。

排序方式top-1top-3召回@20
BM25 关键词22.5%38.0%70.5%
Jev + embedding（产品默认）62.0%66.7%86.8%

1,215 个工具能被找到，不等于 86.8% 的请求一次选对。这两行的差别是后面冷思考的起点。

成本口径也要看清：每解一题的费用是总花费除以解出的题数，失败尝试留在分子里。OpenHuman 全程发了 114 次模型调用，其中 6 次来自子 agent；缓存命中率 90.6%，不是全场最高，也不是最低。

费用那一行还有个细节：OpenCode 也是 $0.0077，README 自己标成并列最好。「最低账单」成立，但不是独占第一。

04 怎么用

三种入口共用一份核心：桌面 App、终端 CLI、Rust 库；真正影响成本的是你开了哪些域、接了哪些外部服务。

  • 桌面安装包：macOS 用 .dmg，Windows 用 .msi 或 .exe，Linux 用 .deb 或 .AppImage
  • 安装脚本：macOS / Linux 用 install.sh，Windows 用 install.ps1，都带校验和检查
  • 嵌入方式：openhuman_embed 里构造 Harness，指定 provider 与 workspace，再 run()

模型侧支持本地 Ollama、LM Studio、MLX，也支持 26 家供应商的 BYOK 和自动路由。模型钱你自己付，仓库里的成本数字只覆盖那 10 道题的 API 调用。

搜索默认带 Exa 与 Gemini，Brave、Tavily、Parallel 等要自己的 key；消息渠道包括 Telegram、Discord、iMessage 和邮件。工作流支持定时、事件或手动触发，允许插入审批步骤，暂停后从断点继续。

集成面很宽：Composio 的 119 个 OAuth 应用、MCP 与技能包、14 个消息渠道。外部账号是否授权、按量计费多少，都要另算。

使用档位配置代价
桌面日常默认 features + 桌面 App二进制最大，功能最全
无头嵌入skills,flows 或纯 slim最小二进制约 51 MB（strip 后）
满负载机群单进程 + 多 AgentSpec需按真实 provider 重测容量

安全边界写在 SECURITY.md：密钥存系统钥匙串，消息内容不用于训练；只支持最新版与上一小版本，更早版本不保证补丁，漏洞走邮件而不是公开 issue。

要复现 500 agent 那组数，得先按文档指定的 commit 构建。当前树跑同一个 example 还需要 storage-sqlite，新旧配置的结果不可直接比较。

05 冷思考

最长的短板不是速度，是 7/10 与 500 之间那段没有公开实测的距离。README 把三套前提条件压成了三行卖点。

README 的表述原始文档里的口径
「正确的工具在 Jev 首选里 86.8%，关键词 70.5%」这两数是 embedding 与 BM25 的召回@20；产品默认 Jev 的 top-1 是 62.0%
「500 个 agent 上 10 美元 VPS」密度数据来自 mock 推理，不是真实 provider 加工具的压力测试
「七种工具里最快」按每道解出的题统计，OpenHuman 只解出 7/10

机群文档自己写得克制：macOS 那组 1,770 KiB / agent 用的是 200 ms 固定延迟的 mock provider，线程数随 agent 增长，「数千个 agent」只是目标，不是测过的结果。

macOS 那组的规模梯度也值得看：50、100、500 个 agent 的边际内存分别是 1,985、1,866、1,770 KiB，空闲 CPU 都是每 10 秒 3 毫秒。线程数从 71 涨到 211，文件描述符从 420 涨到 3,220。

Linux 那组更接近真实部署：2 GiB 与 2 CPU 配额下，500 个并发 agent 的边际内存是 3.355 MiB / agent，cgroup 峰值 1,760 MiB，整队耗时 20.8 秒。

关掉 swap 后再跑一次，边际值升到 3.541 MiB，超过文档给的双倍目标 3.46 MiB。文档明确说，这些数不证明真实 provider、工具子进程或 1,000 个同时 active 的 turn 能活下来。

工程成熟度也要跟上。305 个未结条目里 272 个是 issue，最新 Release 停在 10-09；issue #8759 报 .deb 在 Ubuntu 22.04 上要求 GLIBC_2.39，#8765 说策略描述默认 autonomy policy 已开启。

安全响应写的是 5 个工作日内确认，漏洞走 security@tinyhumans.ai 并适用安全港条款。但它只承诺最新版与上一小版本的修复；最新 Release 已停在 10-09，实际补丁窗口要按自己的发布节奏判断。

它适合把单人或少量 agent 的开销压低，也适合当 Rust 库嵌进自己的服务；不适合只按 README 的 500 与 19.8 秒做容量和验收预算。先看你的任务在不在那 7 道里，再按自己的 provider 重跑一遍机群脚本。
