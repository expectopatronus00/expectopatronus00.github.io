Uncle Bob 把工程纪律写成了 Skill：ub-mode 的三道硬闸门

《Clean Code》作者 Uncle Bob 开源了一个 Agent Skill：ub-mode。仓库只有一份 4KB 的 SKILL.md，四天拿到 4374 星。它不教 AI 写代码，而是给 AI 立工程纪律——并且不靠嘴说，靠三个能算出数字的检查工具。

01 · 这件事

4KB 的 Markdown，四天 4374 星

2026 年 10 月 25 日，Robert C. Martin（圈内称 Uncle Bob，《Clean Code》《架构整洁之道》的作者）在 GitHub 发布了 ub-mode。仓库里没有一行程序代码，只有一份 SKILL.md，整个仓库 4KB。

四天后它的数据是：4374 星、241 个 fork、6 个 open issue。对一个只装了一份 Markdown 的仓库来说，这个速度说明的不是代码质量，而是需求存在——太多人受够了 AI 写出来的东西「能跑但没法维护」。

ub-mode 的定位很明确：它不是让 AI 更会写代码，而是让 AI 按工程纪律写代码。README 里也老实交代了来源——它脱胎于 @poteto 的 poteto-mode / pstack 规则，做了删减，然后配上一组确定性的质量闸门工具。

数据核对：仓库创建于 2026-10-25T16:04Z，本文写作时（2026-10-29）4374 星、241 fork、6 个 open issue，仓库体积 4KB、无 LICENSE 文件。星标是会变的，引用时请以仓库实时数据为准。
02 · 它规定了什么

先跑通、再改对、然后才是日常

整份 SKILL.md 分成三段，顺序本身就是态度：先让东西能跑，再让它变对，最后才谈习惯。这个顺序和很多「代码规范」相反——大部分规范一上来就要求你优雅，ub-mode 要求你先交付。

第一段：First Make it Work（先跑通）。里面塞了九条原则：Laziness Protocol（懒汉协议）、Foundational Thinking（先想地基）、TDD、Redesign From First Principles（从第一性原理重设计）、Attack the Premise（质疑前提）、Subtract Before You Add（先减后加）、Outcome-Oriented Execution（以结果为导向）、Build the Lever（造杠杆），以及一整套架构要求：领域建模、边界纪律、类型系统纪律、操作幂等、共享状态先分离再序列化。

这一段的重点是两条容易被忽略的：Attack the Premise 要求 AI 在动手前先问「这个需求本身成立吗」；Subtract Before You Add 要求加功能之前先看能不能删。这两条恰恰是 AI 编程最容易失守的地方——模型天然倾向于「加点什么」来解决问题。

第二段：Then Make it Right（再改对）。修根因不修症状、把工作切成可验证的小单元、测行为而不是测实现，最后才是重构。注意重构被放在最后——不是不重要，而是在测试和行为边界没立住之前，重构等于赌博。

第三段：Practice（日常）。记工作日志、守住上下文窗口、清理 worktree、按顺序小步提交。这一段最像「老工程师的碎碎念」，但对长跑 Agent 任务特别有用：上下文窗口一旦被垃圾信息灌满，前面所有纪律都会失效。

03 · 三道硬闸门

AI 说「我测过了」不算数，数字才算

这份 Skill 真正有意思的地方，是它不满足于「告诉 AI 要守规矩」。规则写在提示词里，模型可以选择性遗忘；能算出数字的工具不会遗忘。ub-mode 配了三个这样的工具，都是 Uncle Bob 自己的仓库：

crapper（139 星）：算每个函数的圈复杂度、测试覆盖率和 CRAP 分数，阈值定在 CRAP < 10。CRAP 这个指标的含义是「复杂且没测试覆盖的代码，改动风险有多高」——复杂度越高、覆盖越低，分数越难看。

dryer（64 星）：查结构性重复，相似度 >= 0.8 的代码块判为重复，要求消除。它查的不是文本重复，是结构重复，所以改个变量名糊弄不过去。

mutator（81 星）：跑变异测试。做法是往代码里注入小错误，看测试能不能抓住；抓不住的变异体（surviving mutant）就是测试的盲区。它的三个动作写得很直白：补上没覆盖的、杀掉活下来的、删掉死代码。

三个工具都是 Python 写的、0BSD 协议，输出统一是 uml-viewer（471 星，Clojure）能读的快照格式——后者把复杂度、覆盖率、CRAP、变异分数和依赖方向画成一张类图。四个仓库合起来，才是一套完整的闭环：写 → 量 → 看 → 改。

这里有个容易误解的点：ub-mode 仓库本身只有 SKILL.md，三个闸门工具是独立仓库。只装 Skill 不装工具，你得到的是「一份更详细的提示词」；把工具也接上，才拿得到可核对的数字。
04 · 怎么用

装法只有一行，但别只装这一行

安装本身简单到没什么可讲：把 SKILL.md 复制进对应 Agent 的 skills 目录，然后调用。

cp ub-mode/SKILL.md ~/.claude/skills/ub-mode/SKILL.md

路径按你的工具换，README 里给的是 ~/.grok/skills/、~/.claude/skills/、~/.cursor/skills/ 三种，装好后用 /ub-mode 唤起。

但真正决定它有没有用的，是后面两步：一是把 crapper / dryer / mutator 装进项目，让闸门能跑；二是在你的工作流里给它一个位置——ub-mode 适合放在「功能写完了，准备提交」这个节点，而不是一开始就让它在旁边指手画脚。先跑通再改对，这个顺序它自己也是这么要求的。

05 · 冷思考

纪律不是许愿池

先说清楚一件事：4374 星里，有相当一部分是冲着 Uncle Bob 这个名字来的。同样一份 SKILL.md 换个无名作者发布，大概率不会有这个量级。热度不等于内容含金量，这一点得分开看。

第二个更实际的问题：把纪律写进提示词，和 AI 真的遵守纪律，是两回事。模型会不会在长任务里忘掉前面的约束、会不会嘴上说「已按 TDD 执行」实际没写测试——这些都发生过。ub-mode 的价值恰恰在于它意识到了这一点，所以才配了三个能算数的工具。如果只装 Skill 不装工具，你买到的是一份更啰嗦的提示词。

第三个问题是对个人项目的适配度。CRAP < 10 这类阈值是按生产代码设计的；你写个一次性脚本、做个数据清洗，硬套这套标准只会拖慢自己。ub-mode 自己的分段结构其实给了答案——第一段「先跑通」是普适的，第三段的日常习惯看情况，中间那套量化闸门留给真正要长期维护的代码。

如果只想拿走最划算的部分，我建议两条：Attack the Premise 和 Subtract Before You Add。前者让 AI 在动手前先质疑需求，后者让它在加东西前先想能不能删。这两条不依赖任何工具，塞进你自己的 CLAUDE.md 就能用，收益却是最大的一档。

至于 ub-mode 本身，它更像是这个阶段的一个信号：Agent Skill 正在从「教 AI 做事」走向「给 AI 定验收标准」。前者靠提示词，后者必须靠工具链。这个转向，比某一个具体 Skill 值得关注得多。
