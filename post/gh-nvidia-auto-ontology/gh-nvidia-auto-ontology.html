01 · 这件事

12,629 星买的是一层「定义」，不是更快的问答

GitHub 上 0 个 Release，12,629 星却仍在涨，这件事本身要先解释清楚。NVIDIA/auto-ontology 创建于 2026-04-27，Apache-2.0，主语言 Python。

换句话说，这不是一个塞进 ~/.claude/skills 就能用的技能包。它是一套要起数据库、后端、前端和 MCP 服务的语义层，仓库自带的三个 skill 只是教 agent 怎么操作这套服务。本文只做文件级反查，未部署、未跑任何基准。

02 · 核心机制

生成、认证、回答三段流水线，人卡在中间那一段

最关键的机制不是检索，是「人必须先认证定义」。README 把流程写成三阶段：机器从数据库生成一版本体草稿，人把它改对并认证，agent 才被允许据此回答。自动生成的草稿不算数。

阶段谁做步骤产物
Generateingestion 服务4 步术语、关系、SQL 属性与 pgvector 向量
Certify人3 步认证过的名称、描述与度量表达式
Answeragent5 步答案、SQL、所用步骤

本体里存三类定义。Terms 是 Customer、Invoice Line 这类业务概念，带描述、同义词和映射列；SQL attributes 是审过的度量表达式，比如毛利率，agent 复用它，保证每次算同一个指标口径一致。

Relationships 是表怎么连，含桥表，由键和数据推断。Generate 阶段依次读 schema、逐表命名实体、推断 join、把三者写进 Postgres。README 给的示例里，一次编译 Wide World Importers 得到 31 个 terms。

示例问题是 2015 年 6 月宾州某商品的收入，答案回来 588.80 美元、3 条 invoice line，同时附上六表 join 的 SQL 和「解析了哪些 term、怎么连的表」的步骤。答案必须自带可回查的 SQL 和血缘，这是它比纯向量检索更硬的地方。

更值得写下来的是不回答的路径。README 演示问「广告支出回报率」，agent 先跑 check_answerable 得到 coverage 0.5，发现没有 term 覆盖 ad spend，于是反问是改问收入、还是去接另一个数据源。宁可承认不可答，也不硬编一个数字。

04 · 怎么用

先把六个组件起起来，再让 agent 通过 MCP 只读地问

agent 侧的接口是只读的，写操作一律走 Web 应用的 /api 路由。AGENTS.md 把这条写成硬规定：MCP 不能写，术语、关系与认证的修改由 management 技能走 Next.js 的 API 面，每个调用都带上登录用户的权限。

用途README 列出的 MCP 工具
就绪check_readiness
查术语与表search_terms、get_term、get_term_columns、get_term_sql_attributes、get_sql_attribute、describe_table
可答性check_answerable
提问ask_question

本地 quickstart 的顺序是固定的。先克隆仓库并复制 .env.example，填好 NVIDIA API key 与几个密码；再起 Postgres，用另一个仓库的 seed 脚本灌入 Wide World Importers 示例库，然后执行 docker compose up -d --build。

接着要在 Settings → Semantic Compilation 里手动打开编译，等它报 ready，才能在 Chat 提问。这一步不是自动的，也意味着「开箱即用」并不准确：示例数据库、灌数脚本与管理动作都散在别处。

仓库里三个 skill 各管一段，入口是根目录的 AGENTS.md：

  • nvidia-ontology-setup：Helm 安装、Compose 本地栈、连接数据源、编译与排障。
  • nvidia-ontology-management：检查、建模、认证、导入导出与发布，是唯一覆盖写路径的技能。
  • nvidia-ontology-query：MCP 优先、REST 兜底，校验 SQL、结果行与答案。

每个 skill 目录 7 个条目，含 SKILL.md、evals 与 references，还有 BENCHMARK.md 和 skill.oms.sig。AGENTS.md 特别注明后两份由 NVSkills CI 生成、禁止手改；三份技能还会同步到 nvidia/skills 目录仓库。

不走 MCP 可以直接 POST /api/chat/completions，响应是 SSE 流，result 事件带答案，[DONE] 收尾。模型定义还能通过 Apache Ossie 的 YAML 导入导出，避免把语义层锁死在这一套实现里。

05 · 冷思考

12,629 星里，能直接拿走的是流程，不是一套能跑的服务

最该先读的不是功能列表，是 CONTRIBUTING.md 的第一行：本项目不接受外部 PR。代码由 NVIDIA 维护团队改，外部只能通过 issue 提集成请求和 bug。Apache-2.0 给了你可读、可改、可分发的权利，但没给参与协作的通道。

版本口径也值得留意。GitHub 上 0 个 Release、1 个备份 tag，pyproject 却写着 1.2.0；version.py 优先读环境变量 APP_VERSION，值由 Helm chart 版本注入。

想复现某个具体版本，得先找到 NGC 上对应的 chart version，而不是来 GitHub 找 tag。

基准同样不在这个仓库。README 的 Benchmarks 一节只有一句：跑 BIRD 这类 text-to-SQL 评测请参考另一个仓库 ontology-sql-eval。主仓库没有一个准确率数字；三个 skill 里的 BENCHMARK.md 是技能签名流程的产物，不是查询效果。

边界条款比功能表更该先读，下面几条都写在 README 或 SECURITY.md 里：

  • 网络边界：3001 与 3002 须置于私有网络，FastAPI 信任前端转发的 x-auto-ontology-user-id 头。
  • 无自身鉴权：ingestion 的 ingest / delete / reset / compile 四个端点没有独立认证。
  • 数据外发：开启 KumoRFM 后预测问题会上传连接的表，KUMO_MAX_TABLES 默认 20，每表行数默认不限。
  • 口径不齐：NIM 小节与 Models 表给出的 embed / rerank 默认模型名不一致，与 .env.example 对齐的是后者。
  • 漏洞披露：不走 GitHub issue，走 NVIDIA PSIRT 表单或 psirt@nvidia.com，目前无 bug bounty。

还有一个容易被星标盖过去的成本：四个模型角色默认全部指向 NVIDIA NIM，需要 nvapi- key；六个组件、31 个 term 的人工认证，对一个人维护的小项目远超过它能省下的返工。这 12,629 星衡量的是「企业数据语义层」这个议题的曝光，不是这套栈的可用性。

所以别把它当「给 agent 装个记忆插件」来比。真正可以白拿的是那条流程判断：先判问题可不可答，再把解析到的定义、连表路径和 SQL 一起交回来，让人能对着源数据复核。要不要为此起六个组件、交四个模型的 key，取决于你错一个数字的代价有多大——代价小，这套栈就是负债。
