8.2万星、664个菜单全通：45%能干活

81,647 星、16,643 次提交，PhotoCraft 把 Photoshop 的 664 个菜单项全部接上命令，README 却明说它不是日常工作里的替代品。生成的连通率与人工估的可用率摆在同一仓里，差的不只是数字。

02 核心机制

一个命令注册表同时喂给界面、命令行、控制通道和 MCP，这是它最像 agent 工具的地方。

README 自述菜单项、工具、对话框都走同一个注册表，规模是 500+ 命令；UI、CLI、JSON 控制通道和 MCP 服务器只是四种入口。完整树里有 25 份 Cargo.toml、2,890 个 .rs 文件，合计 43.98 MB。

入口怎么用边界
桌面界面egui 画在上面，引擎在下面命令注册表是唯一执行层
命令行photocraft-cli run / batch无界面跑动作列表
MCPphotocraft-cli mcpstdio 或桥接运行中的窗口
控制通道photocraft --control仅回环地址，需令牌

渲染层放了两个合成器：CPU 版当参考基准，wgpu 版负责画布，两者互相对照。256² 的稀疏块做写时复制，让撤销和大画布更轻；整套引擎和界面还能编译到 WebAssembly。

功能面也铺得细：README 列了 16 个调整图层、27 种 Photoshop 混合模式加 6 种 Paint.NET 变体，文档支持 8/16/32 位的 RGB、灰度、CMYK 与 Lab。格式侧覆盖 PSD/PSB、分层 TIFF、PDN3、OpenRaster、XCF、KRA 和 SVG。

  • 控制端口只监听 127.0.0.1，令牌从文件读入，Unix 下新建文件为 0600。
  • 桥接模式用 HMAC-SHA256 挑战认证，令牌不以明文发给监听方。
  • 文档明确写着令牌是 bearer 凭据，拿到令牌就拿到非文件系统控制面。
  • 文件访问默认关闭，读根与写根独立授予，缺失或非法目录直接启动失败。

这里说的是「可自动化」，不是「AI 功能」。同一份自评把 AI / 生成式能力记为 10%，并称还没有 ML 运行时；经典抠图与移除工具只是替代项。

03 关键细节与数据

仓库里同时躺着三套完成度，分母不同、日期不同，混着读就会得出错误结论。

docs/parity-checklist.md 是生成物，当前写 664/664 个菜单项在线、未完成清单为空；评测文档 10-12 的口径是 631/631，10-10 是 628/628。菜单数涨了，结论却始终是「已接通」。

拖后腿的是硬指标：25 个性能预算只有 3 个达标；Photoshop 生成的 PSD 在 oracle 测试里 133/256 匹配（10-10 基线）；插件与脚本生态 15%，AI 10%。README 自己也承认，文件能被重新保存不等于 Photoshop 一定接受。

PSD 的数字更要分开看，重存渲染和参考实现匹配不是一项测试：

  • README：重存后 309 个 psd-tools 文件中 307 个渲染一致。
  • 总评文档：10-10 基线的 psd-tools oracle 为 236/309。
  • 格式文档：11-08 更新后同一 oracle 已升到 249/309。

这些都标在 2026-10-10、Photoshop 2026 27.11.0、PhotoCraft v0.6.0 的基线上。现在稳定版已经是 v0.23.1，预发布到了 v0.24.0-rc.2；评测文档的修订记录更新到 11-10，标题口径没跟着版本走。

04 怎么用

要拿它干活，先把「批量编辑」和「替代 Photoshop」当成两件事，再决定开哪个入口。

最省事的是无界面跑动作列表：把锐化、曲线这样的命令写进参数，一条命令打开、改图、导出。批量目录则交给 batch 加动作文件，不需要桌面窗口。

场景建议入口先确认什么
批量调色 / 导出CLI + 动作文件输出格式与尺寸预算
让 agent 操作打开的窗口MCP 桥接应用版本与令牌文件
无窗口自动化headless MCP读写根目录是否授予
与 Photoshop 交换分层文件桌面应用目标端能否重新打开

发布包覆盖 macOS、Windows、Linux、FreeBSD 与 Web；最新稳定版挂了 52 个资产，Linux 一侧有 AppImage、deb、rpm、tarball 和 Flatpak 五种形态。

桥接模式只认字面量回环地址，不解析 localhost，避免被 DNS 指向另一个监听者。连接空闲会被服务端关闭；发送后没收到回执的编辑不许自动重发，要先检查文档状态。

  • 起服务时用 --control-token-file，别把令牌写进命令行参数。
  • 用 --automation-read-root 与 --automation-write-root 分开授权。
  • 复核进度可跑 cargo xtask parity 与 cargo xtask scorecard，别直接改生成表。

如果日常依赖插件、生成式填充、复杂排版或稳定交付给 Photoshop 的 PSD，先做一次真实文件往返测试。README 给的建议很直白：报告问题时带上系统、文档尺寸、图层数和截图。

05 冷思考

100% 是机器测出来的分母，45% 是人估出来的判断，别拿前者替后者背书。

664/664 数的是菜单项能否派发命令，不是像素是否一致。评测文档也承认，菜单目录由项目自己照着 Photoshop 写，没解析 Photoshop 的 Default Menus.mnu，27.x 新增项可能根本不在分母里。

  • 「约 45%」是加权估算，不是跑出来的通过率；区间 40–50% 本身就说明口径弹性。
  • 剩余工时按 Opus 5.5 agent 小时估，基于 1,004 个已合并 PR；它是尺度参照，不是交付承诺。
  • 令牌拿到的是整套非文件系统控制面，安全边界落在令牌保管，而不是逐方法授权。
  • 16,643 次提交对应 4,050 个开放 issue，铺开速度与收敛速度不是一回事。

语言表也有口径差：12 种关键语言里 7 种 UI 键覆盖 100%，但引擎消息仍是英文；印地语与阿拉伯语没有词库，界面也不支持 RTL。界面翻译完成不等于本地化完成。

还有一个时间差值得记住：README 里的界面截图和 1,700 多项测试是真的，v0.6.0 时代的 45% 也是真的，但两者隔了 17 个小版本。拿旧评估给新版本担保，等于替别人做判断。

我会把它当一条可控的编辑管线看：命令注册表、双合成器、回环控制通道都做得扎实；至于「Photoshop 开源替代」，项目自己都没这么写。选它，是选自动化能力，不是选一次平替。
