录一遍操作，AI 自动生成可复用 Skill：一个新的工作流正在形成

你不再需要手动写 Skill 了——现在只需要对着电脑做一遍你想让 AI 做的事，它就能自动把这段操作「理解」成一个可复用的 Skill。下次同类任务，直接调出来用，效率提升不止一个量级。

01 · 先演示一遍

把你想做的事做一遍，AI 帮你翻译成 Skill

传统方式是这样的：你打开 Claude，告诉它「帮我写一个读取 JSON 文件的函数」。然后它写了第一版，你发现需要加错误处理。于是再发一条 Prompt，它改了。然后你又发现需要支持大文件……这个过程可能要来回十几次。

新方式完全不同：你打开电脑，对着它做一遍「读取 JSON 文件」这件事——打开文件、解析内容、处理异常、返回结果。全程录制。

AI 在后台看完你的操作后，直接生成一个叫 read-json-skill 的东西。下次你只需要说「用 read-json-skill 处理这个数据」，整个流程就跑完了。

不是 AI 学你的操作，而是 AI 把你的操作「翻译」成了一种它能理解并复用的格式。

02 · 它到底是怎么工作的

三步：从录制到可复用 Skill

这套流程分为三个阶段，每一阶段都有明确的目标：

第一步：操作录制。你对着电脑完成一个任务，工具在后台记录你所有的操作轨迹——点击了哪个按钮、打开了哪个文件、输入了什么内容。关键不是录屏，而是录「意图」：你在做什么、你为什么要这样做。

第二步：意图翻译。AI 读取录制数据，识别其中的「模式」——哪些是重复步骤、哪些是关键决策点、哪些可以参数化。然后生成一段结构化的 Skill 定义：输入是什么、输出是什么、中间的逻辑是什么。

第三步：测试与迭代。生成的 Skill 先在小样本上跑一遍，验证它是否真的复现了你的操作。如果不对，告诉 AI「第三步漏掉了异常处理」，它会修正。这个过程可以循环，直到 Skill 达到可用状态。

03 · 和传统 Prompt 相比好在哪

从「说一次做一次」到「做一次用一辈子」

传统 Prompt 是线性的：你说一句，AI 做一步。你每次遇到同类任务，都要重新说一遍。

Skill 是结构化的：你录一次，AI 生成一份可复用的操作定义。下次遇到同类任务，一句话调用。

举几个具体例子：

代码评审：你做一遍「找出这个 PR 里所有潜在 bug」的操作，AI 生成 code-review-skill。以后每个 PR 过来，直接调。

数据清洗：你做一遍「把这份 CSV 里空值填上默认值」的流程，AI 生成 clean-csv-skill。以后每份数据，丢进去就能用。

文档生成：你做一遍「根据代码注释生成 API 文档」的操作，AI 生成 gen-doc-skill。每次写完代码，调一下就有文档。

04 · 现在的局限性

它不是银弹，有些事它还做不好

尽管这个方向很有潜力，但目前的实现还有几个短板：

1. 操作粒度依赖录制质量。如果你的录制过程有冗余步骤，生成的 Skill 会包含无效逻辑。如果录制太粗糙，Skill 可能漏掉关键细节。

2. 参数化能力有限。目前大多数系统只能处理结构化数据（如文件路径、列名）。对于更抽象的参数（如「什么样的代码算有 bug」），还需要人工补充 Prompt。

3. Skill 之间没有标准协议。不同 AI 工具生成的 Skill 格式不通用，迁移成本高。

使用建议：先把 Skill 用来处理「规则明确、输入结构化、输出标准」的任务——这是它目前最擅长的场景。

05 · 展望：每个人都能成为 Skill 开发者

不需要写代码，你的工作流就是最好的 Skill

这件事最大的意义不是「省代码」，而是它让 Skill 的生产门槛大幅降低了。

以前，一个 Skill 需要：懂技术的人 + 理解业务的人 + 愿意写 Prompt 的人，三者缺一不可。

现在，一个 Skill 只需要：愿意做一遍这件事的人。剩下的，AI 来翻译。

这意味着，非技术背景的人也可以把自己工作中的重复操作变成 Skill。整个团队的工作流可以指数级地积累和复用。

未来的工作场景，可能是这样的：你早上打开电脑，调出昨天录制的「分析竞品数据」Skill，输入今天的链接，整个分析报告 10 分钟生成。

Skill 化的本质，是把你的工作流变成可积累的资产。你的每一个「再做一遍」，都在让 AI 变得更懂你。
