113812 星对 33587 星：一个省历史，一个省回显

113,812 星、9,873 fork，claude-mem 把旧会话压成摘要注回新会话；33,587 星的 context-mode 压的是工具回显字节。两者都号称省上下文，却压在不同层。传得最广的「98%」其实只是 HN 帖子标题。

expectopatronus 2026-11-06 约 9 分钟阅读 原创 · AI 编程
01 · 这件事

两个都在给 agent 省上下文，一个管「过去」，一个管「当下」

thedotmack/claude-mem 于 2025 年 8 月 31 日建库，到 2026 年 11 月 6 日是 113,812 星、9,873 个 fork、358 个订阅者、127 个未关闭 issue，Apache-2.0 协议，TypeScript，仓库体积 784,595 KB，最后一次 push 停在当天 11 点 52 分。它的 description 写得很直白：捕获会话里 agent 做的一切，用 AI 压缩，再把相关上下文注入未来会话，支持 Claude Code、OpenClaw、Codex、Gemini、Copilot 等一长串宿主。

另一个是 mksglu/context-mode，2026 年 2 月 23 日建库，33,587 星、2,305 个 fork、107 个订阅者、6 个未关闭 issue，JavaScript，53,235 KB，同日 13 点 11 分刚 push 过。description 是：一个免费的本地插件，把工具输出挡在 coding agent 的上下文窗口之外，用 sandbox 加 SQLite FTS5 搜索，让进上下文的字节少 99%。有一处口径要先记下：GitHub API 给它的 license 字段是 Other / NOASSERTION，而 README 的徽章写的是 ELv2。

两个仓库差了 80,225 星，建库差了近半年，但真正要命的差别不在体量。它们压缩的根本不是同一段上下文：claude-mem 压的是「上一次会话留下的历史」，context-mode 压的是「这一次会话里工具刚吐出来的字节」。前者是时间维度，后者是 I/O 维度。把它们当成同类工具二选一，一开始就把问题问错了。

它们在积压队列里同属 context-memory 一族，一条 87 分、一条 85 分，所以这篇是横评，一次消耗两条。下面先把「压缩发生在哪一层」拆开，最后给判断表。

02 · 核心机制

一个在会话之间搬运记忆，一个在工具返回之前截住输出

claude-mem 的压缩发生在会话结束之后。README 把骨架列成六层：六类 lifecycle hook（SessionStart、UserPromptSubmit、PreToolUse、PostToolUse、Stop、SessionEnd，每条只是 claude-mem hook claude-code <event> 这样一条命令）、Smart Install、由 Bun 管理的 Worker Service 本地 HTTP 服务、存 sessions / observations / summaries 的 SQLite、mem-search skill，以及做混合检索的 Chroma 向量库。它捕获的是 README 里叫 tool usage observations 的东西——agent 用过什么工具、改了什么、下过什么判断——再用 AI 生成 semantic summaries 落库。

注入发生在下一次会话的 SessionStart。新会话一开头，相关摘要被注回上下文，agent 于是「记得」上个会话做过什么。它管的是跨会话的历史记忆：为了让新会话接上旧会话，你本来得把整段历史重新贴进去，claude-mem 把这笔开销换成一小段摘要。它完全不碰当前会话里正在产生的工具输出——那些字节照样一条条进上下文。

context-mode 反过来，压缩点在单次会话内、工具返回的那一刻。agent 读文件、跑命令、抓网页，结果不直接回上下文，而是先落进本机 ~/.context-mode 下按项目分的 context.db（SQLite FTS5 索引）；agent 要哪一部分，用 ctx_search 检索，或者按 README 说的「Thinking in Code」写一段短脚本在 sandbox 里处理数据，只有脚本 print 出来的那几行进入上下文。

所以它省下的是工具回显的原始大块字节：一次 gh issue list --json 的输出、一份 1,999 行 syslog、一页 Chrome DevTools 快照、5,000 条 JSON 记录。这些原本会一口气塞满窗口、把会话逼进 compaction。context-mode 不记「上周为什么选了这个方案」，不跨会话，也不做 AI 摘要，它是纯字节层面的拦截。一个省「过去」，一个省「当下」，作用在不同层，理论上可以同时装。

还有一处容易混的账。claude-mem 的 README 也写 ~10x token savings，但那是它 4 个 MCP 工具的三层检索策略：先 search 拿紧凑索引（约 50–100 tokens/条），筛完再 get_observations 取详情（约 500–1,000 tokens/条）。省的是「从已存记忆里取多少」，不是压缩率。两处的「省」根本不是同一个分母。

03 · 关键细节与数据

「98%」是帖子标题，仓库自己的基准写的是 99.4%

先处理那个被传得最广的数字。context-mode 的 README 在 Adoption 一节收录了 2026 年 2 月 28 日 Hacker News 的一条：帖子标题是 MCP server that reduces Claude Code context consumption by 98%，570+ 分、107 条评论，上了首页。「压掉 98%」是那条帖子的标题，不是仓库跑出来的基准。仓库 description 的自述是 99% fewer bytes in context，README 里带日期、带 commit 的基准是 2026-11-01 那次（2.0.0-next.23，commit 16a4bcc5，median of 5 runs）：36 行原始输出 ≥10 KB 的样本，回复字节的中位数比原始输出小 99.4%。

这些基准自述值得逐条看分母。同一次 bench 里，一次完整调试会话 281,261 B 原始输出压到 3,266 B 进上下文（约 70K → 817 tokens，按 4 B/token 估算）；压缩后接着跑的一段 442,893 B transcript 变成 2,019 B 的块（约 111K → 505 tokens）。README 另记了一次会话：1015.5 KB 变 3.7 KB，99.6% 的字节被挡在外面，约 259K tokens，相当于 1.3 个 200K 窗口。四行 bench 表里，gh issue list 列 40 条是 182,943 B → 850 B（99.5%），gh pr list 列 25 条是 195,471 B → 776 B（99.6%），Context7 查文档 6,917 B → 473 B（93.2%）。

try-it 那组数更能说明口径。2026-11-02 的四次 live 运行里，5,000 条 JSON 记录那次是 1,039,898 B → 393 B、99.96%，README 自己补了一句 this is the best case of the four——答案只是两个短事实，所以这是最优情形。同一组里网页抓取是 96.5%，十条故事是 95.7%，1,999 行 syslog 是 99.7%。分母始终是「工具原始输出字节」，不是整个上下文窗口；把 98% 或 99.4% 读成「上下文整体省了这么多」，是把账记错了地方。以上全部是作者自述的 bench 或社区帖子标题，本文没有独立复现。

再看两个仓库的热度面。claude-mem 113,812 星配 358 个订阅者、127 个未关闭 issue；context-mode 33,587 星配 107 个订阅者、6 个未关闭 issue。README 里还留着 2026-11-01 的自述快照：33K stars、683K npm downloads（stats.json 每天存一份，累计到 2026-10-29）。claude-mem 的 README 挂着 Vercel OSS Program、Greptile、SerpApi 三个徽章，列了三十多个语言版本的入口，版本徽章 15.10.1，要求 Node ≥ 20.0.0；context-mode 要求 Node 24.15.0+，声明支持 10 个 coding agent、9 个 MCP 工具。

04 · 怎么用

按你被撑爆的是哪一段上下文来选

claude-mem 一条命令：npx claude-mem install；Claude Code 内也可以 /plugin marketplace add thedotmack/claude-mem 再 /plugin install claude-mem。README 特别提醒 npm install -g claude-mem 只装 SDK，不注册 hooks、不启 worker。装完重启 Claude Code，旧会话的上下文会自动出现在新会话里。安装器会引导浏览器登录（email magic link）、给 30 天 CMEM Pro 免费试用，memory provider 可选 observer、自己的 OpenRouter / Gemini key 或 Anthropic 套餐；不想登录可以传 --provider，或在 CI 里非交互跑完。

context-mode 按 agent 分安装块，Claude Code 是 claude plugin marketplace add mksglu/context-mode 加 claude plugin install context-mode@context-mode；通用路径是 npm i -g context-mode 再 context-mode setup --agents <agent>，装完在 agent 里跑 /ctx-doctor 逐项 PASS。hooks、sandbox、FTS5 索引都是本地进程，索引落在 ~/.context-mode，README 声明零遥测、装完可离线。它不要账号，也不要常驻的托管内存。

判断表如下，A 是 claude-mem，B 是 context-mode：

  • 每次开新会话都要重新交代项目背景、上周改过什么、当初为什么这么设计——选 A。要的是跨天、跨会话的决策沿革，只有它在会话之间搬运记忆。代价是接受登录、常驻 worker、SQLite 加 Chroma 这一整套。
  • 一次会话里跑几条命令就被日志、测试输出、大 JSON 撑爆，频繁触发 compaction——选 B。痛点是当下这一轮的工具回显，本地 sandbox 加 FTS5 直接截住，零遥测、可离线，还覆盖 10 个 agent。
  • 数据不能出机器，或要给团队统一装同一套——选 B。claude-mem 默认引导到 CMEM Pro 托管内存、安装末尾还会问使用分析；context-mode 把「数据留在本机」写成硬约束，并按 agent 把安装、更新、体检命令列全。
  • 长会话既被工具输出撑爆、又要跨会话记结论——两个都装，不冲突。一个管当下 I/O，一个管历史，安装通道也不同（npx claude-mem install 对 claude plugin install context-mode@context-mode）。反过来，只想要方法论就都别装：读 context-mode 的 bench 表和 claude-mem 的 progressive-disclosure 文档，比养两个常驻服务便宜。

一个务实提醒：两者都不轻。claude-mem 要 Node ≥ 20、Bun worker、Chroma 与 SQLite，context-mode 要 Node 24.15.0+，Windows 上还得装 Git for Windows——README 明说 shell 工具跑在 Git Bash，/ctx-doctor 会检查这一项。为一个「省上下文」的工具引入常驻进程和数据库，本身就把故障面变大了。

05 · 冷思考

113,812 星对 33,587 星，量出来的不是同一个东西

先质疑星标。claude-mem 早建库近半年、多 80,225 星，但 README 里那三个赞助徽章、三十多个语言版本、Star History 徽章、30 天免费试用加浏览器登录，是一整套分发投入；context-mode 的首页也写着 Hacker News 570+ 分、GitHub Trending 14 天。热度里有相当一部分是分发能力，不是机制优劣。更该看的是订阅与星标之比：358 / 113,812 约 0.31%，107 / 33,587 约 0.32%，几乎一样，两边都是「先收藏」的量级。

再质疑那个百分比。98% 来自 HN 帖子标题，99% 是 description 自述，99.4% 是 36 行样本中位数，99.96% 是 README 自己标注的 best case。四个数字分母都是工具输出字节，没有一个是「整个上下文窗口省了多少」。tokens 那两处还标着 estimate at 4 B per token。读者最容易犯的错，就是把「工具输出省了 99%」直接当成「上下文省了 99%」——真正被压掉的只是那部分回显，system prompt、历史对话、模型自己的输出一个字节没动。

第三处质疑是压缩本身的成本没进账。claude-mem 要「用 AI 生成 semantic summaries」，这个动作得调模型：要么 CMEM Pro 托管，要么自己的 OpenRouter / Gemini / Anthropic key。省下的注入 token 有没有被「生成摘要」的调用抵掉，README 没给净账。context-mode 不做 AI 摘要、看着更省，却把成本换到了别处：每项目一个 context.db、9 个 MCP 工具、10 个 agent 的 hook 适配、Node 24.15.0+。两边都在把一种开销换成另一种开销，只是换法不同。

第四处是「免费」和「开源」的边界要按字读。context-mode 的 GitHub API license 字段是 Other / NOASSERTION，README 徽章写 ELv2，是 source-available，不是 OSI 认可的开源；free forever 说的是本地插件，而真正做跨会话记忆的 Gateway Memory 是另一条独立订阅线。claude-mem 是干净的 Apache-2.0，却同样把 hosted memory 放进 30 天试用之后的付费档。两个项目都把「跨会话」放在了要付钱或要账号的那一侧，这不是巧合，是这门生意最自然的收费点。

所以要选的不是哪个星多、哪个百分比大。我的判断是：先确认你的上下文是被「上一次会话」撑爆，还是被「这一条命令的回显」撑爆。是前者，claude-mem 那套 hook 加摘要加注入没有替代品，哪怕要养一个 worker；是后者，context-mode 的本地拦截更直接、也更诚实，它至少把分母写在了 README 里。真正不该做的是拿这两个数字互相比，然后挑一个大的：一个量的是字节，一个量的是记忆，它们根本不在同一把尺子上。
