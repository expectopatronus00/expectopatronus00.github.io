讲透 Loop Engineering，AI 工程的下一层

AI 圈正在集体换口号。Loop Engineering 这个新词被越来越多人挂在嘴边。但它到底是又一次概念炒作，还是 AI 工程真的进入了一个新阶段？

01 · 一个新词的出现

Loop Engineering 是炒作还是进化

最近 AI 圈又在集体换口号了。一个叫 Loop Engineering 的新词，正在被越来越多人挂在嘴边。很多人连它到底指什么都还没弄明白，就已经开始说「我的项目就是 Loop Engineering」。

但问题是：这到底是又一次概念炒作，还是 AI 工程真的进入了一个新阶段？这篇文章尝试给出一个朴素的、可操作的答案。

02 · 从 Prompt 到 Agent 到 Loop

三代工程范式的本质差异

如果把过去三年 AI 工程的演进压缩成一条线，你会看到三个清晰的节点。它们不是替代关系，而是层层叠加的关系。

2023 · Prompt
Prompt Engineering。人写一条指令，模型给一个答案。核心是「把指令写对」。适用场景：单步查询、内容生成。工程复杂度低。
2024 · Agent
Agent Engineering。人给一个目标，模型自己拆步骤、调用工具、做决策。核心是「把流程写对」。适用场景：多步任务、工具调用。工程复杂度中等。
2025+ · Loop
Loop Engineering。人给目标 + 评估标准 + 护栏，模型在循环中自我迭代、自我修正。核心是「把反馈环设计对」。适用场景：需要反复迭代、无人值守的任务。

如果你只把 Loop Engineering 理解成「更高级的 Prompt Engineering」，你会错过它真正的价值。Loop 的核心不是指令优化，而是把改进的主体从人变成系统本身。

03 · 一个 Loop 的解剖

它由哪些部件组成

一个可以被称为 Loop Engineering 的系统，至少需要以下五个部件。缺任何一个，都只是「循环执行」而不是 Loop Engineering。

1. 目标函数：用机器可理解的语言定义成功的样子。如果目标不能被自动化检测，那就不存在 Loop——因为系统无法判断自己做得好不好。

2. 动作空间：定义 Agent 可以做什么（改代码、跑命令、读文件）和不可以做什么（不能删数据库、不能联网部署）。这是 Harness 的核心。

3. 评估器：对每一轮产出打一个客观分。可以是测试通过率，可以是 lint 检查数量，可以是格式校验。关键是：必须自动运行、必须可复现。

4. 反馈回路：把评估器的输出送回给 Agent，让它据此调整下一轮的策略。这是 Loop 与「单次 Agent」最本质的区别。

5. 停止条件：定义何时退出循环——可以是达成目标、可以是连续失败 N 次、可以是 token 预算耗尽。没有停止条件的 Loop 就是烧钱。

一句话判断：如果你去掉人工干预后，系统仍然能自主收敛——那它就是一个 Loop。否则它只是一个被人反复调用的 Agent。

04 · 它解决了什么问题

为什么今天需要它

Loop Engineering 的出现，不是谁发明了一个新名词，而是工程实践中遇到了两个无法用 Prompt 解决的硬问题。

问题一：人的注意力成为瓶颈。当模型的执行速度超过人的阅读和反馈速度时，人就成了最慢的一环。Loop 通过让模型自己判断「做得好不好」，把人从每一轮评审中解放出来。

问题二：一致性难以保证。同一个人在不同时间对同一产出的评价可能不同。不同的人对同一产出的评价差异更大。Loop 通过把评估标准编码进系统，让评价标准稳定下来，进而让改进有可追踪的轨迹。

Loop Engineering 不是让 AI 替代人，而是让人从「反复催 AI」变成「设计 AI 的改进规则」。

05 · 它不是什么

避免被概念炒作裹挟

现在很多东西被贴上 Loop Engineering 的标签，但它们其实不是。为了避免被炒作裹挟，我列三个「它不是什么」作为过滤标准。

它不是把指令写得更长。很多人以为「写一个 3000 字的系统提示词」就是 Loop Engineering。不是。提示词再长也仍然是单步指令——它缺少「评估 — 反馈 — 再执行」的闭环。

它不是写一个定期任务。Cron job 不是 Loop。定期执行是时间的循环，不是改进的循环。Loop 的核心是「根据上一轮的结果决定下一轮做什么」。

它不是一套框架。没有哪个 npm 包叫「loop-engineering」。它是一种方法论——一组关于如何设计系统的原则。套用别人的框架，不等于你在做 Loop Engineering。

06 · 给初学者的三步建议

从哪里开始上手

如果你第一次听到 Loop Engineering，不知道从哪开始，下面是一个按顺序的三步建议。

第一步：写一个可以自动运行的质量检查。不一定要用 AI。可以是项目的测试套件，可以是 `npm run lint`。关键是：它能在没人操作时自己跑，并给出一个可判断的输出（通过 / 失败、错误数量）。

第二步：把你的 Agent 指令从「请实现 X」改成「请让以下检查全部通过」。把目标从描述实现步骤，转为描述验收标准。你会发现模型开始做出你意想不到但又正确的选择。

第三步：让 Agent 在失败后自己重试。不只是让它跑一次、出了错你粘回去——而是让它自己能读到失败信息，自己判断怎么改，自己再跑一次。这一步之后，你的 Agent 就开始具备 Loop 的雏形。

07 · 写在最后

AI 工程的下一层是什么

回到最初的问题：Loop Engineering 是概念炒作吗？我的答案是——它的命名可能会被炒作，但它描述的是一个真实存在的工程趋势。

这个趋势可以用一句话概括：工程师的产出物正在从「代码」变成「让代码被自动改进的系统」。这个转变不是你要不要加入的问题，而是当你的同行开始这样工作后，他们的产出速度和质量会系统性地超过你。

理解 Loop Engineering 的最好方式，不是读更多文章，而是把你手边的一个小任务，完整地走一次「目标设定 → 自动评估 → 自动重试」的流程。一次之后，你就会明白它和 Prompt Engineering 的区别——不是程度上的，而是方向上的。

AI 工程的下一层，不是更聪明的模型，而是更聪明的协作方式。
