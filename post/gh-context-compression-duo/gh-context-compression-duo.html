8,004 星压发送、42,517 星管记忆：基准不能直接相减

billion-context 8,004 星，OpenViking 42,517 星：一个压请求，一个建记忆库。两份 README 都亮出八成以上分数，但一套警告记忆与 RAG 不可混算，另一套自曝逐字检索 69%→27%。

01 这件事

两条同在 11 月 11 日进池的候选，其实不在同一层干活。billion-context 拦在客户端与模型 API 之间，OpenViking 落在 agent 的记忆与知识层。一个改的是发出去的请求，一个改的是留得下来的数据。

billion-context 有 8,004 星、645 fork，2026-08-06 创建，11 月 20 日仍在推送。主语言 TypeScript，最新发布 v0.1.216。OpenViking 有 42,517 星、3,530 fork，1 月 5 日创建，同一天也在推送，主语言 Python。

未结条目的构成也不相同。billion-context 的 1,479 个拆成 880 个 issue 与 599 个 PR；OpenViking 的 1,555 个里，PR 有 1,051 个，超过三分之二。前者更像报告问题，后者更像贡献流程在排队。

完整文件树分别是 2,505 个 blob / 55.57 MB 与 7,965 个 blob / 137.81 MB，两棵树的 truncated 都是 false。体积差主要来自文档和前端：OpenViking 单是 docs/ 就有 919 个文件、约 60 MB。

02 核心机制

一个重写请求，一个重写存储，两条路并不互斥。billion-context 是夹在任意 agent 与模型 API 之间的代理，改写 Anthropic 与 OpenAI 流式响应；压缩由模型自己决定何时触发，不是硬性截断。

代理向对话注入四个上下文工具，压缩动作在服务端执行，折叠过的区间留在历史里直到被恢复。

  • compress：把一段消息折成详细摘要
  • decompress：需要原细节时还原该段
  • search_context：在摘要与可见消息里检索
  • acp_status：查看用量与可压缩区间

README 把健康会话的 prefix-cache 命中率定为 96–99%，压缩本身的额外成本 ≤2%。默认按增长量触发：初始内容之后每多约 50K token nudging 一次，输入越过窗口时另有预检兜底。

OpenViking 的做法是把 agent 知道的一切挂到 viking:// 虚拟文件系统下。文档、记忆、技能各有 URI，代理可以像操作文件一样 ls、tree、read、grep，人也能直接打开目录改内容。

层级内容用途
L0 Abstract一句话摘要快速判断相关性
L1 Overview核心信息与场景规划要不要展开
L2 Details原始全文确定要读时才加载

提交会话会把对话归档，并把抽出的记忆写成可编辑的 Markdown；开启 VikingBot 后，ov compile 还能把素材编成 wiki、知识图谱或报告。

04 怎么用

压缩层可以十分钟接上，数据库层要先备好模型和服务器。billion-context 的通用安装只有一条命令：npm install -g billion-context --prefix=~/.local，之后得到 bili 命令。

它给出三种接法，按侵入程度递减。

  • 原生插件：bili plugin install pi 等，代理住进客户端
  • 启动器：bili codex 之类，一条命令同时起代理和客户端
  • 改写 URL：把 baseURL 前缀改成 http://localhost:8787/bili/

三种模式都可逆。但原生插件与旧版独立扩展互斥，同时启用会双重压缩；Codex 的插件安装只暴露四个工具，不代理自身流量，必须先启动 bili。README 还点名 Claude Desktop 的 Code 页会绕过代理。

OpenViking 的最小自托管条件是 uv、Python 3.10+，以及能提供 embedding 模型与 VLM 的服务。向导会把模型配置写进 ~/.openviking/ov.conf，服务在前台运行。

  • uv tool install openviking --upgrade 安装服务端
  • openviking-server init 选择模型提供方并写配置
  • ov add-resource 导入仓库，ov find 做检索
  • 或用 curl -fsSL https://openviking.ai/install 装记忆插件

不想自建可以用官方托管，README 写明首批 50 个文件免费。安装脚本只支持 macOS 与 Linux，需要 Node.js 18+ 和 curl；Windows 目前给的是桌面应用测试版。

05 冷思考

星标差五倍，不代表成熟度也差五倍。billion-context 有 214 个 tag、187 位贡献者，README 的 Status 一节仍写着 Early：协议与压缩只过了 500 多条 mock 测试，真实模型集成测试是下一阶段。

许可证也不是一眼能看穿的。billion-context 的 LICENSE 主体是 MIT，但末尾追加了署名条款：用户可见的产品要在首页、文档或致谢页说明使用了它并给出链接。GitHub 接口因此把许可证标成 NOASSERTION。

OpenViking 主项目是 AGPLv3，CLI、examples 是 Apache-2.0，Hermes 插件保留 MIT；README 另外禁止整体重写后重新开源，跨语言翻译需书面授权。「开源」在这两个仓库都不是单一答案。

信任边界同样要具体看。billion-context 的启动器可能装证书做 MITM，代理默认只听回环，但 --host 0.0.0.0 之后明确没有认证。OpenViking 要区分 root key 与用户 key，README 说 root key 读写不了记忆；自托管的 ACL 是可选开关，暴露到公网前要先配认证。

两套分数不能直接相减：一边评的是多轮编码代理的证据利用率，一边评的是跨会话用户记忆准确率；底座模型、任务集和判定标准都不同。把它们排进同一张榜单，比星标排序更容易误导。

你的处境选谁理由
单个超长会话被窗口打断billion-context压缩发生在发送前，不动客户端历史
跨会话记忆要能查看和编辑OpenVikingviking:// 可浏览，提交后落 Markdown
要逐字检索固定原文两者都不优先压缩会抹掉原句，RAG 对照分数更高
产品要二次分发先读许可证一个要署名，一个是 AGPL 加翻译限制

判断：先用压缩层救当前的窗口，再按可审计性需求决定是否引入上下文数据库。它们解决的是发送与留存两端的问题，真正的成本不在安装，而在基准口径、凭据范围和许可证条款。
