20,822 星、1,008 个未结 issue：开源只到编排层

20,822 星，1,008 个未结 issue。OpenMausBot 把 Claude、Codex、Grok 的本地命令行收进一个聊天应用，每个 bot 配自己的模型与云电脑。拆开账单看：开源的是编排层，模型和电脑各付各的。

01 · 这件事

20,822 星，把一队 agent 收进联系人列表

OpenMausBot 提供的不是新模型，是把几个本地 agent 命令行编排成一张联系人列表。仓库 2026-08-11 创建，2026-11-11 核对时 20,822 星、2,890 fork，主语言 TypeScript，最近一次推送就在当天。

它的自述定位是「开源 Grok Bot 替代品」：侧边栏里每个 bot 是一个真 agent，有自己的性格、模型、云电脑和已连接的应用。用户像跟联系人聊天一样派活，再逐条审批它要做的动作。

02 · 核心机制

两个进程、一条事件流、一个审批点

整套架构只有一个支点：界面不持有任何传输，所有 agent 进程归一个本地 harness server 管。app 把命令用 HTTP 发过去，服务端把各家 CLI 的原生协议归一成一条 SSE 事件流，前端折叠成状态。

层位置 / 端口职责
界面React + Tailwind，5199聊天、模型选择、电脑面板
Harness127.0.0.1:8799驱动注册表、事件总线、权限代理
驱动server/drivers/Claude、Codex、Grok 走本地 CLI
电脑云端 / 本地 VM / 本机给 bot 一台能操作的桌面
应用Composio SessionGmail、Slack、GitHub 等工具

驱动层是它最省事的地方。claude、codex、grok 都是装在本机并已登录的命令行，bot 复用现有登录与订阅，不需要新账号，中间也没有代理转发。

本地优先落在目录上：transcript、密钥与事件都写在 ~/.openmausbot，harness 只监听回环地址。README 把这一点写进「Why」的第一段，而不是藏在部署文档里。

真正决定体验的是权限代理。shell 命令、文件改动和提问会以卡片形式出现在聊天里，人点 Allow 或 Deny，云端电脑和本地电脑走同一套审批。

  • 云电脑：Boat 提供的隔离 Linux 桌面，带实时预览
  • 本地 VM：隔离的本机虚拟机，不走第三方
  • 本机控制：macOS 与 Ubuntu Xorg 需显式开启
  • Wayland：因 issue #345 的安全边界未解决，保持禁用

随仓库还带一个 stdio MCP server，给 Claude Desktop、Cursor 这类外部客户端用。它开放查 bot、读 transcript、派活、等完成、切模型、中断回合，明确不开放审批授权、删除、凭据与电脑生命周期。把危险动作留在人这一侧，是这份设计里最值得肯定的取舍。

04 · 怎么用

装桌面包最快，但「不用配密钥」只成立于本地聊天

最短路径是下发布包或全局装 CLI，前置条件是本机至少有一个已登录的 agent 命令行。README 给的平台包覆盖三套系统，源码运行另需 Node 24+ 与 pnpm。

渠道方式备注
macOSApple silicon / Intel 两个 dmg已签名公证
Windows x64setup.exe，免管理员安装器未代码签名，SmartScreen 会提示
Ubuntu 24.04.deb 或 AppImagebeta，仅 GNOME 受支持
源码pnpm dev:server + pnpm dev5199 与 8799 两个端口
命令行npm install -g openmausbot也可用 npx，无需全局装

源码启动的三条命令在 README 里是并列的：先起 harness，再起界面，pnpm dev:desktop 另起 Electron 外壳。桌面发布包把 harness 内嵌了，不需要单独配服务端。

  • 端口：界面 5199、harness 8799、webhook 接收器 8800
  • 驱动：claude / codex / grok 任一 CLI 已安装并登录
  • 脚本化：openmausbot team apply 与 openmausbot run 支持 --json
  • 触发：定时例程间隔 5–1,440 分钟，Gmail 每 15 分钟轮询一次

密钥存放有个必须讲清的口径差。命令行模式下，API keys 以明文写进私有 config.json（Unix 权限 0600）；打包的桌面应用改用系统加密，但同一份 config.json 仍会保留部分明文项，如 OpenCode provider keys 与 MCP header 值。

账单也要算在前面。README 明说 Composio 和 Boat 是各有账号与条款的第三方，Boat 试用结束后是付费服务，用云电脑可能产生费用；语音另需 ElevenLabs、Fish Audio 或 xAI 的密钥。

省下的仍要自己付的
编排层与应用代码模型订阅或 API 调用
新账号与中间代理Boat 云电脑（试用后收费）
本地 transcript 存储Composio 应用连接
逐条审批的交互托管语音与 VPS

README 有一句很实在的话：这些凭据都是可选的，本地聊天不配也能跑。把可选层按需打开，是这个项目比较克制的一面；但「开源」并不等于「零账单」，两者别混。

05 · 冷思考

热度和可用之间，隔着 1,008 个未结 issue

真正该问的不是它能不能替代 Grok Bot，而是替代发生在哪一层。README 的五方对照表是作者写的，没有第三方基准；换掉的是「一队 agent 在聊天列表里」这个形态，不是模型能力或托管服务。

发布节奏也说明它仍在快速变形。11-09 与 11-10 连着两天发版，v0.1.152 的说明里还在把 Advanced 模式开关找回来，并放开 Starter 的 bot 数量上限——可以无限创建，但同一时刻 5 个保持唤醒、2 个同时工作。

  • 成熟度：0.1.x 版本号、1,008 个未结 issue、Ubuntu 仍标 beta
  • 套餐边界：Starter 并发 2 个，与「一队 bot」的宣传口径要分开读
  • 终端体验：Windows 安装器未签名、CLI 模式明文存密钥、Wayland 禁用
  • 维护结构：contributors 前 10 里作者 5,673 次提交，第二名 744 次

贡献者分布还带着两个自动化账号：claude 107 次、github-actions[bot] 92 次。个人项目大多如此，不算缺陷；但要嵌进团队流程，就得接受作者一人的节奏决定你的升级节奏。

open-core 那条边界同样不是问题，只是容易被工具误读。合规扫描若只认根目录 LICENSE 的 Apache-2.0，会漏掉 enterprise/ 的另证；商标条款还要求基于它做产品时改名。删掉目录才是纯开源版这件事，得由人确认。

还有口径上的小坑：接口 homepage 与 README 域名不同，tag 数与 release 数差着量级，Starter 的「不限 bot 数」后面跟着并发限制。这类数字单独看都对，连起来读才不会误判。

所以我的判断是：想在一台机器上同时指挥几个已登录的 agent、并且保留逐条审批，它现在就值得试，因为省下的是编排与账号；要把它当团队基础设施或对外服务，先锁版本、确认 enterprise/ 授权、把云电脑与应用连接的账单算清楚。20,822 星是关注度，不是验收报告。
