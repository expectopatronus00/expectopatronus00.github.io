49096 星对 7831 星：控制面管调度，IDE 管落地

49096 星、9697 fork 对 7831 星、477 fork。t3code 是纳管 7 家 agent 的控制面，thinkrail 把 agent 焊进 IDE、用 git worktree 隔离改动。一个管调度，一个管落地。

01 · 这件事

两个今天都还在推的仓库，一个 49096 星，一个 7831 星

pingdotgg/t3code，2026 年 2 月 8 日建库，到 11 月 6 日是 49096 星、9697 个 fork、5398 个未关闭 issue、107 个订阅者，MIT 协议，TypeScript，最后一次 push 停在 11 月 6 日 14:10。仓库的 description 字段是 null——连一句自我介绍都没填，homepage 指向 https://t3.codes。README 第一句管它叫 agent harness control surface，agent 编排控制面。

另一个是 JetBrains/thinkrail，2026 年 7 月 8 日建库，比前者晚整五个月，7831 星、477 个 fork、355 个未关闭 issue、23 个订阅者，Apache-2.0，同样 TypeScript，最后一次 push 在 11 月 6 日 13:57，只比 t3code 早十三分钟。它的 description 写满了：Vibe code with pi in a lightweight, real IDE that customises itself around the way you work — The Vibe You Need，homepage 是 https://thinkrail.ai/，还挂了 13 个 topics，从 vibe-coding、spec-driven 一直到 pi-agent-extension。

GitHub 的 size 字段先给出一个反直觉的数：t3code 记 741154 KB，thinkrail 记 78608 KB，前者约是后者的 9.4 倍。一个自称"控制面"的东西，比一个自称"real IDE"的东西重了将近一个数量级。两个仓库今天都还在推，都在 agent 编辑器这一族里，进了同一条待办队列，所以这篇是横评，一次消耗两条。但真正该分开的不是星标，是它们各自接住 agent 的哪一段。

t3code 不内嵌编辑器，也不自带 agent；thinkrail 把 agent 焊进了 IDE。一个补"人不在机器前"的空，一个补"agent 动了代码之后"的空。下面按这个次序拆。

02 · 核心机制

一个接调度与在场，一个接隔离与落地

t3code 的机制写在 README 那句 T3 Code can control them 里：它不生产 agent，只控制你机器上已经装好的 agent。安装警告列了 7 家 provider——Claude Code、Codex、Cursor、Grok Build、OpenCode、Google Antigravity、fx，前提是至少装好一家并登录：codex login、claude auth login、agent login、opencode auth login、fx login；Antigravity 不用 CLI，在设置里点 Install Antigravity 再 Sign in with Google。控制面铺到四个端：iOS、Android、https://app.t3.codes 网页、Electron 桌面。

所以它接住的是agent 跑起来之后的「调度与在场」：几个 CLI 在几台机器上并行，你要在手机上看见哪个卡住、切一次会话、排一个后续任务，而不必坐回那台机器前。它是横向的——跨 provider、跨设备、跨会话，把散落的 agent 收进一块玻璃后面。README 说灵感来自 Codex desktop app、Conductor、Claude Desktop 和 Cursor Glass，四者都不达标，它要的是远程可用、性能好、真开源，走错方向你能直接 fork。它不定义工作区、不管 diff、不碰你的 checkout。

thinkrail 反过来。它围绕 pi（@earendil-works/pi-coding-agent）这个 coding agent 建了一整个工作台：可拆分的 Monaco 编辑器 tab、带实时 git 变更标记的 Files 树、Changed 视图、终端、文档，全部按当前 workspace 收窄；还能在文件和 diff 上留锚定审查评论，把评论当结构化上下文丢回对话。一个 workspace 里能并发跑几个 pi 会话，各有自己的模型和实时 token / 成本读数，共享一份 agent 会更新、你也能改的 plan，每一步做完单独 commit、单独 review。

真正把它和"控制面"区分开的是两样东西。一是隔离工作区：把任意 git 仓库开成 project，再从中切出 git worktree，每条分支一个工作目录，agent 并行干活不碰你的 checkout；PR 合并或关闭、或者安静一周，workspace 自己 settle 到项目级 shelf，你一回去它又回来。二是SPEC.md 规格图当 ground truth：一堆互连的 SPEC.md 放在代码旁边，agent 通过 spec_* 工具读、搜、维护，意图不随会话结束而丢。再加 ⌘K 命令面板跨项目找会话与工作区、MCP server 接进 pi 的 mcp.json、可移植 Agent Skills 原地读取。它接住的是纵向那一段：改动落在哪、怎么被审、怎么合回分支、意图怎么沉淀。

换句话说，t3code 把 agent 当成需要被看管的外部进程，thinkrail 把 agent 当成 IDE 里的一等公民。前者替你解决"同时看好几个 agent"，后者替你解决"agent 写出来的一坨东西怎么算数"。

03 · 关键细节与数据

轻的不轻，重的不重；还有一处署名得打折

把顶层 contents 拉下来数一遍，那个 9.4 倍就说得通了。t3code 顶层是 apps/、native/、infra/、evals/、assets/、docs/ 这一串目录，加上 AGENTS.md（24670 字节）、knip.jsonc、oxlint-plugin-t3code、.devcontainer——四个端加 Electron 加七家 provider 适配都要自己打包，README.md 反而只有 5256 字节。thinkrail 顶层是 apps/、packages/、pi-extensions/、thinkrail-extensions/、e2e/，几份厚文档：architecture.md 44071 字节、pi-compatibility.md 26221 字节、README.md 19787 字节，还有 bun.lock 336825 字节。「控制面」不轻，「完整 IDE」不重，用仓库体积判断它处在哪一层会翻车。

再看最诚实的两个数。t3code 5398 个未关闭 issue 配 107 个订阅者，订阅率约 0.22%；thinkrail 355 个配 23 个，约 0.29%。fork 比反过来：9697 除以 49096 是 19.8%，477 除以 7831 是 6.1%，前者是后者的三倍多。但 t3code 的 README 同时写着 We are very very early in this project. Expect bugs. 和 We are (mostly) not accepting contributions yet——高 fork、高 issue、不收贡献、自称极早期，这几件事摆在一起，那 9697 个 fork 里有多少是拿去自建控制面、多少只是先收藏，得打个问号。

协议也分道。t3code 是 MIT，README 明说 truly open、让你 fork 去做自己想要的编辑器，配得上；thinkrail 是 Apache-2.0，LICENSE 11346 字节，带专利授权条款，想 fork 做商业发行的人得把这条算进去。还有一处小反差：t3code 的 description 是 null，49096 星没有一句仓库自述；thinkrail 写满 tagline 加 13 个 topics，7831 星。热度显然不来自仓库自己那行简介。

归属要单独说清。API 里 thinkrail 的 owner.login 是 JetBrains、type 是 Organization，organization.login 同样是 JetBrains——能核到的只是仓库署名在这个组织账号下。README 顶部挂的是 JetBrains incubator project 徽章，链接指向 JetBrains on GitHub 的孵化器说明，不是某条正式产品线发布。所以本文按「仓库署名」处理，不把它当成 JetBrains 官方出品的产品认证；同理 t3code 的 owner 是 pingdotgg，也是组织账号，homepage 是 t3.codes，「谁做的」这件事 API 只给到账号这一层。

README 里的细节也能对上各自定位。t3code 给了四套安装：curl -fsSL https://t3.codes/install.sh | sh、Windows 的 irm https://t3.codes/install.ps1 | iex、winget install T3Tools.T3Code、brew install --cask t3-code，不想装直接 npx t3@latest。thinkrail 是桌面安装包加 curl -fsSL https://raw.githubusercontent.com/JetBrains/thinkrail/main/install.sh | bash，装完 thinkrail ~/code/my-repo 直接把一个 git 仓库开成 project；README 还列了内置 5 种界面语言、两个可单独装进原生 pi 的扩展包 @thinkrail/pi-ask-user-question 与 @thinkrail/pi-visualize，以及 ThinkRail has no accounts of its own。一个把入口铺到四种包管理器和四个端，一个把入口收在一个 thinkrail <repo> 上。

04 · 怎么用

按你要接住的那一段选，不按星标选

用 t3code 的前提不是装它，是先把它要控制的 agent 装好。README 的 WARNING 写得很直白：Install and authenticate at least one provider before use。也就是先 codex login 或 claude auth login 之类，再 curl -fsSL https://t3.codes/install.sh | sh，t3 起 server 打开本地 web app，t3 service install 挂后台，t3 update 升级。它不动你的仓库结构，装的是一个服务加四个端的壳。

thinkrail 反过来，前提是一个 git 仓库和一个 model provider：thinkrail 需要 git 在 PATH 上，模型走 JetBrains AI 或自带凭证，第一次启动会带你接 provider。装完 thinkrail ~/code/my-repo，它自己按 git worktree 切隔离工作区、把 SPEC.md 建在代码旁边；桌面版与 CLI 共用同一套引擎，状态在 ~/.thinkrail，pi 的配置读 ~/.pi/agent。你交给它的不是一次会话，是整个项目的变更生命周期。

判断表分三种情况：

  • 手上已经有一批在跑的 agent CLI，痛点是「人不在机器前」——选 t3code。7 家 provider 里只要一家登录过就能纳管，iOS / Android / 网页 / 桌面四端看住、切换、排队，MIT、可 fork 自建控制面；它不替你管 diff，也不要求改工程习惯。
  • 从零起一个项目，要 agent 的改动被当成一次正式变更来管——选 thinkrail。git worktree 隔离、Monaco 里逐条看 diff、锚定评论丢回对话、SPEC.md 跨会话留意图、逐步 commit 逐步 review，这些 t3code 里没有对应物。代价是接受它自带的 pi agent 和 Apache-2.0。
  • 想两个一起用——先别急。t3code 列的 7 家 provider 里没有 pi，也没有 thinkrail；thinkrail 走自己的 ~/.pi/agent 配置。「控制面遥控 IDE」不是开箱即用的组合，得等其中一边先认了对方。

还有一笔不写在安装命令里的账。t3code 要 7 家里至少一家的订阅，thinkrail 要 JetBrains AI 或自带 provider 的 key，两边的 token 账单都落在你自己的账号上，不在「免费开源」四个字里。t3code 那句 Nothing. We built T3 Code because we wanted the best possible development experience with agents 说的是不卖你东西，不等于不花你订阅。

05 · 冷思考

49096 星里有多少是品类红利，7831 星里有多少是署名光环

先质疑那个 6.27 倍。49096 除以 7831 是 6.27 倍；但 t3code 建库早五个月，做的是「跨 7 家 provider 的通用控制面」，受众天然是所有已经装了 CLI agent 的人；thinkrail 绑在一个具体的 pi agent 和一整套 IDE 习惯上，受众窄得多。把这两个数直接当成「谁更好」的排序，等于拿装机量比一个插件和一个工作台。t3code 连 description 都空着还拿到 49096 星，这本身就说明热度来自仓库之外的东西——品类、署名、发布节奏，而不是那份 5256 字节的 README。

第二个质疑必须给到归属。把 owner.login = JetBrains 读成「JetBrains 官方下场做 IDE」，中间跳了一步：API 只证明仓库挂在这个组织账号下，README 顶上挂的是 JetBrains incubator project 孵化器徽章，LICENSE 是 Apache-2.0 而不是商业产品那套，还明说 ThinkRail has no accounts of its own。孵化器项目不等于正式产品线，账号署名不等于产品认证。7831 星、23 个订阅者、355 个 issue，这个量级配「官方下场」的叙事，本身就该让人多问一句。同理，「Theo 团队的编辑器」这句在 API 里也只能落到 pingdotgg 这个组织账号，再往上就不是这次能核到的了。

第三个是 t3code 那 5398 个未关闭 issue 和 9697 个 fork。19.8% 的 fork 比看着像「真有人拿去改」，可 README 同时说 Expect bugs、mostly not accepting contributions yet、Big features will not be——一个不收大功能贡献、自称极早期的仓库攒下五千多个开放 issue，说明它被大量试用，也说明适配债全压在使用者自己身上；四端加 7 家 provider，任何一端掉链子都得等上游。反过来 thinkrail 有 architecture.md、pi-compatibility.md、CODE_OF_CONDUCT.md、CONTRIBUTING.md，文档像正经工程，但 23 个订阅者对 7831 星，日常盯着它的人少得可怜。

最后一个质疑留给「编辑器层 vs IDE 层」这个分法。它好用，但别当成高低：t3code 741154 KB 比 thinkrail 78608 KB 大 9.4 倍，「轻控制面」一点都不轻；thinkrail 把 worktree、spec、diff 全做进 IDE，也没因此变重。真正分层的不是界面厚薄，是它愿不愿意替你承担仓库语义——t3code 明确不碰 checkout，thinkrail 明确要定义工作区、分支和规格图。

所以我的判断落在这一句：先看你手上有没有一批已经在跑的 agent。有，装 t3code，把它们看住，别为一个遥控层去改工程习惯；没有、且你要从零把 agent 写的每一坨 diff 当成一次可审、可合、可追溯的变更，就上 thinkrail 那套 git worktree 加 SPEC.md。再往下一层，决定选型的其实不是「编辑器还是 IDE」，而是你承不承认 agent 的产出需要被当成变更来审——承认，IDE 层那套隔离和规格图就是必付的税；不承认、只要多地看住进程，控制面到头了，多一层都是负担。
