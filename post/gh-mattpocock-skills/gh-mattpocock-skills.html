01 · 这件事

32 万星，README 只认 27 个技能

这个仓库最值得读的不是那 27 个技能，而是它把「哪些技能不发货」写成了一条硬规则。

mattpocock/skills 的作者是 Matt Pocock，plugin.json 的 author.name 写的就是这个名字。仓库描述是「Skills for Real Engineers. Straight from my .agents directory.」。

它是一组给编码 agent 用的 Markdown 技能文件，不是运行时，也不是框架。

2026-11-13 用 api.github.com 核对：323,055 星、27,100 fork、240 个未结条目，MIT，主语言 Shell，建于 2026-02-03，最近推送 2026-11-12。默认分支 main，主页指向 aihero.dev/skills。

240 这个数含 PR。用 search/issues 拆开是 217 个未结 issue、23 个未结 PR，不能当成 240 个 bug 读。

README 的 Reference 只列 27 个技能：Engineering 20 个、Productivity 7 个；按调用方式分是 16 个只能手打、11 个模型可自动触发。插件清单也正好 27 条。

但完整 git tree 里有 39 份 SKILL.md。差的 12 份，仓库自己给了答案。

02 · 核心机制

27 是发货单，39 是库存，规则写在 CLAUDE.md

27 和 39 的差值不是漏数，是 CLAUDE.md 里写死的一条打包规则。

CLAUDE.md 原文规定：engineering/ 与 productivity/ 里的每个技能，都必须同时出现在顶层 README 和 .claude-plugin/plugin.json 的 skills 数组里；括号里补了一句，插件「只发这一组」。

同一段还写明：misc/、in-progress/、deprecated/ 里的技能，两份清单都不许出现。换句话说，README 是发货单，不是库存清单，两个数字本来就不是一个口径。

五个桶按这个口径列成表。20 + 7 + 8 + 4 + 0 得 39，其中被发货的恰好是前两行。

桶目录SKILL.md进 README进插件状态
skills/engineering20是是正式，日常代码工作
skills/productivity7是是正式，通用工作流
skills/in-progress8否否Beta，刻意公开求反馈
skills/misc4否否冻结且不再维护
skills/deprecated0否否空桶，退役即删除

plugin.json 的 version 是 1.3.2，skills 数组 20 条 engineering 加 7 条 productivity，与 README 逐项对应。marketplace.json 只挂了 1 个插件，source 写的是 ./。

plugin.json 的 author.name 写的是 Matt Pocock，license 为 MIT，和仓库接口的许可字段一致。两份清单里都找不到 in-progress 的路径，规则确实落在文件上，而不只是写在文档里。

tag 共 10 个，最新 v1.3.2；CHANGELOG 从 1.0.0 到 1.3.2 列了 9 个版本段。规则、清单、版本号三处对得上，没有一处需要靠猜。

所以 把 39 写成「README 虚报」是误读：这里真正在维护的是一套筛选规则，技能只是它的产物。

03 · 关键细节与数据

规则写得越细，越容易露出两处没同步

桶清单本身有两处没跟上 CLAUDE.md，第三处看着像漏删，其实是规则允许。

第一处在 in-progress/。桶 README 说这些是 Beta、刻意公开求反馈、不进插件也不进顶层 README，正文列了 7 个技能。目录里却有 8 份 SKILL.md。

多出来的是 chief-of-staff。.changeset/ 里还有一份 chief-of-staff-shared-wiki-procedures.md，说明它正在改动中，只是桶 README 没跟上。CLAUDE.md 明确要求每个桶 README 列出桶内每一个技能。

第二处在 .out-of-scope/。SCOPE.md 的「Already decided」列了 8 份否决记录，目录里实际有 9 份，多的是 lazy-load-writing-for-agents.md。该文件开头要求提 issue 前把这些全部读完。

第三处看着像漏删，其实合规。docs/engineering 有 21 个页面，对应 20 个技能；多出的 resolving-merge-conflicts 首行标着 Archived，写明 v1.3.0 从插件移除、页面保留备查。

CLAUDE.md 对此写了例外：被整体移除的正式技能，文档页留下并标 archived。所以 21 不是错，是留档。把三处并列看，才分得清哪些是漂移、哪些是设计。

位置应然实然判断
in-progress/README.md列全桶内技能列 7，目录 8少 chief-of-staff
SCOPE.md 已决清单列全 .out-of-scope列 8，目录 9少 lazy-load 那份

04 · 怎么用

先选插件还是可编辑文件，两条路不能同时走

装它之前要先决定走哪条分发路径，双装会让每个技能出现两次。

README 安装段第一句就是提醒：插件会自更新，skills.sh 拷的是可编辑副本、要手动更新；每个 agent 只挑一种。五条路径按原文列成表，命令不合并、不改写。

目标安装命令更新方式
Claude Codeclaude plugin install mattpocock-skills@claude-plugins-official默认自更新
Codexcodex plugin marketplace add mattpocock/skills启动时自更新
GitHub Copilotcopilot plugin marketplace add mattpocock/skills配置后每日更新
Gemini CLIgemini skills install ... --path skills/engineering手动重跑两条
其他 / 可编辑npx skills@latest add mattpocock/skills -a <agent>手动 update 与 add

装完还要在每个仓库跑一次 /setup-matt-pocock-skills。这一步不是可选项，README 说它会问三件事。

  • 用哪个 issue tracker：GitHub、GitLab、本地文件，或自己描述的其他系统
  • triage 时给票据贴什么标签：/triage 依赖这些标签
  • 过程中产生的文档存到哪里

CLAUDE.md 补了一条口径：Claude Code 走官方市场 claude-plugins-official，其余 agent 走仓库自带的 marketplace.json 拿自动更新；改过任一清单后要跑 claude plugin validate . --strict。

要 Beta 技能得单独装，插件不给：命令是 npx skills@latest add mattpocock/skills --skill=<name>。in-progress/README.md 明说这些技能可能随时改动或消失。

30 秒装完，不等于 30 秒能用：选哪条路径、要不要 Beta、每个仓库的配置问答，都排在安装之后。

05 · 冷思考

让你随意改，却基本关上了改完往回交的门

README 鼓励你自己魔改，治理文件却把贡献通道收得很窄，这两句话得一起读。

README 写着「Hack around with them. Make them your own.」。SCOPE.md 却写明新技能提案与贡献一律关闭，misc/ 冻结且每个 issue 都关；配置选项、适配某个 harness、迁就个人流程，都该放进自己的 CLAUDE.md 或 fork。

CONTRIBUTING.md 说 PR 只对 collaborators 开放，仓库接口的 pull_request_creation_policy 也正是 collaborators_only。

issue 要同时过两道闸：有真实会话里的失败复现，且不撞 .out-of-scope/ 里已拒的概念。

门槛还带时限：14 天没回复就关，拒绝按 not planned 结案。AI 代写的 issue 另有一套要求，一个问题一条、复现写在分析之前、不许贴完整规格或重写后的 SKILL.md。

贡献者接口只有 4 个账号、合计 539 次提交，其中 mattpocock 本人 507 次，占 94.1%。其余三个账号的提交数列成表。

贡献者提交占 539 次

这更像一份个人工作台的公开发布，而不是社区共建的技能库。32 万星里有作者名气的分量，也有「不 vibe coding」这句口号的传播力，两者很难从星标里拆开。

对普通团队更实际的质疑是：某个技能不合你的项目时，规则明确指向 fork 或自己的 CLAUDE.md，而不是提 PR。那你接手的是一份要自己维护的分支，版本号、桶规则、文档页同步都得跟着走。

把它当一份带版本号的产品说明读，比当插件装进项目更省事。
