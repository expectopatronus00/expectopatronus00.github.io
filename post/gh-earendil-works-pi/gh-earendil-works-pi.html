01 这件事

12.3 万星的 pi，先把「谁能提问题」写成门禁，再把功能留在核心之外。它不靠堆特性证明自己，靠的是一套能被 workflow 执行的边界。

earendil-works/pi 创建于 2025-08-09，截至 2026-11-22 有 123,267 星、15,902 fork、282 个未结条目，MIT 许可，主语言 TypeScript，最近推送 11-22。11-13 入池时是 86 分候选，第 9 天复核热度未衰减。

README 把定位压缩成三句，句句都在做减法：

  • 极简、可扩展，让你按自己的工作流改它
  • 默认不做 sub-agents，也不做 plan mode
  • 没有内建权限系统，默认继承启动用户的权限

这三句决定了后面所有取舍：核心只留 agent loop 与工具调用，扩展、技能、主题和提示词模板都做成可打包分发的 Pi package。

仓库底部还有一行致谢：pi.dev 域名由 exe.dev 捐助。项目把品牌、安装入口和代码分发放在三个地方，这也是后面读数字时要分开的口径。

02 核心机制

「极简」说的是运行时默认行为，不是仓库体积：12 份 package.json 里，README 表格只列了 7 份。没列出来的多在内层链路上。

12 份清单里 11 份公开、1 份标了私有。这不是 README 漏写版本：所有包的版本号都是 1.6.0，与 11-20 发布的 release tag 对齐。

版本口径还分两层：根仓库叫 pi-monorepo 0.0.3，对外发布的是 CLI 1.6.0。模型目录由 catalog 生成，AGENTS.md 明令不许直接改生成物。

扩展点写在 README 第一段：扩展、技能、提示词模板、主题。它们可以打成 Pi package，用 npm 或 git 分发给别人。

接入方式也被拆成四条，而不只有一个聊天框：

核心不做 sub-agents 与 plan mode，想要就自己装包或让 Pi 写。这不是功能缺失的托词，而是 CONTRIBUTING.md 的硬约束：让核心变胖的 PR 很可能被拒。

03 关键细节与数据

贡献门禁不是文档口号：三条 workflow 会自动关掉新人的 issue 和 PR，白名单里只有 278 个账号。这是全仓最硬的数字。

workflow触发与判定结果
issue-gate无写权限且不在名单打 untriaged 标签后关闭
pr-gate未获 lgtm 批准评论说明后关闭 PR
approve-contributor解析维护者评论开头或结尾的 lgtm / lgtmi写入 .github/APPROVED_CONTRIBUTORS
issue-analysis打 pi-analyze 标签或 @issuron analyze用仓库 /is 提示词分析，读 PI_AUTH_JSON

命令位置也有讲究：lgtmi 只豁免 issue，lgtm 才同时豁免 PR；必须放在评论开头（可先 @ 人）或结尾。CONTRIBUTING.md 还写明周五到周日的 issue 不保证被查看。

名单文件 419 行，去掉注释后 278 条：275 个账号有 pr 权限，3 个只有 issue 权限。AI 可以帮忙分组、摘要和找缺失信息，但最后的开关仍由人按下。

模板口径也对不上：CONTRIBUTING.md 说「两个 issue 模板」，目录里实有三个表单——Bug Report、Contribution Proposal、Package Report，且关闭了空白 issue。

规则写明两次无视文档、或用 agent 批量提 issue 会永久封号。周末提交不保证回复，急事被引导去 Discord；维护者每天回看自动关闭的条目。

README 顶部把规则放在徽章下方，等于提醒：看到自动关闭，先别急着判定项目没人维护。

04 怎么用

上手最容易被忽略的不是命令，而是安装路径的锁依赖差异和默认放行的执行权限。先决定隔离，再决定怎么装。

安装路径入口依赖口径
官方安装脚本curl -fsSL https://pi.dev/install.sh | sh固定全部依赖，pi update 更新
npm 全局npm install -g --ignore-scripts @earendil-works/pi-coding-agent不锁传递依赖
Nixnix run github:earendil-works/pi/stable从源码构建，模型目录用 pin 固定

Node.js 要求 22.19 或更新。进目录运行 pi，用 /login 接订阅或 API key；无人值守用 --print、--mode json 或 --mode rpc。

  • .npmrc 设 save-exact=true 与 min-release-age=2，避开当天发布的依赖
  • package-lock.json 是依赖事实源，提交改动要带 PI_ALLOW_LOCKFILE_CHANGE=1
  • 安装脚本从 install-lock/ 目录取包，npm 全局安装不锁传递依赖
  • CI 用 npm ci --ignore-scripts，另有定时任务跑 npm audit --omit=dev
  • npm 发布的是本地验证过的 tarball，不在发布时重新打包工作区

可选能力默认也关着：tool_search 要显式写进 defaultTools，codemode 则在 QuickJS 沙箱里调其他工具，两者都要在配置里打开。

从源码跑也不难：npm install --ignore-scripts 后执行 npm run build，pi-test.sh 可从任意目录启动；test.sh 在没有 API key 时跳过依赖 LLM 的用例。

安全边界要自己搭。README 说没有内建权限系统，默认继承启动用户权限；usage 文档补了一句：它不会在每次工具调用前问你。

隔离方式Pi 运行位置凭据处理
Plain Docker容器内凭据传进容器
Docker Sandboxes托管沙箱真 key 留宿主机，代理替换
OpenShell本地或远端沙箱策略控制凭据与推理路由
Gondolin extension宿主机只把内置工具送进微 VM

README 只列三种隔离方式，文档表格是四种，多出来的正是 Docker Sandboxes：真 key 不进沙箱，由代理在出站时替换。

还有一处容易漏：/share 会上传会话换取查看链接，默认走 Radius 组织可见或私有 GitHub gist；文档要求上传前先检查提示词、工具输出和凭据。

05 冷思考

极简的代价是边界外移：SECURITY.md 直接把提示词注入和沙箱写成「不在范围内」。能不能用好，取决于你愿不愿意自己补这一层。

原文说本地账户及可写文件都在同一信任边界内；本地已有写权限的攻击不算漏洞，除非能跨操作系统权限边界。它不承诺替你挡住本机恶意代码。

  • 提示词注入：AGENTS.md 与代码注释就能注入，文档写「无法防护」，工作流却鼓励 agent 读仓库指令
  • 不可信仓库、扩展、技能、沙箱行为、公开暴露实例，全部列在 out of scope
  • 供应链管得很细：精确版本、min-release-age=2、--ignore-scripts、CI 定时 npm audit，但只管安装不管运行

有个微妙对照：产品默认没有 sub-agents，仓库自己的 AGENTS.md 却要求评审者用 subagent 或其他 session 并行看改动。它不反对多 agent，只是不替你预设一种编排。

贡献门槛也能反过来看。12.3 万星的项目，只有 278 个账号免于自动关闭；质量筛选换来维护可持续，也可能把新用户的问题挡在讨论之外。

仓库自己给了答案的一半：AI 能分重复、做摘要、找缺失信息，但不做最终判断；提交 issue 也不许用 LLM 代笔。它把人的责任留在入口和出口，中间才让机器帮忙。

如果只想找个开箱即用、每次改动都先确认的编码 agent，pi 不是那个产品。愿意把隔离、扩展与审核规则自己拼起来，这 12.3 万星的大部分价值才真正可用。
