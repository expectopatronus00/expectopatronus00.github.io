3.4 万星插件仓：README 说 11 个，机器管 22 份

34,497 星、3,815 个 fork、Apache-2.0，Anthropic 把给知识工作者用的岗位插件整包开源了。但 README 说 11 个插件，仓库里躺着 22 份清单；说没有代码，里面有 26 个 Python 文件。真正值钱的不是插件本身，是那条每晚自动跑的去更新流水线。

01 · 这件事

Anthropic 把岗位插件整包开源，34,497 星

anthropics/knowledge-work-plugins，2026 年 1 月 23 日建库，到今天 34,497 星、3,815 个 fork、213 个订阅者、161 个未关闭 issue（其中 93 个 issue、68 个 PR），Apache-2.0 协议，最后一次 push 停在昨天（11 月 2 日）。仓库自己的描述很直白：Open source repository of plugins primarily intended for knowledge workers to use in Claude Cowork——给知识工作者用的插件仓库。

它做的事不复杂：把销售、法务、财务、数据、产品这些岗位的工作方式拆成 Claude 能读的 Markdown 和 JSON，装进插件里，让 Claude 在 Cowork 或 Claude Code 里变成这个岗位的助手。每个插件一个目录，四件套：.claude-plugin/plugin.json 是清单，.mcp.json 是连接器，commands/ 是你手动敲的斜杠命令，skills/ 是它自己判断要不要读的知识。

它在待办队列里躺了五天，10 月 29 日入池、评分 91，是积压最久的一条。但把整个仓库数完之后，真正值得写的不是 3.4 万星，而是「官方开源的插件生态」这句话和仓库实际形状之间的落差：README 说 11 个插件，仓库里躺着 22 份清单；README 说「没有代码」，里面有 26 个 Python 文件和 6 条 GitHub Actions。

02 · 核心机制

四个文件件，和一条每晚自动跑的流水线

插件机制本身很薄。README 把结构写成四行，然后说 no code, no infrastructure, no build steps。技能是自动触发的领域知识：销售插件教你怎么准备一场客户会议，财务插件教你怎么对账。装法两条命令——claude plugin marketplace add anthropics/knowledge-work-plugins 把市场加进来，claude plugin install sales@knowledge-work-plugins 装具体那个。

真正厚的是市场文件。.claude-plugin/marketplace.json 有 68,192 字节、123 个条目，名字互不重复。拆开：22 条指向本地路径（./sales 这种），101 条指向外部——59 条用 url，42 条用 git-subdir。101 条远程条目每一条都钉着一个 sha，42 条还额外钉了 ref 和子目录 path。这不是一张目录，是一份带版本锁的外部依赖清单。

而这份清单怎么不腐烂，靠的是一条夜间流水线。bump-plugin-shas.yml 每天 UTC 07:23 跑：哪个外部条目的上游 HEAD 动过了，就在新 sha 上先跑 claude plugin validate，通过就开一个 bump/<slug> 分支的 PR，一个插件一个 PR，失败的那条隔离在自己分支上不拖累别人。单条 bump 成本约 2 秒，一晚上默认封顶 30 条。

但 bump 只是搬砖，真正把关的是另一条。scan-plugins.yml 的 scan 是 main 分支的 required status check——它克隆外部仓库，用 .github/policy/prompt.md 那份 7,977 字节的审查提示词跑一遍 Claude，按 Anthropic 的目录政策和 AUP 判断这插件「是否负责任地处理用户数据」，通过才放行。

也就是说，一个 Claude 写的插件，要先过另一个 Claude 的策略审查，才能进官方市场。而这条审查的省法是缓存：判定按 <plugin>@<sha> 存，sha 不可变所以同一组合只烧一次约 90 秒的 Claude 时间，30 天后过期，策略提示词一改全部失效重扫。文件里写得很直白——without a cache, the scan would re-burn ~90s of Claude time per entry per night，有了缓存稳态每晚约 10 条。

还有一条流水线是关门的。close-external-prs.yml 用 pull_request_target 监听所有 PR：作者不是 Anthropic 成员，且改动不属于「只新增市场条目、别的什么都不碰」这类范围，就留评论然后关掉。评论里给的通道是 https://clau.de/plugin-directory-submission。仓库 README 写的却是 Fork the repo, make your changes, and submit a PR——README 说的和 workflow 做的是两件事。

03 · 关键细节与数据

三处对不上

第一处是插件数。README 原话 open-sourcing 11 plugins，下面的表格也正好 11 行。但仓库里 .claude-plugin/plugin.json 实际有 22 份。多出来的 11 份是 engineering、design、human-resources、operations、small-business、pdf-viewer，加上 partner-built/ 下的 5 个合作方插件（Salesforce 的 Slack、Apollo.io、Common Room、Tribe AI 的 brand-voice、Zoom）。这 11 份一个都没进 README 表格，但每一个都进了市场文件的本地 22 条。

第二处是「没有代码」。仓库里确实有 26 个 Python 文件（310,650 字节，其中 25 个在 bio-research 下）、1 个 Node 脚本（7,281 字节）、2 个 HTML（合计 108,341 字节，最大的一个 productivity/skills/dashboard.html 98,403 字节）。「无构建步骤」是真的，「无代码」是假的——README 描述的是一种可以照抄的最小结构，不是这个仓库现在的样子。

第三处是连接器。README 表格给每个插件列了一栏 Connectors，11 个插件加起来 77 个名字；而对应的 11 份 .mcp.json 实际登记了 108 个 server 条目。11 个插件里除 cowork-plugin-management（本来就没有连接器）外，每一个的 README 都比实际少——sales 差得最多，表格写 9 个（Slack、HubSpot、Close、Clay、ZoomInfo、Notion、Jira、Fireflies、Microsoft 365），实际 23 个 server，多出 Gong、Otter、Calendly、Lusha、Crunchbase、Apollo、Outreach 一串；product-management 表格 11 个、实际 16；marketing 表格 9 个、实际 13。

差距的来源之一是命名粒度：README 把 Jira 归成「Jira」一个名字，实际登记成 atlassian 一条；Microsoft 365 表格算一个，实际还分列 microsoft-365、google calendar、gmail。另一个来源是表格只写「常用几个」。

再看数字分布。全仓库 1,285 个文件、8,116,474 字节，Markdown 占 7,292,925 字节（89.9%），加上 JSON 共 91.1%。SKILL.md 共 252 个（第一方 181、合作方 71），而 commands/ 下的斜杠命令只有 15 个，且只有 3 个目录有：pdf-viewer 4 个、product-management 1 个、partner-built 10 个。17 个第一方插件里只有 2 个带显式命令。官方给的默认入口是「让 Claude 自己判断」，不是「让你敲命令」。

技能最多的两个也最重：small-business 44 个技能、35 个 MCP server、版本 1.35.1；sales 36 个技能、23 个 server、版本 2.1.0。版本号还暴露了成熟度差：productivity 1.3.1、finance 1.3.0、legal 1.3.0，而 cowork-plugin-management 停在 0.2.2、pdf-viewer 0.2.0，合作方那边 apollo 是 0.1.0。合作方那一坨 765 个文件、4.4 MB，其中 Zoom 一家占掉 71 个合作方技能里的 57 个，还带两份 OAuth 权限参考文档，377,288 和 371,007 字节——全仓库最大的两个文件。

数据核对：2026-11-03 经 api.github.com 与 raw.githubusercontent.com 读取 anthropics/knowledge-work-plugins。仓库元数据：stargazers_count 34497，forks_count 3815，subscribers_count 213，open_issues_count 161（search 接口拆分：issue 93、PR 68），created_at 2026-01-23T20:11:54Z，pushed_at 2026-11-02T07:26:44Z，language Python，size 6711KB，license Apache-2.0，default_branch main。文件与字节数取自 git/trees?recursive=1（truncated 为 false，1864 项：1285 blob / 579 tree）。marketplace.json 为 68192 字节、123 条、123 个不重复名称，其中 22 条本地路径、101 条远程（59 url / 42 git-subdir），101 条远程全部带 sha、42 条另带 ref 与 path。SKILL.md 252 个（第一方 181、合作方 71），plugin.json 22 个（第一方 17、合作方 5），.mcp.json 21 个，commands/*.md 15 个，CONNECTORS.md 17 个。21 份 .mcp.json 合计 186 条 server、91 个不重复名字、30 条 url 为空字符串、14 条 oauth（全部 slack，clientId 与 callbackPort 均唯一）。贡献者 32 个、提交 1128 次（contributors 接口累计 1127 次），其中 github-actions[bot] 807 次。易误解点三处：一是 README 自述 11 个插件，仓库实际 22 份 plugin.json，多的 11 份未出现在 README 表格中；二是 README 说 no code，实际有 26 个 .py、1 个 .js、2 个 .html 与 6 条 workflow，「无构建步骤」成立，「无代码」不成立；三是 README 表格的 Connectors 一栏 11 个插件合计 77 个名字，对应 .mcp.json 实际 108 条 server，每个插件的表格都少于实际。
04 · 怎么用

装一个、改一个、或者只读它

装法就两条命令，加市场再装插件。装完自动生效：技能在相关时自己触发，斜杠命令出现在会话里（README 举例 /sales:call-prep、/data:write-query、/finance:reconciliation、/product-management:write-spec）。想换成自己的工具栈，就改 .mcp.json 的 url；想加公司术语和流程，就写进 skills 文件；想新建插件，仓库自带 cowork-plugin-management 专门干这个。

怎么选，三条：

  • 只想用一份现成岗位能力：装 sales 或 finance。skill 数最多、版本最高（sales 2.1.0），是官方维护最久的部分。
  • 想看这套东西到底怎么写的：先读 sales/skills/（36 个 SKILL.md）和 product-management/commands/（唯一带命令的第一方插件）。这是全仓库唯一能看清「显式命令怎么设计」的样本。
  • 想做自己的插件并上架：看市场文件里远程条目怎么写——带 sha、带 ref、带 path。但别指望走 PR 进官方市场，close-external-prs.yml 会关掉它，官方通道是 clau.de/plugin-directory-submission。

一个务实的提醒：186 条 server 里 30 条 url 是空字符串，集中在 google calendar（12）、gmail（12）、snowflake（2）、databricks（2）、benchling（1）、google drive（1）；pdf-viewer 那条走的是 stdio 命令而不是 http 地址。装完先确认连接器状态，别把「技能已经就绪」当成「工具已经连上」。

05 · 冷思考

3.4 万星里，最有价值的部分不是给人用的

先看两个比例。星标对订阅：34,497 星配 213 个订阅者，0.62%。fork 对星标：3,815 除以 34,497，11.1%。fork 比例不低，说明确实有人拿去改。但订阅率很低，因为插件和库不一样：装插件的人不需要 watch，只有等着它更新的人才会 watch。这更像一个「安装即消费」的市场，不是开发者社区。

更该看的是那 71.6%。按 contributors 接口累计的 1,127 次提交算，github-actions[bot] 占 807 次，31 个人类合计 320 次，头部 jordanecker-ant 一个人 155 次，接近人类提交的一半，还有 14 个人只提交过 1 次。这个仓库的「作者」其实是一套自动化加两个中心化的人。这不一定是坏事——夜间扫 sha、逐条 validate、逐条开 PR、策略扫描缓存、失败自动回退，这套东西一个人手写不出来，bot 占比高恰恰说明它跑的是自动化而不是靠热情。但代价是：仓库的形状是「Anthropic 想要的市场」，不是「社区自然长出来的市场」。123 条里 22 条本地、101 条外部，外部全是 sha 锁定的别人仓库——市场的大小不反映生态健康度，只反映有多少上游动过。

第二个质疑在审查本身。让 Claude 审 Claude 写的插件，判据是那份 7,977 字节的提示词加两份政策文档。提示词本身写得很细——要求读完整负载而不只是加载面，专门点名要翻 .claude/、scripts/、tests/ 这些不加载、但会随插件克隆到用户磁盘的目录，还要求检查有没有跨服务外泄凭据的代码。这套防线是认真写的，但它的上限就是提示词的上限：一个会读文件、会调工具的审稿模型，判断力和它的上下文窗口绑在一起。而且它审的是已发布的快照，不是持续运行的行为。

第三个质疑在凭据。14 个插件共用同一个 slack clientId（1601185624273.8899143856786）和同一个回调端口 3118。这在官方自用场景里合理，一个应用一套 OAuth。但如果这些插件被复制进你的团队、复制进别人的公司，拿到的是同一把钥匙。再叠加 30 条空地址——google calendar 和 gmail 这两个服务在十几个插件里重复出现空 url，看起来是「占位，等填」而不是「配好了」。一个 186 条连接器的官方插件市场，凭据和地址这两件事都还没落到每个用户身上。README 说的「swap connectors，指向你自己的工具栈」，本质上就是把官方替你填的地址换成你自己填的——市场给了骨架，地址和钥匙都得你来补。

第四个是入口的收缩。README 教 Fork the repo, make your changes, and submit a PR，但 workflow 会把非成员的 PR 关掉，只放行「只加市场条目、什么都不改」的那一类，其余走另一个表单。「开源」在这套设计里指的是代码可见、目录可读、fork 可用，而不是准入通道敞开。这不违背 Apache-2.0——协议本来就不承诺合并——但对读者的预期是一次校准。

我的判断是：这个仓库最值得抄的不是那 181 个第一方技能，也不是那 123 条市场条目，是那条夜间自动 bump + 逐条 validate + Claude 策略扫描 + 缓存判定 + 失败自动回退的流水线。它把「维护一份会腐烂的外部依赖清单」这件苦差做成了一个每晚跑一次的 cron。Skills 是产物，那条流水线才是方法。而对想用的人，现实的判断是：现在就能装、官方维护最久的那几个（sales 2.1.0、small-business 1.35.1、productivity 1.3.1）值得装；合作方插件和那 30 条空地址的连接器，装之前先自己确认一遍地址。
