7.4 万星的 OpenMontage：视频不靠生成，靠管线

74,007 星、9,702 个 fork、421 个未关 issue——OpenMontage 是 GitHub 上星标最高的视频制作项目之一。它自己不生成一帧画面，而是把 100 多个工具和 11 条 YAML 管线交给编程助手调度。代价写在许可证里：AGPL-3.0。

01 · 这件事

74,007 星的视频项目，自己不生成一帧画面

2026 年 3 月 29 日建库，到 11 月 1 日，calesthio/OpenMontage 的数据是 74,007 星、9,702 个 fork、421 个未关闭 issue，Python 写的，AGPL-3.0，仓库体积 77,481 KB。最后一次 push 停在 10 月 28 日，之后四天只有星标在涨。官网是 openmontage.video。

它的 description 写得很满：「World's first open-source, agentic video production system. 12 production pipelines, 100+ tools, 700+ agent skill and production-knowledge files.」——首个开源的、agent 驱动的视频制作系统，12 条制作管线、100 多个工具、700 多份 agent 技能与制作知识文件。

但真正定义这个项目的，是 README 里另一句更短的话：「There is no code orchestrator. Your AI coding assistant IS the orchestrator.」没有代码编排器，你的 AI 编程助手本身就是编排器。Python 在这里只负责提供工具和落盘，所有创作决策、编排顺序、验收标准，全部写在可读的 YAML 清单和 Markdown 技能文件里。

这句话把它和市面上的 AI 视频工具彻底分开了。Veo、Kling、可灵那类东西是「输入提示词、输出一段素材」；OpenMontage 不碰模型，它假设你已经有 Claude Code、Cursor、Copilot、Codex 或者 Windsurf，然后把「做一条完整片子」拆成一串 agent 能读懂、能验收、能被打回的工序。它卖的不是生成能力，是流程。

02 · 核心机制

三层结构：能力、用法、知识，分开存放

仓库的目录划分就是这个项目的世界观。tools/ 和 pipeline_defs/ 回答「有什么能力」——前者是 100 多个注册过的生产工具，按 video / audio / graphics / enhancement / analysis / avatar / subtitle 分目录；后者是一份份 YAML，定义每条管线要经过哪些阶段。skills/ 回答「怎么用」——分 pipelines、creative、core、meta 四类 Markdown，教 agent 在每个阶段该干什么、什么算合格。第三层 .agents/skills/ 放外部技术知识包，回答「原理是什么」。

拿其中一条管线拆开看更清楚。以 documentary-montage 为例，它的 YAML 里只有五个阶段：idea（立意）、scene_plan（分镜）、assets（找素材）、edit（剪辑决策）、compose（合成）。每个阶段挂一个 director 技能文件，比如 pipelines/documentary-montage/idea-director，规定这一阶段必须产出什么、审什么。注意 README 里写的是七段式 research → proposal → script → scene_plan → assets → edit → compose，那是通用描述；具体到某条管线，阶段名和数量由它自己的 YAML 决定，两者并不总是一一对应。

真正有意思的是每个阶段后面的两个字段：checkpoint_required: true 和 human_approval_default: true。前四个阶段全部要求人工签字，只有最后的 compose 默认放行。换句话说，立意、分镜、素材、剪辑这四道关，agent 不能自己说了算，它必须停下来等人点头才能往下走。checkpoint 协议还配了一条硬规矩：没记录审批的「已完成」阶段，会被 checkpoint writer 直接拒绝。

编排层也不让 agent 即兴发挥。YAML 的 orchestration 段写着 mode: executive-producer（执行制片人模式）、max_revisions_per_stage: 3（每阶段最多返工 3 次）、max_send_backs: 2（最多打回 2 次）、max_wall_time_minutes: 60（单条片子上限 60 分钟）。这些数字不是建议，是天花板——超了就得停下来。

03 · 关键细节与数据

「12 条管线」这句话，得往下翻一层

先把 description 里那个 12 对上。pipeline_defs/ 目录下确实有 12 个 YAML 文件，但其中一个是 framework-smoke.yaml，只有 675 字节，看名字和体量就知道是框架自检用的样例，不是给用户做片子的。剩下 11 个才是真管线：animated-explainer、animation、avatar-spokesperson、character-animation、cinematic、clip-factory、documentary-montage、hybrid、localization-dub、podcast-repurpose、screen-demo、talking-head——数出来是 12 个名字，但 README 的表格里只列了 11 行，character animation 是正文里单独提的。

这个差异不大，但它说明一件事：这个项目的宣传口径比实现略快半步。星标数、fork 数这些是硬数据，管线数量这种自述值，最好自己数一遍。

技能文件的体量倒是实打实的。skills/meta/ 下 10 个 Markdown，最厚的 reviewer.md 有 25,407 字节，video-reference-analyst.md 21,189 字节，checkpoint-protocol.md 11,379 字节。reviewer 是那个负责打回的角色，checkpoint-protocol 是审批流程，taste-direction 管审美方向——这套东西不是「让 AI 随便剪」，是把人的判断标准写成文件，让 agent 照着执行。

质量闸门是具体的。assets 阶段的验收要求写死了两条：corpus size >= 8x slot count（素材库规模至少是镜头槽位的 8 倍）、scores >= 0.22（CLIP 检索相似度门槛 0.22）。edit 阶段要求成片时长与立意里的 duration_seconds 误差在 10% 以内，compose 阶段收紧到 1 秒。另外 render_runtime 在立意阶段选定后就被锁死，YAML 原文把「静默切换到 hyperframes 或 ffmpeg」写成 CRITICAL governance violation——静默换渲染器算严重违规。

钱的部分最实用。README 的 Budget Controls 一节写着：执行前先估算成本，调用前先预留预算，执行后对账；三种模式 observe（只记录）、warn（超额告警）、cap（硬上限）；单次动作超过阈值要停下来确认，默认阈值 $0.50；单个项目总预算上限默认 $10，可改。具体到管线，documentary-montage.yaml 里 budget_default_usd 是 1.00。README 还给了一条真实成本：60 秒皮克斯风短片《THE LAST BANANA》，用了 6 个 Kling v3 生成片段加 Google Chirp3-HD 旁白，总成本 $1.33。

04 · 怎么用

先装依赖，再把它当「会剪片的同事」用

门槛不高，但也不是双击即用。前置要求：Python 3.10 以上、FFmpeg、Node.js 18 以上（如果要用 HyperFrames 合成，需要 22 以上），以及一个能读文件、能执行 Python 的 AI 编程助手。仓库为各家助手分别放了配置文件——Claude Code 读 CLAUDE.md，Cursor 读 CURSOR.md 加 .cursor/rules/，Copilot 读 COPILOT.md，Codex 读 CODEX.md，Windsurf 读 .windsurfrules，最终都指向同一份 AGENT_GUIDE.md。

标准装法是两条命令：

git clone https://github.com/calesthio/OpenMontage.git
cd OpenMontage && make setup

没有 make 就手动来，macOS / Linux 一行搞定：建 venv、装 requirements.txt、进 remotion-composer 跑 npm install、装 piper-tts、把 .env.example 复制成 .env。Windows 上如果 npm install 报 ERR_INVALID_ARG_TYPE，README 给的绕法是 npx --yes npm install。

装完就在助手对话框里下指令，不需要记命令。比如：「Make a 60-second animated explainer about how neural networks learn」。想要真实素材路线，措辞要更明确——必须点出 documentary montage / stock-footage collage 这类词，并显式写上 use real footage only，否则 agent 会默认走生成路线。README 把这当作已知的触发条件，不是 bug。

零密钥也能跑。make setup 自带的免费组合是：Piper TTS 做离线旁白，Archive.org、NASA、Wikimedia Commons 提供开放素材，Remotion 做 React 合成，FFmpeg 做后期，字幕用内置词级时间戳。Pexels、Unsplash、Pixabay 的 key 免费申请。想接商业模型再往 .env 里加，FLUX、Veo、Kling、Seedance、ElevenLabs、Suno 这些都有对应变量，README 的原话是 every key is optional。想白嫖本地算力就跑 make install-gpu，之后把 VIDEO_GEN_LOCAL_ENABLED 打开，模型可选 wan2.2-ti2v-5b、hunyuan-1.5 之类。

还有两个不装 key 也能用的自检命令，值得先跑一遍看看它认得出多少能力：python -c "from tools.tool_registry import registry; registry.discover(); print(registry.provider_menu())"。以及 make demo 渲染一条零密钥的演示片，make test-contracts 跑不需要 API key 的契约测试。

05 · 冷思考

74,007 星里，有多少是投给「流程」的

第一个数字对比值得盯住：74,007 个星标，订阅者（watch）只有 368 个，占比 0.5%。同时 fork 有 9,702 个，占星标 13.1%——这个比例在开源项目里偏高。星标是收藏，fork 是要真跑。两者一起看，更像是「很多人想拿它改自己的流水线」，而不是「很多人天天在用它做片子」。热度真实，但用法可能和标题给人的印象不一样。

第二个质疑是维护节奏。421 个未关闭 issue，最后一次 push 在 10 月 28 日。一个 7.4 万星的项目，四天没有代码提交，issue 堆到四百多——这不一定是作者跑路，但至少说明吞吐跟不上流入。AGPL-3.0 也是道坎：你要是拿它改一改，做成给别人用的网络服务，按协议得把改动开源。想做商业化剪辑 SaaS 的，这条得先想清楚，它不是 MIT。

第三个是最实际的：预算闸门的摩擦成本。单次动作超 $0.50 就要停下来等人确认，总预算默认 $10 封顶。对个人玩一玩够用，但一条 60 秒的片子如果涉及几十次素材生成，你会被反复打断，最后大概率把阈值调高——而调高之后，这套治理机制就等于没有。它设计得很认真，但认真和好用之间隔着一段。治理的价值取决于你愿不愿意一直守在旁边点确认。

第四个是隐性成本：上下文。700 多份技能与知识文件，每个阶段都要加载对应的 director skill，加上 reviewer、checkpoint-protocol 这些 meta 层。这意味着每次跑管线，模型都要先吃进一大堆指令。README 承认目前还不支持本地 LLM，Ollama 和 LM Studio 在「coming soon」里——也就是说，你依然得为这套流程付云模型的 token 钱，而这笔钱不显示在 $10 的预算表里。

最后说一句它没解决的问题。「把视频制作拆成工序」这件事，对熟手是加分——它把经验固化成可复用的检查项；对新手是负担——你得先知道自己要什么，才能批准分镜、才能判断素材选得对不对。项目把「人的判断」放在了流程的正中央，四个阶段都要你签字。这既是它比一键生成靠谱的原因，也是它没法真正「自动」的原因。

我的判断是：OpenMontage 值得装，但别指望它替你做决定。它真正的价值不在那 11 条管线，而在 skills/meta/reviewer.md 那 25KB 的验收标准——那是一份可以抄的「什么叫剪得还行」的清单。哪怕你不用它的工具链，把那几个文件读一遍，也比再看十个 AI 视频工具测评有用。想省事、想一键出片的人，用 Veo 或可灵更直接；想把做片子的标准沉淀下来、反复复用的人，才用得上它。
