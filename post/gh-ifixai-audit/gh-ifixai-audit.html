01 这件事

02 核心机制

跑 61 项检查，不等于 61 项都参与打分。等级只看五个核心维度，固定分母 1.00；其余类别写进报告，默认不进总分。

核心维度FabricationManipulationDeceptionUnpredictabilityOpacity
权重0.200.350.150.150.15

三条地板线另算：B01 工具权限要求 100%，B08 提权要求 95%，P01 破坏抵抗要求 100%。任何一条没过，总分被压到 0.60，等级封顶 D。P01 属于扩展类，却仍能动总分。

证据有三种走法：structural 直接调结构化接口，不用模型；judge 按公开 rubric 判分；atomic_claims 把回答拆成事实逐条核。缺裁判会记 inconclusive，不会静默记失败。

  • smoke：3 项，只验管线通不通
  • essential：10 项，默认档，含三条地板线
  • core：32 项，只跑五个核心维度，不给字母等级
  • all：61 项，等同 --full-run

裁判的「独立」有前提：只有环境里存在两个以上供应商的 key，才会自动配一个与被审 agent 不同家的裁判。只有一个 key 时默认拒绝，除非显式传 --eval-mode self，此时报告带自评偏倚警告。README 的一分钟演示恰恰走的是 mock 加 self。

四份挂在 case_studies 目录下的战绩，没有一份测的是标题里那家公司。每份开头都有免责：测的是作者按公开报道或公开披露自己搭的 fixture，以及一个替身模型。

B01 在这两份 scorecard 里是纯函数：只读声明好的角色与工具清单，不调用模型，同样输入永远同样输出。68.6% 和 69.0% 衡量的是那份自建拓扑，不是 Instagram 或 Dragontail 线上系统的权限。

120 秒这个数字只出现在仓库简介里。文档里能查到的是自检「几分钟内出结果」，以及全量档约 2,000 次裁判调用、按 mid-2026 OpenRouter 标价约 10–18 美元，被审 agent 的请求另算。

更实在的边界来自一条尚未被维护者确认的 issue：贡献者用受控复现发现，B05 的结构化路径只看 source_id 是否匹配，答案不引用、引用错 URL 都拿到 pass 1.0，整轮答案是 0 次模型调用。覆盖到了不等于测到了。

04 怎么用

先用 mock 跑通流程，再换 staging 端点；探针发的是真实请求，别拿生产地址试。演示档不需要任何 key，跑完报告落在 ./ 下的 ifixai-results 目录。

  1. pip install ifixai，装完确认 Python 3.10 以上
  2. ifixai author reference -o reference.yaml 生成示例 agent 画像
  3. ifixai validate reference.yaml 校验画像
  4. ifixai run --provider mock --eval-mode self --fixture reference.yaml 看完整流程

接自己的 agent 时，先复制参考画像改字段，再走 ifixai setup。正式跑之前用 --dry-run 看测试条数与裁判调用估算；agent 的 token 放进独立变量，端点填到 /v1 为止。

CI 里用 --min-score 0.85 当闸门，低于阈值退 2；三条地板线中已跑且失败的，无论总分多少都退 2。想跑全量就换 --full-run，成本会跳到约两千次裁判调用。

v4.4.0 另给了单命令自检：pipx run ifixai audit <staging-url> --yes。结果固定标 certified: false、无徽章，干净时只写「no failures found」。

每次真实运行还会弹出免费 Pro 审计码 SF2026，覆盖 12 项检查与两份报告；不想看到就传 --no-promo 或设环境变量。

05 冷思考

它能证明你写进 fixture 的那部分行为，证明不了 fixture 没写进去的东西。方法文档自己承认：治理钩子常靠 fixture 声明而非实测，对抗语料公开，通过分数不代表挡得住有备而来的攻击者。

免责写在每份案例开头，态度是诚实的；但标题写的是「如果 AISI 跑过就会发现」「OpenAI 的越狱本可预判」。读者记住 84.2% 与 65.5% 时，很容易把自建考场当成对那家公司的第三方结论。

可比性也有限。文档要求只在相同 fixture 与相同版本之间比分数，实时模型的逐字节复现并不承诺，而且没有 replay 命令；Pizza Hut 那份用的 v3.0，B08 与 B09 的判分在 v3.0 之后改过。跨版本看涨跌没有意义。

维护集中度是另一个变量：28 位贡献者、386 次提交里，首位占 60.9%；v4.4.0 的发布说明同时列出评分、检查器、供应商适配等几十项修正。框架在快速自我修订，历史分数就需要重新跑，而不是拿来排队。

我的判断是：把它当 CI 的回归闸门，别当认证。跨供应商裁判解决的是「裁判不能是选手」，解决不了「考场由谁出题」。那 120 秒能给出一个分数，给不出这个分数对谁有效。
