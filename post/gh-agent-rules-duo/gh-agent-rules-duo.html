230784星负面清单、148584星官方脚手架：约束不在一层

230,784 星，karpathy-skills 只交一份 2,357 字节的 CLAUDE.md 负面清单；spec-kit 148,584 星，是 GitHub 官方 SDD 脚手架，9 个命令模板把流程做成门禁。改脾气还是改工序。

expectopatronus 2026-11-08 约 10 分钟阅读 原创 · AI 编程
01 · 这件事

两个仓库都在给编码 agent 立规矩，一个交清单，一个交工序

multica-ai/andrej-karpathy-skills 2026 年 1 月 27 日建库，核对时 230,784 星、22,965 个 fork、1,305 个订阅者、139 个未关闭 issue，API 的 size 字段只有 20 KB，license 与 language 都是 null，最后一次 push 停在 2026 年 4 月 20 日。它的 description 一句话交代了来历：A single CLAUDE.md file to improve Claude Code behavior, derived from Andrej Karpathy's observations on LLM coding pitfalls——把 Karpathy 对大模型写代码那些毛病的观察，收成一份 CLAUDE.md。

另一个是 github/spec-kit，GitHub 官方仓，2025 年 8 月 21 日建库，148,584 星、13,354 个 fork、737 个订阅者、209 个未关闭 issue，MIT，Python，size 22439 KB，最后 push 在 2026 年 11 月 7 日 04:09——核对当天它前一天还在动。description 写的是 Toolkit to help you get started with SDD or any other process!，homepage 指向 github.github.io/spec-kit/，挂了 7 个 topic：ai、copilot、development、engineering、prd、spec、spec-driven。

两条都在积压队列的 agent-rules 一族，评分 97 和 82，所以这篇做横评，一次消耗两条。但把 README 和目录摊开就会发现，它俩根本不在同一层上约束 agent：一个交给模型一份人写的负面清单，靠它自觉少犯错；一个交给项目一套官方脚手架，把「先写清楚再动手」做成必须走完的流程。站内 11-07 的 gh-agent-skills-trio 讲 skills 规范与三方实现之争，本文不复述那场争论，只问一句：装完之后，agent 的具体行为到底哪里变了。

02 · 核心机制

一份压进上下文的否定句，和一组生成产物的命令门禁

A 的全部机制就是那个 2357 字节的 CLAUDE.md。它分四节：Think Before Coding、Simplicity First、Surgical Changes、Goal-Driven Execution，通篇是 Don't assume、No features beyond what was asked、Don't refactor things that aren't broken 这类否定句，要求下笔前先陈述假设、不确定就问、只改该改的行、把任务翻成可验证的目标再循环。约束靠的是 CLAUDE.md 这个约定文件名本身——Claude Code 一开会话就把它读进上下文。它不改变工作流程，只压住模型的默认倾向：装完最直观的变化是 diff 更干净、澄清问题前移、少过度设计。

更值得注意的是它给自己写的退路。文件开头就声明 These guidelines bias toward caution over speed. For trivial tasks, use judgment.，结尾又给了一条自检标准：更少的无关改动、更少的返工、澄清问题出现在动手之前而不是出错之后。这是软约束，没有 hook、没有脚本、没有任何拦截：模型不理它，什么都不会发生；换个不读 CLAUDE.md 的宿主，仓库另给一份 CURSOR.md（1955 字节），仍是同一份文本、同一种软约束。

B 反过来，管的是工序。specify init 之后项目里多出 .specify/，templates/ 下 7 个条目里有 spec-template.md、plan-template.md、tasks-template.md、constitution-template.md、checklist-template.md，templates/commands/ 下 9 个命令模板：analyze、checklist、clarify、constitution、converge、implement、plan、specify、tasks。README 给的最小流程是 /speckit-constitution 立原则、/speckit-specify 写规格、/speckit-plan 定技术栈、/speckit-tasks 拆任务、/speckit-implement 执行、/speckit-converge 收口，每一步落一份可评审的产物。它把「接活就写」改写成一条不能跳的流水线。

于是装 B 之后，agent 的活法变了：不再直接答你「做个相册」，而是先逼出一份章程和 spec，把「按日期分组、平铺预览」这类话固定成文档，再逐层往下推，产物留在 .specify/ 里供下次续用。README 自己把定位写得很白：gives AI coding agents structured processes, reusable templates, and documented outcomes。A 改的是脾气，B 改的是工序——同样是立规矩，一个改模型下笔前的犹豫，一个改模型开工后的顺序。

03 · 关键细节与数据

230,784 星的那个只报 20 KB，148,584 星的那个有 22,439 KB

先把两组的硬数字摊平。A：230,784 星、22,965 fork、1,305 订阅、139 未关闭 issue、2026-01-27 03:53 建库、2026-04-20 10:05 最后 push、license 为 null、language 为 null、size 20 KB、topics 0 个、default_branch main、homepage 空。B：148,584 星、13,354 fork、737 订阅、209 未关闭 issue、2025-08-21 22:54 建库、2026-11-07 04:09 最后 push、MIT、Python、size 22,439 KB、topics 7 个、default_branch main、homepage 指向官方站。星更高的那个，size 只有 20 KB，另一个是 22,439 KB。

再看「厚度」完全不和星标成正比。A 的核心就一份 2,357 字节的 CLAUDE.md，加上另外 4 份 Markdown（CURSOR.md 1,955、EXAMPLES.md 14,838、README.md 6,198、README.zh.md 6,042 字节）和 1 个 skills/ 目录；B 是 22,439 KB 的 Python 工程，src/specify_cli、scripts/ 下 bash / powershell / python 三套脚本、presets/ 7 个条目、templates/commands/ 9 个命令模板，外加 docs/、tests/、workflows/，还带 CHANGELOG.md 149,562 字节和 CONTRIBUTING.md 30,235 字节。一个把全部约束压进 2,357 字节，一个把约束摊成整套工程。

有两处口径必须挑明。第一处是 A 的体积：API 的 size 字段报 20 KB，可 /contents/ 下根目录 5 个文件的字节相加是 31,390——size 是压缩后的 git 体积口径、且可能滞后，不是文件实数，别拿它当「全仓就这么大」。第二处是 description 的自述：它写 A single CLAUDE.md file，可仓库实际已经长出 CURSOR.md、EXAMPLES.md、两份 README、skills/ 和 .claude-plugin/，「单文件」是叙事，不是目录现状；再加上 API 的 license 字段为 null，抄进闭源产品前得自己确认能不能用，而不是看一句 description。

最后是热度口径。选题池给 github/spec-kit 挂了「本周 Trending 标注增 4,280 星」，karpathy-skills 那条只是 97 分积压、并没有这个标注，两者别混；但 GitHub API 根本没有「本周新增星」这个字段，4,280 无法从仓库或接口复核，本文只当作选题时的热度标注、不进任何实测结论。把周榜标注当实测排序，等于拿标注当测量。能站稳的只有 stars、forks、created_at、pushed_at 这类接口直接给的字段，和 /contents/ 数出来的 9 个命令模板、7 个模板条目、5 个根目录文件。

04 · 怎么用

先决定要约束的是脾气还是工序，再选安装命令

A 几乎不用装。把 CLAUDE.md 放进项目根目录（或按它开头那句 Merge with project-specific instructions as needed 并进你已有的规则文件），Claude Code 开会话自己会读；用 Cursor 就换 CURSOR.md；想按插件分发，.claude-plugin/ 里已经有 marketplace.json 和 plugin.json。它的正确用法偏「读」：照四节否定句改自己的 AGENTS.md，或翻 EXAMPLES.md 看反例，而不是指望它替你管流程。零依赖、零配置、跨宿主，代价也在这：全靠模型愿意照做。

B 要先装 CLI。README 要求 Python 3.11+ 和 uv，命令是 uv tool install specify-cli，再 specify init my-project --integration copilot 生成项目；换别的 agent 要按 integration key 分别配。想加 bug 修复或点子评估，再 specify extension add bug、specify extension add assess，对应的 /speckit-bug-assess、/speckit-assess-intake 才会出现。装完按 /speckit-specify 到 /speckit-implement 的顺序走，产物落在 .specify/。它给的是一套可复现的工序，代价是每次都得从模板起步。

判断表如下，A 是 multica-ai/andrej-karpathy-skills，B 是 github/spec-kit：

  • 只想压住过度设计、乱改相邻代码、不懂装懂这些常见毛病，且改的多是琐碎任务——选 A。2,357 字节的负面清单放进根目录就生效，不绑架开工顺序，改一行 bug 也不用先写 spec；代价是纯靠模型自觉，且 license 为 null、最后一次 push 停在 2026-04-20。
  • 要从零起一个正经项目、团队要可评审的 spec/plan/tasks 文档、要把「先写清楚再动手」变成门禁——选 B。9 个命令模板加 specify CLI 把流程固定成产物，官方维护、MIT、核对前一天还在 push；代价是 Python 3.11+ 与 uv 的前置，以及改个小 typo 也得走流程（或另装 bug 扩展）。
  • 两者都想要——可以叠：把 A 那四节否定句抄进 B 的 constitution-template.md，让「别过度设计」成为项目章程的一条，再交给 B 的命令门禁去执行。别指望 A 给流程、B 给否定清单，它俩管的是不同层，混着读会两头落空。
  • 两者都可以不装——你若只需要「先报假设、只改该改的」这几条，直接把方法写进自己的 AGENTS.md，比养一个 CLI 和 9 个命令模板便宜；反过来，只想看看 SDD 长什么样，读 spec-driven.md（26,229 字节）也就够了，不必 specify init。

一个务实提醒：两者都不改模型，改的是模型开机时读到的那摞文本、以及它按什么顺序被驱动。A 是 2,357 字节的清单，B 是 uv 装出来的 CLI 加 9 个命令模板。装得越重，故障面越大：B 少了 Python 3.11+ 或 uv，specify init 根本跑不起来；A 更干脆，本来就只是几份能读的 Markdown。

05 · 冷思考

230,784 星量的是谁的名字，不是装了之后改变多少

先质疑星标。A 230,784 星、B 148,584 星，差了八万多，可把时间摊开看很不对劲：A 的 created_at 是 2026-01-27，pushed_at 停在 2026-04-20，核对时已经超过半年没动，license 是 null，size 报 20 KB；B 2025-08-21 建库，2026-11-07 还在 push，MIT、22,439 KB、7 个 topic、一份 149,562 字节的 CHANGELOG。星更高的那个，作者名气和「一份文件治好 AI 瞎写代码」的叙事占了大头，机制上它只是 4 节否定句。订阅率也都不高：A 1,305 除以 230,784 约 0.57%，B 737 除以 148,584 约 0.50%，两边都是「先收藏」的量级。把 23 万星读成「更该先装」，正好读反了：持续投入的官方工程反而是星更少的那个。

再质疑「装了行为变了」这件事本身。A 是纯文本、无 hook、无强制，连自己都写 bias toward caution over speed、For trivial tasks, use judgment，等于承认琐碎任务上这份规矩会自动让位；换一个不读 CLAUDE.md 的宿主，行为根本不变。B 把流程做成门禁，可反过来，偏不了流程也意味着临场改主意变难——官方后来把 bug fixing、idea assessment 拆成 specify extension add 才装的可选扩展，README 还专门声明 These are independent entry points, not mandatory phases，正是在给「改一行字也要走六步」松绑。粒度越粗，agent 越听话，你越难绕开它。两者交付的都是文本加命令，不是运行时；行为的改变全靠宿主愿不愿意在开机时读进去、愿不愿意按命令走。

第三处质疑在自述的可靠性。description 说 A single CLAUDE.md file，目录里却已经摊着 5 份 Markdown 加插件壳；API 的 size 报 20 KB，/contents/ 的根目录字节和却是 31,390；所谓「本周 Trending 标注增 4,280 星」只来自选题池周榜，GitHub API 根本没有周增字段，还被特意叮嘱别混到 karpathy-skills 头上。这些对不齐的地方，恰恰是最容易被当成硬指标的那些。唯一能站稳的，是 stars、forks、created_at、pushed_at，和 /contents/ 数出来的 9、7、5 这些实数。

第四处是「不装配套工具会怎样」。B 不装 Python 3.11+ 和 uv，uv tool install specify-cli 就走不下去，脚手架进不了项目；A 更干脆，它本来就只是几份能读的 Markdown，不读就完全没装。「立规矩」这件事的成本，几乎全在宿主这一侧：清单要宿主开机读、脚手架要宿主认命令，换一个不认的环境，重装一遍是小事，规则根本不生效才是常态。

所以判断不是「哪个星多装哪个」，也不是「官方的就更该装」，而是「你要约束的是 agent 的脾气还是它的工序」。只想让它少过度设计、少乱改、不懂就问，选 A 那份 2,357 字节的负面清单，放进根目录就完事；要把它从「接活就写」改造成「先立原则、再写 spec、再拆任务、最后收口」，选 B 那套 9 个命令模板的官方脚手架，并接受 Python 3.11+ 与 uv 的门票。最该先做的不是装，是先写清楚你要改的是哪一层：改脾气用文本，改工序才上 CLI——顺序反了，你会先花半小时配 uv，再发现要的只是一句「别自作主张加功能」。
