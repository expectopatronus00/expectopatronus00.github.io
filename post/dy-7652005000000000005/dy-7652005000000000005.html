AI 开发 Harness

CodeX 进阶教程：模型变强后，开发流程该怎么重做

Fable 5 已上线，GPT-5.5 和 Opus 4.8 也在逼近能力边界。当大模型已经足够自主时，AI 开发的 Harness 不该再是写详细步骤，而是设目标、写循环。

01 · 一个正在发生的变化

模型变强了，而我们的协作方式没变

过去 12 个月，大模型的能力边界发生了一次安静的跃迁。Fable 5 上线，GPT-5.5 和 Opus 4.8 在不同场景中逼近或超越了之前的 SOTA。一个直接的影响是：模型不再需要你手把手告诉它怎么做了。

但大多数人使用 AI 的方式并没有随之更新。我们仍然在写长长的步骤清单、在对话框里一条一条喂信息、在出问题时花同样长的时间手动修正。这就好像买了一台全自动洗衣机，却仍然坚持用手搓每一件衣服——不是机器不行，是我们的使用方式没跟上。

模型越强，你给它的指令应该越少，而不是更多。

02 · 从步骤到目标

什么叫「重做开发流程」

一个好的 AI 开发流程，应当把人和模型的分工重置为：人定义目标和边界，模型负责达成目标。这句话听起来很抽象，但在 CodeX 的实践中，它可以分解为几个非常具体的操作。

第一，把步骤清单换成目标描述。不要告诉它「1. 创建一个文件 2. 定义这个函数 3. 添加错误处理」，而是告诉它「创建一个能完成 X 功能的模块，要求：通过 Y 测试、包含错误处理、不引入 Z 依赖」。

第二，把单点调用换成循环。不要一次只让它做一件事。让它自己跑「生成 → 自检 → 修复 → 再自检」的循环，直到达到你定义的通过条件。

第三，把人工评审换成可机器校验的评估。如果你判断「代码写得好不好」的方式是「看起来还行」，那这个标准无法被机器复用。把验收标准翻译成可运行的东西——测试、lint、格式检查、性能基准——然后让循环在这些检查面前自动收敛。

03 · Harness 不是框架

它是一套约束模型行为的工具

很多人听到 Harness 这个词，会以为它是又一个 Agent 框架。不是。Harness 更准确的翻译是「牵引带」——它不决定模型朝哪个方向走，它只决定模型不能朝哪走。

在 CodeX 的语境中，Harness 通常由三样东西组成：

文件系统的可写边界：模型能改哪些文件、不能改哪些文件。如果你在做一个既有项目，通常只允许它修改特定目录下的新文件，避免它触碰正在生产运行的旧逻辑。

命令白名单：模型能跑哪些命令。通常允许它跑测试、代码格式化、类型检查，但禁止它执行数据库写入、权限变更、部署等不可逆操作。

停止条件：当模型在循环中连续失败 N 次，或者消耗的 tokens 超过预算时，Harness 会强制中断它，向人发出信号。

一个好的 Harness 有三个特征：默认封闭、例外透明、失败可回滚。

04 · Vibe Coding 的核心

不是写代码，而是描述「想要的样子」

在 CodeX 社区里流行一个词：Vibe Coding。翻译过来大概是「凭感觉编码」——但它的意思恰好和字面相反：它不是让你凭直觉瞎写，而是让你用自然语言描述「想要的系统是什么样子」，然后让模型自己去实现它。

Vibe Coding 的一个典型工作流程是这样的：

第一步（人）：打开一个空目录，用一段话描述你要的系统——用什么语言、有哪些功能、数据如何流动、怎么部署。这一步不需要写任何代码。

第二步（模型）：模型根据描述，自主拆分文件结构、编写实现、添加测试。它会自己判断需要几个文件、每个文件里放什么、用什么设计模式。

第三步（人 + 模型）：你检查它的产出是否符合你的 Vibe。如果方向对但细节不够，你不用逐行改，而是用一句话反馈你「想要的样子」，让它自己进入下一轮循环调整。

第四步（人）：当产出接近你的标准时，你接管最后的打磨——通常是命名调整、结构微调、边界条件补充。这一步的工作量不到 20%。

Vibe Coding 的本质：把工程师从「实现者」挪回「架构师」和「评审者」的位置。

05 · 为什么是现在

三件刚刚成熟的事

这种流程不是新想法，它之所以在 2026 年突然变得可落地，是因为三件事同时成熟了。

第一件，长上下文 + 工具调用稳定了。现在的模型可以在一个上下文中保持一整个项目的心智模型，不会在 300 行之后忘记之前的决策。

第二件，模型能自己跑测试、自己读日志。之前的模型只能产出代码，需要人把代码挪到终端里跑一遍、再把错误粘回去。今天的模型可以自己调用命令、读取输出、再自己修。

第三件，社区对 Harness 的共识正在形成。不是每个人都在写 Harness，但越来越多的人同意：不加护栏的 AI 编码，在生产环境里是不负责任的。这让「设目标 + 写循环 + 加护栏」的三件套，从个人偏好变成了团队规范。

06 · 你可以立刻开始的三件小事

不用等别人推流程，自己先试

如果你读完这篇文章想立刻动手，我建议三件小事，按顺序来：

1. 下次写代码时，先把需求写在注释里。不要写实现，只写「这段代码应该做什么、输入是什么、输出是什么、哪些情况应该报错」。然后让模型去填——这是在练习「描述目标」。

2. 为你负责的项目加一个可以一键运行的质量检查。不只是跑测试，还包括 lint、类型检查、格式化校验。这个东西的价值，不是它能发现多少 bug，而是它给了 AI 一个可自动执行的评估标准。

3. 挑一个小的新功能，完整地走一遍 Vibe Coding 流程：描述 → 让它自己写 → 自己跑测试 → 让它自己修 → 你最后评审。不要在中间插手。完整走完一次，你会对循环的力量有不同的感受。

07 · 写在最后

开发流程的重做，核心是职责的重划

当我说「开发流程该重做」时，我不是在说要把 CodeX 塞进每一家公司，也不是说所有代码都必须让 AI 写。我在说的是一件更朴素的事：当工具的能力边界变了，人和工具的分工也应该跟着变。

模型变强之后，工程师的核心产出，不应该再是代码行数，而是目标的清晰度、评估标准的完备性、以及系统边界的健壮性。你写的不是步骤清单，而是让模型在里面循环的那个「框」。

未来判断一个工程师是否优秀，标准可能会从「他写的代码有多快」，逐渐变成「他设计的循环有多聪明」。这不是悲观的宣告，而是乐观的邀请——因为循环设计这件事，比写代码更能体现人的判断力和品味。
