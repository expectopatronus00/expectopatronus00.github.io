01 这件事

把 agent 当队友排进看板、让它在你自己的机器上领 issue 干活——Multica 把这件事做成了产品，但仓库简介里的「开源」二字要打折读。截至 2026-11-21，multica-ai/multica 有 56,998 星、7,505 fork，2026-01-13 创建，主语言 Go，当天仍有推送。

仓库 description 写的是「Make humans and AI agents work as one team — open-source and self-hostable」。README 第一段却改口，称自己是 source-available workspace。

两句话贴在同一个仓库门口，指向的是两种不同的东西。

02 核心机制

Multica 不发货模型，它把已经登录好的命令行 agent 变成看板上的「员工」，工作单元是 issue，交付物是 pull request。意图、运行记录、决策和 diff 都挂在同一个 issue 上，人只在 review 闸门点头。

层技术栈跑在哪
WebNext.js 16 App Router浏览器
Desktop / MobileElectron / Expo React NativemacOS、Windows、Linux；iPhone、iPad
BackendGo（Chi、sqlc、gorilla/websocket）自托管服务器或云
DatabasePostgreSQL 17（pgcrypto + pg_trgm）自托管服务器或云
Agent runtime本地 daemon，拉起 agent CLI你的机器，贴着代码

它驱动的命令行工具按 README 表格数正好 31 个：15 行各两列，加最后一行 ZCode 一个。

Claude Code、Codex、Cursor Agent、Copilot、Kimi、OpenCode 在列，DeepSeek Harness、Qwen Code、Grok、Devin CLI 也在列。切换供应商是一个下拉框，不是一次迁移。

但「能上岗」不等于「能中途接话」。README 写明当前只有 6 家支持运行中改指令：claude、codex、cursor-agent、grok、kiro-cli、pi。其余二十多个 provider 领了任务就按自己的节奏跑，靠 retries 和 timeouts 兜底。

看板之上还有四个概念：Squads 把人和 agent 编成一队、由 leader 派活；Skills 把解决过的问题固化成复用手册；Autopilots 用 cron 跑站会和审计；Review gates 让产物先落在评审、再进主分支。它管的是分工与留痕，不是模型能力。

03 关键细节与数据

许可证把「自己用」和「拿出去给别人用」切成两半，遥测又把「自托管」切成默认开启和显式关闭两半。这两处都不在仓库简介里，得翻到 LICENSE 和 SELF_HOSTING.md 才看得到。

文件 / 目录适用条款关键限制
LICENSE Part IMultica 附加条件不得对外提供托管服务或商业嵌入；不得移除品牌
LICENSE Part IIApache License 2.0 全文与 Part I 冲突时以 Part I 为准
server/ee/ packages/ee/各目录内单独的商业许可证不适用 Multica License，共 31 个文件、76,964 字节

附加条件 a 写得极具体：没有商业许可证，不得用这份源码向第三方提供托管服务，也不得作为商品组件分发；面向组织外部开放即算托管，即便免费、无广告、不卖付费层也一样。

单一组织内部使用（含多个 workspace）不需要商业许可；公开 fork 源码本身不算托管，但每个运营方要各自取证。

条件 b 管品牌：不得移除或改动 LOGO、产品名和界面上的版权信息，覆盖范围点名 apps/web/、apps/desktop/、apps/mobile/、packages/views/、packages/ui/ 以及前端容器镜像。

条件 1.d 再补一刀：商业许可不自动包含品牌豁免，两者要分别书面取得。

04 怎么用

真要自托管，先算三笔账：Docker 环境、至少一个已登录的 agent CLI，以及许可证允不允许你的用法。README 把先验条件说在前面：Multica 驱动这些工具，但不随附它们，也不替你登录。

  1. 装好 Docker 与 Docker Compose，这是脚本的硬前置
  2. 运行 curl -fsSL https://raw.githubusercontent.com/multica-ai/multica/main/scripts/install.sh | bash -s -- --with-server
  3. 执行 multica setup self-host，脚本从 GHCR 拉官方镜像并按 localhost 配置
  4. Team → Runtimes 添加机器，把页面给的两条命令贴到目标机器终端
  5. Team → 新建 agent，选 runtime、provider 和名字，再建 issue 指派给它

Windows 用 $env:MULTICA_MODE="with-server" 加 PowerShell 安装脚本。镜像 tag 尚未发布时，退回源码构建 make selfhost-build；要钉版本就设 MULTICA_IMAGE_TAG，例如 v0.2.4。

有 K8s 集群可改用 GHCR 上的 OCI Helm chart。

关遥测要在 API 服务器上设 DO_NOT_TRACK=1 或 true，再重建并重启后端。ANALYTICS_DISABLED 管的是另一套 PostHog 集成，关不掉第一方遥测。

克隆生产库做 staging 时，先清掉 instance_telemetry_state 表，否则两套部署共用一个身份、当天快照会互相去重。

接入面比想象中杂：Git 支持 GitHub、GitLab、Gitea、Forgejo；聊天通道列了 Slack、飞书、钉钉、企微、Telegram 和微信。

微信只接受扫码账号的私聊，新飞书连接目前只开放中国大陆租户，钉钉、企微、Telegram 标注为社区维护。iOS 客户端今天仍需从源码构建，未上 App Store。

05 冷思考

56,998 星买的是「把 agent 排进看板」的编排层，许可证保留的是「谁可以把它当服务卖」的那一层。这两层不矛盾，但把它们混成一句「开源替代」，就会在部署那天踩空。

信息落差是真实存在的：搜索结果和星标只显示 description 里的 open-source；README 正文写的是 source-available；许可证接口返回 NOASSERTION；LICENSE 第一页就声明 Part I 优先于 Apache 2.0。

作者没有藏，只是藏得比标题深一层。对只想内部用的团队，这无关紧要；对打算基于它做托管产品的人，这是第一道门槛。

免费对外托管也要授权这条尤其具体。公司内部开一百个 workspace 都行；给客户开账号、哪怕不收费、不放广告、不设付费层，就要商业许可证。

公开 fork 源码不被算作托管服务，但源码分发不授予接收方运营权——每个接手的人得自己去找 producer 谈。

贡献条款也值得先读：提交贡献即视为同意 producer 可以把这份许可证改得更严或更宽，且贡献代码可用于其云业务。

这在 source-available 项目里是常见写法，不是陷阱；但它提醒你，这里的「社区」和「许可证」不是同一件事。

31 个 provider 与 6 个可中途指挥的落差，是另一处要打折的地方。多一家供应商确实是下拉框，但下拉框背后是另一份订阅和另一次登录——agent CLI 的 token、额度与可用性都不归 Multica 管。

看板把并发排得再整齐，账还是各自结。

README 还强调 no lock-in。技术上确实如此：源码可 fork，Git host 可选 GitHub、GitLab、Gitea、Forgejo。但锁定换了地方——31 家 provider 各自要订阅、要登录、要管 token，Multica 只负责把它们排进看板，不承担任何一家的额度。

遥测默认开启、端点硬编码不可重定向，文档写得细也算坦诚，但「自托管」在多数人心里等于数据不出内网。每天有一个匿名快照出网，直到你显式关掉它——匿名不等于没有。

我的判断是：要内部团队的 agent 看板，它把编排、留痕和 review 闸门摆齐了；要能改名、能对外托管、能打包转售的开源底座，这份许可证从第一天起就没打算给。别看星标，翻到 Part I。
