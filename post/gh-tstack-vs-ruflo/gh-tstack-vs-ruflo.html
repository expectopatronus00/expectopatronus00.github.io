2600 星对 8 万星：一份手册和一个运行时

2,600 星、14 次提交、16 个文件、59,560 字节——tstack 整个仓库摊开不到 60 KB。另一个是 80,584 星、10,008 次提交、8,446 个文件、648 MB 的 ruflo。两者都自称 agent harness，但仓库里同时躺着 32、33+21、35、48、49 五套插件数口径，还有一个自相矛盾的 150 倍加速说法。

01 · 这件事

两个都在管 agent 的仓库，一个 58 KB，一个 648 MB

t3dotgg/tstack，2026 年 10 月 24 日建库，到今天 2,600 星、171 个 fork、30 个订阅者、12 个未关闭 issue，MIT 协议，最后一次 push 停在 10 月 28 日。仓库的自我描述很克制：The agent skills I use every day, cleaned up so anyone can use them——我每天在用的 agent skills，清理干净了所以谁都能用。

另一个是 ruvnet/ruflo，2025 年 6 月 2 日建库，也就是 Claude Flow 改名前的那个项目。80,584 星、9,458 个 fork、475 个订阅者、987 个未关闭 issue，同样是 MIT。今天上午 9 点 21 分它刚 push 过，作者是 Reuven Cohen（rUv）。仓库描述第一句就写着 The original agent harness。

两者的体量差了一个数量级还不止。我把两个仓库的 git tree 整个拉下来数过：tstack 一共 16 个文件、59,560 字节，ruflo 是 8,446 个文件、语言字节 44,466,739。GitHub 自己的 size 字段也是同一个结论——tstack 记 25 KB，ruflo 记 663,914 KB。前者整个仓库摊开还不到 60 KB，后者约 648 MB。

它们也被放进了同一个待办队列：都是「agent 编排」这一族，都排在积压队列的前列，都被人打了 80 分以上的分。所以这篇是一次横评，一次消耗两条积压。

02 · 核心机制

一个是把手法写成说明书，一个是把说明书变成运行时

先说 tstack 的机制，因为它简单得有点反常。整个仓库是 9 个 SKILL.md，加起来 30,646 字节，加上 4 个 agents/openai.yaml（850 字节）、一个 LICENSE、一个 README.md，以及唯一一段可执行代码——skills/babysit-pr/scripts/pr-wait，24,724 字节。它占全仓字节的 41.5%。也就是说这个 2,600 星的仓库，超过四成的体积是这一个 Python 脚本，其余全是 Markdown 说明书。

这 9 个技能是一张有向图。README 自己写明了依赖关系：full-send 会调 sol-loop、file-pr、babysit-pr；full-stop 调 full-send；takeover 调 modernize、file-pr、babysit-pr、leaving-pr-comments；而 file-pr、babysit-pr、modernize 三个都用 leaving-pr-comments。装的时候不能只装一个。

机制上最有意思的是 council 和 sol-loop 这两个。

council 的做法是请三个委托方来审：每家 provider 出一个最强模型，Claude Opus、GPT Sol、Gemini Pro 各一个，要求每个给出 10 分制评分，然后循环到三方都满意。SKILL.md 里有一条硬规定：If you cannot reach three providers, or a named member is unavailable, report it instead of substituting.——够不到三家就报错，不许拿别的模型顶替。

sol-loop 是单一审阅者的循环，而且它把预算写死了：默认总共 3 轮，第 1 轮全量，后面只查改动和未决项；只有涉及安全、权限、鉴权、数据丢失或状态并发这类问题才允许延到 5 轮。它还规定了意见分级——blocker 是「预期场景就是错的」，should 是「真实存在的 bug，调用方会撞上」，剩下的都算 nit。审查者被明令不许自己再开子 agent。

转到 ruflo，机制完全不同。它不是一个技能集合，是一整套运行时。README 里的数字是：314 个 MCP 工具、26 条 CLI 命令、100+ 个专用 agent、27 个 hook、12 个自动触发的后台 worker、5 家模型供应商带故障切换、路由准确率 89%。仓库里的骨架文件也印证了这个规模：.claude-plugin/marketplace.json 49 条市场条目，skills.sh.json 分 34 组共 134 个技能名，而全仓库真实存在的 SKILL.md 文件有 389 个。

它的插件分层也很清楚：plugins/ 下 48 个目录各自是一个 Claude Code 插件，市场文件里 46 条指向本地路径、3 条指向外部 git 仓库（agentic-qe-fleet、agentdb、agentic-flow）。安装方式是 npx ruflo@latest init wizard，或者 claude mcp add claude-flow -- npx ruflo@latest mcp start。

03 · 关键细节与数据

一个仓库的自述数字和实际内容完全对齐，另一个对不上

先说对得上的那个。tstack 的 README 用表格列了 9 个技能，我数了 skills/ 下的目录：babysit-pr、council、file-pr、full-send、full-stop、leaving-pr-comments、modernize、sol-loop、takeover，正好 9 个，一个不多一个不少。README 表格里写的触发短语、依赖关系、运行前提（已认证的 gh、python3、需要跨 provider 的子 agent 能力）都能在 SKILL.md 里对上。9 个 SKILL.md 的大小也讲得通这份克制：最大的 full-send 5,395 字节，最小的 leaving-pr-comments 1,600 字节。

再看对不上的那个。ruflo 描述自己插件数量时，仓库里同时存在四套口径：

  • README 第 206 行的折叠标题写 All 35 plugins；
  • README 的特性表写 33 native Claude Code plugins + 21 npm plugins；
  • plugins/README.md 第一行写 32 Claude Code plugins，第 92 行又写 All 32 plugins；
  • 而磁盘上实际是 48 个插件目录，市场文件里实际是 49 条。

而且这四套数字没有一套能推导出另一套。35 ≠ 33 ≠ 32 ≠ 48 ≠ 49。顺手对了一下名单：plugins/ 里的 ruflo-chatgpt-federation 和 ruflo-rure 两个目录不在市场文件里，市场文件里的三个外部条目则不在 plugins/ 目录下。

技能数也有一层偏差。README 的对比表写 Full Ruflo loop — 98 agents, 60+ commands, 30 skills，但 skills.sh.json 里是 34 组共 134 个技能名，全仓库真实 SKILL.md 文件 389 个，commands/ 下的 md 文件 491 个。分布上，.agents/skills 独占 135 个，v3/@claude-flow 41 个，.claude/skills 38 个，插件目录里最多的是 ruflo-cost-tracker 24 个、ruflo-metaharness 13 个、ruflo-ai-team 12 个。

最能说明问题的是一处性能数字的自我矛盾。plugins/README.md 写 ruflo-agentdb 提供 HNSW vector search (150x-12,500x faster)；而主 README 同一件事写的是 measured ~1.9x faster at N=20k, ~3.2x–4.7x at N=5k vs brute force，并且老老实实补了一句「小 N 时会打平甚至更慢」。两个数差了三个数量级。后者带着审计文档链接和基准脚本路径，前者没有出处。

不过 ruflo 最新版本（v3.71.0，11 月 1 日发布）里的实测数据是可以核的：它对 6 个真实仓库文件做 A/B，委派开关两种状态下都 6/6 正确，总成本降 22.5%，主循环输入 token 降 21.5%，耗时反而增加 6.5%。单次实测跑 agent-tools.ts（48,368 字节），模型只看到 1,360 字节（−97.2%），worker 用了 3.3 秒、16,741 输入 token、328 输出 token。这个版本还顺手纠正了前一个 release 说明里的一行错字：npm 的 CLI tarball 只打包 ruflo-console 和 ruflo-metaharness，光跑 npx ruflo@3.71.0 并不会装上那个功能。

再看两个仓库的 issue 面，那是最诚实的一面。tstack 的 12 个未关闭 issue 几乎全是环境适配：fix(babysit-pr): make pr-wait run on Windows、babysit-pr: never finishes in repos without Greptile or Macroscope、sol-loop: async review round has no deadline, so the parent waits forever if Sol never ends its turn、sol-loop: Sol reviews run at the model's default effort (low for gpt-6.1-sol)，还有一条 feat: publish skills as a Claude Code plugin marketplace。ruflo 那边是 987 个未关闭 issue。

04 · 怎么用

按你要解决的问题选，不按星标选

装 tstack 只要两条命令：git clone https://github.com/t3dotgg/tstack，然后 cp -R tstack/skills/* ~/.claude/skills/（Codex 换 ~/.codex/skills/）。没有依赖管理、没有构建、没有版本协商，拷过去就能用，改坏了直接删掉重来，成本是零。但要注意 README 里的依赖链：只装 full-send 会缺三个技能。

ruflo 走的是另一条路：npx ruflo@latest init wizard 初始化，或者 claude mcp add claude-flow -- npx ruflo@latest mcp start 把 MCP server 接进 Claude Code。它要求 Claude Code 2.1.287 或更高版本，安装时会把默认权限设成 read + ask，要放开得自己调。

我的判断表是这样的：

  • 只想要一套能跑的 PR 自动化手法——选 tstack。9 个说明书、1 个脚本，你可以逐行读完再决定用哪几个，council 和 sol-loop 的评分与预算规则写得很死，不存在黑箱。
  • 想要多 agent 团队、跨会话记忆、后台 worker、联邦通信——选 ruflo。这些能力 tstack 根本没有对应物，硬凑不出来。
  • 在意上下文成本和可审计性——先看 tstack。11 KB 的 sol-loop 说明书明确写着「第 1 轮全量、后面只查改动」，这是能自己算出来的账；ruflo 那 314 个 MCP 工具进上下文意味着另一笔开销，官方给的对策是 v3.71.0 那个自动委派机制，实测省 21.5% 输入 token，代价是耗时 +6.5%。
  • 要合规、要签名、要回归保护——看 ruflo 的 verification/ 目录（Ed25519 签名的 witness manifest）和 ADR 编号制度，它的每个插件能力都有对应 ADR 可查，这在 tstack 里完全不存在。

一个务实的提醒：两个仓库都自称支持 Codex，但 tstack 明确要求 council 与 sol-loop 能调度其他 provider 的模型——Claude Opus、GPT Sol、Gemini Pro 各一个。凑不齐三家它会报错而不是降级。这三个订阅是实打实的成本，不是可选项。

05 · 冷思考

58 KB 的手册和 648 MB 的运行时，不该用同一个尺子量

先质疑星标在这里的意义。tstack 2,600 星、14 次提交、1 个贡献者、最后一次 push 是 5 天前；ruflo 80,584 星、10,008 次提交、82 个贡献者、今天还在推。差 31 倍。但这两者根本不在同一个品类里竞争——tstack 不提供多 agent 编排，它提供九份写好的做法；ruflo 提供的是运行时，你是在用它的插件体系，不是读它的 README。用星标数给这两者排序，等于拿字数比论文和工具箱。

再质疑 ruflo 那五套并存的插件数。32、33+21、35、48、49——这不是笔误问题，是文档规模化的必然结果：plugins/ 每天都在加目录，市场文件每天都在改，而三份 README 是不同时间点、不同作者、不同目的写的快照。真正该被质疑的是，一个用「All 35 plugins」当折叠标题的仓库，读者凭什么相信它的任何其他数字——包括那个 89% 的路由准确率、314 个 MCP 工具。

那处性能矛盾最值得警惕。150x 到 12,500x 对 1.9x 到 4.7x，差了三个数量级，而且「12,500 倍」那个版本在插件文档里传播得更广，因为它更像一个卖点。主 README 的版本不仅给了数字，还给了审计文档链接、基准脚本路径，甚至老实交代了「小 N 会打平甚至更慢」。同一个仓库里，一个数字带证据链，另一个只有形容词。这不是能力问题，是文档纪律问题——而它恰好说明为什么「同一个项目的 README」不能当作单一事实源。

然后质疑 tstack 的隐忧。它停更 5 天，12 个 issue 无人接手，其中三个是真 bug：Windows 上跑不了 pr-wait、在没用 Greptile 或 Macroscope 的仓库里 babysit 永不结束、sol-loop 那一轮没有超时机制所以模型不收尾就会永远等着。还有一条 feat: publish skills as a Claude Code plugin marketplace 说明它连个规范安装路径都还没有，社区里已经有人在提了。一个人维护的手册，能读懂、能抄、能自己改，代价是所有环境适配都得你自己兜。

我的判断是这样的：如果你要的是「一套能立刻照做的 agent 手法」，tstack 的性价比是荒谬地高——16 个文件、不到 60 KB、十分钟读完、零依赖、随便改。它的真实使用门槛不在安装，而在「你得自己解决 Windows 和超时」这两件事上。

而 ruflo 真正值得抄的从来不是插件数量，也不是那 314 个工具。值得抄的是它的 ADR 编号制度和 Ed25519 签名的验证层——每个能力对应一份可追溯的决策记录，每处修复有见证清单，这是它敢在一个仓库里同时放 8,446 个文件而没塌掉的原因。反过来，它那五套并存的数字和那个 150 倍的说法，是庞大体量必然带来的税，用的时候记得自己回仓库数一遍。
