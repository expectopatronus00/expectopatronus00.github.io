46,542 星、1,329 插件：AstrBot 不担保第三方

46,542 星、3,447 个 fork。AstrBot 建于 2022 年 12 月 8 日，不是本周的新库。README 写「1000+ 插件一键安装」，市场接口此刻返回 1,329；主仓自带却只有 2 组，EULA 第 3 条写着：市场插件全是第三方，官方不审计、不背书、不担保。

01 · 这件事

一个 2022 年的老仓库，最近被写成了别人的替代

AstrBotDevs/AstrBot 建于 2022 年 12 月 8 日，到 2026 年 11 月 10 日核对时是 46,542 星、3,447 个 fork、1,185 个开放条目，订阅者 96；Python，AGPL-3.0，仓库 82,901 KB，主页 astrbot.app，最后一次 push 是 11 月 9 日 16:15 UTC。当前版本 v4.29.4，10 月 31 日发布。它不是本周冒出来的新星，而是快满四年的老项目——11 月 1 日进候选池时是 45,333 星，九天涨了 1,209 星，属于稳步增长，不是突然爆红。

仓库 description 里有一句挺新的话：「can be your openclaw alternative」。但 README 的功能清单讲的是另一件事：多平台 IM 接入、多模型服务、插件扩展、Agent 沙箱、WebUI、知识库、人格设定与自动上下文压缩。「替代某某」是后加的定位，代码里长出来的却是一套 IM 侧的 Agent 运行时，两件事不能混着读。

这次不测模型也不比体验，只把可核对的数字过一遍：README 说「1000+ plugins available for one-click installation」，徽章背后的市场接口返回多少；平台表里列了几个平台，仓库里真有几个适配器；那 1,185 个开放条目到底是什么。结论不在星数上，而在 EULA 的第 3 条。

02 · 核心机制

三层结构：入口适配、运行时、插件市场

从目录看，AstrBot 分三层。最底下是 astrbot/core/platform/sources/，每个子目录是一个 IM 平台的接入实现，负责把各家的消息格式、事件回调和登录态翻译成框架内部的统一事件；中间是 astrbot/core/ 下的会话、模型供应商、配置、上下文压缩与 Agent 沙箱；最上面是插件与技能生态，以及 Vue 写的 dashboard/ WebUI。它卖的不是「聊天机器人」，是把十几个 IM 变成同一个 Agent 的入口层。

能力清单也很清楚。README 列了 MCP、Skills、Knowledge Base、Persona Settings、Auto Context Compression，以及可隔离执行代码与 shell 调用的 Agent Sandbox；还支持接 Dify、阿里云百炼、Coze 等 LLMOps 平台。v4.29.4 的更新日志里，新增项包括跨平台消息按钮、独立于聊天模型的 Decision Provider、SerpApi Google News 网络搜索、会话来源统一选择，修复项里有上下文压缩设置简化与 WebUI 卡死问题。这些是运行时该管的事，不是一个转发 webhook 的脚本该管的事。

运行门槛写在 pyproject.toml：version = "4.29.4"、requires-python = ">=3.12"、license = { text = "AGPL-3.0-or-later" }，运行时依赖 66 条，其中 3 条带条件（按 Python 版本或 Windows 平台）。qq-botpy==1.2.1、dingtalk-stream、lark-oapi、slack-sdk、python-telegram-bot、wechatpy、py-cord 这些平台 SDK 被直接编进主依赖，多平台不是一句「支持」，是几十个 SDK 一起装进同一个进程。

03 · 关键细节与数据

1,329 个插件在主仓之外，18 对 18 也不是同一份名单

README 的插件数徽章指向 api.soulter.top/astrbot/plugin-num，核对时返回 {"result":1329}，所以「1000+」这句成立。但拉下完整 git tree（2,239 个条目、1,976 个文件、23,799,096 字节，未截断）后：astrbot/builtin_stars/ 下只有 astrbot 和 builtin_commands 两组内置插件，41 个文件、177,373 字节，其中 4 个 SKILL.md 分属 documents / pdf / skill-creator / spreadsheets。1,329 在主仓之外，仓库自带的只有 2 组。

更该读的是 EULA.md（13,427 字节，最后更新 2026-01-12）第 3 条：AstrBot 团队「不对任何第三方插件、扩展或服务进行审计、控制、背书或担保」，并且明确定义「插件市场中的插件都是第三方插件」，风险、数据泄露与法律后果由用户承担。「一键安装」是分发便利，「不担保」是责任边界，两句话都出自项目自己。同一份 EULA 还写明默认开启健康模式（在 cmd_config.json 里把 provider_settings.llm_safety_mode 设为 False 才关闭）、可用 ASTRBOT_DISABLE_METRICS=1 关掉匿名统计，并声明不收集对话内容与消息正文——这些是按自述引用，未做实测。

平台数也有口径差。README 的 Supported Messaging Platforms 表是 18 行：15 行标 Official（其中 WhatsApp 写着 Coming Soon），3 行标 Community（Matrix / Rocket.Chat / VoceChat，都链到外部插件仓库）。代码里 platform/sources/ 恰好也是 18 个一级目录，但两份 18 不是同一份：3 个社区平台的适配器不在主仓，只在 docs/ 与 dashboard 的 logo 里留下痕迹；WhatsApp 没有任何源码，与 Coming Soon 一致；webchat 是自带 Web 聊天，不在表格里；反过来 QQ 有 qqofficial 与 qqofficial_webhook、企业微信有 wecom 与 wecom_ai_bot、微信侧有 weixin_oc 与 weixin_official_account 各两套实现。表格数的是「平台」，目录数的是「接入实现」。

适配器共 74 个 Python 文件、1,195,948 字节，而整个仓库有 839 个 Python 文件、9,847,364 字节——按文件数占 8.8%，按字节占 12.1%。wecom_ai_bot 一个目录 12 个文件，aiocqhttp、telegram、satori、weixin_official_account 各只有 2 个。README 另一张 Supported Model Services 表 35 行：18 行 LLM 服务（含 2 个标注 API Gateway 的中转）、3 行 LLMOps 平台、3 行语音转写、11 行语音合成。接得多的地方是模型入口和语音输出，不是每个 IM 都做到同等深度。

还有一处容易被误读：GitHub 接口的 open_issues_count = 1185 常被当成「1,185 个 bug」。用 search 接口拆开是 749 个 open issue 加 436 个 open PR，正好 1,185。v4.29.4 的日志里 PR 编号已到 #10902，而 11 月 10 日新开的 PR 是 #11070。仓库另有 297 个 docs 文件、279 个 tests 文件、214 份 changelogs、7 种语言的 README 和 4 份多语言首次启动提示。这是一个工程化维护中的项目，不是一个只有 README 的展示仓。

04 · 怎么用

先选部署路径，再决定要不要开插件市场

README 给了五条路。最短的是 uv：uv tool install astrbot --python 3.12 → 首次执行 astrbot init → astrbot run，升级用 uv tool upgrade astrbot --python 3.12；Docker / Docker Compose 走官方文档；桌面用户有 AstrBot App 与 Launcher；不想管服务器可用雨云一键部署；面板党还有宝塔、1Panel、CasaOS 与源码部署。Python 3.12 是硬门槛，pyproject.toml 与 README 的安装命令一致（顺带一提，ruff 与 pyright 的配置里仍写着 3.10，属于工具配置滞后，别拿它判断运行时版本）。

接平台前先看清实现名。QQ 对应 aiocqhttp（OneBot v11 协议）与 qqofficial 两套，企业微信有普通机器人与 AI Bot 两套，微信公众号也是两套目录；社区平台 Matrix、Rocket.Chat、VoceChat 要额外装外部适配器，WhatsApp 还没实现。照 README 表格勾平台，和照 platform/sources/ 目录勾平台，得到的清单并不一样。

插件这一步值得多花两分钟。市场里的 1,329 个都是第三方插件，EULA 明说团队不审计、不背书；Agent Sandbox 提供代码与 shell 的隔离执行，但那是运行时的隔离，不等于插件来源可信。「一键安装」省的是依赖操作，没省掉读权限、看仓库、看更新记录。真要长期跑，优先用主仓内置的 2 组插件打底，第三方插件按最小必要装，并把 ASTRBOT_DISABLE_METRICS=1 之类的开关按自己的隐私口径设好。

授权要单独算账。LICENSE 是 34,500 字节的 AGPL-3.0 全文，另有 13,427 字节的 EULA.md 单独成文，第 11 条在 AGPL 之外又约定了「非独占、不可转让、不可再许可」的使用许可，第 1 条强调项目未开展商业化服务。做二次分发或对外提供服务前，两份文件都要读，不能只看 SPDX 那一行。

05 · 冷思考

把「能接多少」和「谁负责」分开算

先质疑那个最顺手的数字。1,329 个插件、18 个平台、35 行模型服务，都能核到，README 没虚报；但前两个数字的口径都需要补一句：插件在主仓外、平台表里混了 Coming Soon 与社区外置，而 EULA 第 3 条把第三方插件的责任完整留给了使用者。便利被写进第一屏，边界被写进一份很少有人点开的 EULA。这不是欺骗，但传播时天然不对称。

再质疑「替代某某」这个标签。仓库建于 2022 年 12 月，AGPL-3.0，EULA 最后更新是 2026 年 1 月，版本已经走到 4.29.4，PR 编号过万，749 个未关闭 issue 配 436 个未合并 PR。这是一个有四年历史包袱、维护面很宽的项目，不是为新范式从零写的轻量工具；把它当成刚出现的平替，会低估部署和升级成本，也会高估它与新范式在架构上的相似度。

还有一处口径值得说明。EULA 说团队未提供收费服务，而 README 里确实有 3 条带推广参数的第三方链接（雨云一键部署、CompShare 的 referral_code、302.AI 的邀请链接），模型服务表里也有多家 API 中转商。两者不矛盾——收费方是第三方，不是项目团队——但「免费开源」容易被读成整条链路都没有商业利益。模型调用费、云主机费、中转服务费，一样都不会因为 AGPL 而消失。

所以判断落在用途上，不落在 46,542 星上。如果你要把 QQ、企业微信、飞书、Telegram 等多个 IM 收成同一个 Agent 入口，愿意维护 Python 3.12 环境、自己审第三方插件，它是少有的把 18 个接入实现、沙箱、上下文压缩和 WebUI 放在一个仓库里且持续迭代的选择；如果你只接一个平台、要的是开箱即审计的插件集，或者打算做闭源商用，66 条运行时依赖、AGPL 加 EULA 双文件、以及那句「不担保」都是多余的负担。决定结果的是你愿意替多少个第三方组件负责，不是市场里有多少个插件。
