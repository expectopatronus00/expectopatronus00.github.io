187 星对 201 星：一个记人设，一个记事实何时为真

187 星、2 fork 与 201 星、5 fork，两个仓库都建于 10 月底：一个把人设与关系做成可替换人格卡，一个给每条事实挂有效时间与记录时间两条轴。一个记它是谁，一个记何时为真，数据模型与失效场景都不同，按星选就错了。

expectopatronus 2026-11-08 约 10 分钟阅读 原创 · AI 编程
01 · 这件事

两个都叫 agent memory，存进库的却是两种东西

tavern-labs-ai/persona-ai-sdk 2026 年 10 月 31 日建库，到 2026 年 11 月 8 日是 187 星、2 个 fork，MIT，TypeScript，仓库 217 KB，最后一次 push 停在 11 月 2 日。description 只有一句：默认人格、持久角色记忆、Bedrock / OpenAI 适配打成一个包；npm 发布名 ai-persona-sdk 与仓库名不同。另一个是 gh9ko8y/graphmemory，早一天建库，10 月 30 日，201 星、5 个 fork，同样 MIT，Python，7480 KB，push 停在发布当天。description 长得多：双时态 AI 记忆系统，六变量衰减、时间分级召回、TTL 到期、去重、竞争检索，底下压着 Neo4j、PostgreSQL 与 Redis。

两个仓库差 14 星，建库只差一天，体量差了三十多倍，但真正要命的差别不在这些数上。它们要存的根本不是同一件东西：一个存「这个角色是谁、和用户处到了哪一步」，一个存「某条事实在什么时间成立、后来被改成什么」。11 月 6 日那篇讲上下文压缩发生在哪一层，这篇不碰那个框架，只看记忆落库后的结构与时间语义。

两条同属 agent-memory 一族，积压 78 分与 77 分，是一次消耗两条的横评。下面按数据模型、召回、失效三条线拆开，最后给选 A 还是选 B 的判断，README 里的变量与阈值只按作者自述引用。

02 · 核心机制

人设是会被覆盖的记录，事实是带两条时间轴的账本

persona-ai-sdk 的最小单位是人设卡。personas/ 目录下 8 个 json，atlas、sage、vera、scout、wren、ember、lumen、mica 各一张，字段按 README 是 systemPrompt、traits、greeting、memorySeeds。README 把 SDK 拆成 Personas / Memory / Model / Persistence / Interface 五层，五层可替换；卡是产品默认值，应用要把它映射成自己的 persona manifest，其中 relationships 写死 stranger / acquaintance / trusted 三段，默认从 stranger 起。它存的是身份：一份提示词、一组特质、一句开场白，和随交互推进的关系刻度。

召回和写入的路径写在 ARCHITECTURE.md 里。写入是 normalize → provider extraction → 校验 schema 与源消息 provenance → 丢弃低置信候选 → consolidation，默认策略会合并语义重复、supersede 可变状态、把矛盾抛给调用方。召回反过来：可选 query embedding，先过 scope 与 identity 过滤，再按 semantic、lexical、importance、recency 四路打分，接着 expiry filtering，最后按 token 预算打包成一段「明确不可信」的上下文，渲染时标成 recollection 而不是 instruction。也就是说，人设记忆的更新方式是覆盖：关系推进到 trusted，旧的 stranger 就被顶掉，系统不承诺留一份旧版本。

graphmemory 反过来，最小单位是一条挂了时间的事实。README 自述每条事实同时有 valid_from / valid_until 这条有效时间（事情在现实里何时为真）和 tx time 这条记录时间（系统何时写入），能分别回答「当时是什么」和「后来改了什么」；episodes 原文账本只追加不更新。事实状态放 PostgreSQL 的 fact_state，关系边放 Neo4j 的 RELATES_TO 与 MENTIONS，Redis 只做读路径缓存。src/graphmemory/recall/ 目录里确有 11 个 py 与之对应：decay.py、validity.py、time_gradient.py、competitive.py、temporal_age.py 等——文件名对得上自述，公式是否生效是另一回事。

它的召回围着时间设计。README 自述的竞争检索是「激活 × 匹配 × 资源适配 → θ 相对阈值 → Top-K」，命中反过来巩固记忆；时间梯度列了 1 天到 1 年十档，越久 D（细节）上限越低、R（检索难度）下限越高。失效走的是降级而不是删除：六变量 S / D / R / E / C / I 控制衰减，TTL 按内容分类（临时状态 1 天、事件 7 天、普通事实 14 天、偏好永久、身份 3 年），到期先隐藏、宽限 1 天再物理删，episodes 原文账本永久保留。以上出自 README 与 DESIGN_ZH.md，是作者自述，不是本文实测。

03 · 关键细节与数据

差别最硬的一处：一个覆盖旧状态，一个给旧状态留原文

先把能对着目录数出来的东西摆齐。persona-ai-sdk 的 README 15239 字节、ARCHITECTURE.md 5614 字节，docs/ 下 7 篇、src/ 下 7 个子目录，personas/ 8 个 json 与 README 的「8 personas」徽章对得上。graphmemory 的 README 8106 字节、API.md 12336 字节、mcp_server.py 27734 字节、docs/DESIGN_ZH.md 28853 字节，scripts/ 6 个、docs/ 6 个，recall/ 下 11 个 py，其中 repository.py 18,818、competitive.py 11,961 字节等。这些字节数是目录接口给出来的，机制描述则来自仓库自己的文档，两件事要分开看。

三条线对齐之后，差别就清楚了。数据模型上，A 存「角色属性 + 关系阶段 + 带来源的记忆记录」，B 存「事实 + 两个时间轴 + 只追加的原文」。召回上，A 是四路打分加 token 预算打包，取此刻最该塞进 prompt 的几段；B 是相对阈值加时间梯度，取在这个时间点仍成立且被激活的事实。失效上，A 靠 consolidation 覆盖可变状态，B 靠 TTL 隐藏、六变量降级、memory_forget 打墓碑，但原文账本不删。

于是两者的失效场景几乎互补。用 A，你要担心的不是「记不记得」，而是「被改成了什么」：关系阶段一推进，旧阶段被 supersede；同一件事说两次，语义重复被合并；一轮对话太长，召回块被 token 预算裁掉。用 B，你要担心的是「现在还看不看得到」：一条事实 TTL 到期先隐藏，六变量衰减把 D 压低、把 R 抬高，它在当前视图里越来越难被激活，可 get_timeline 和 episodes 仍能把当时原话翻出来。A 不承诺历史版本，B 不承诺当前可见——这不是实现好坏，是两种记忆各自要保的东西不同。

还有一处口径必须写明。六变量衰减、双时态、十档时间梯度、θ 竞争检索，在 README 和 DESIGN_ZH.md 里都有段落、在 recall/ 里都有对应文件，但仓库没给权重复现脚本、没给衰减曲线的数据集；scripts/ 那 6 个文件是 init_db.sql、verify_chat_memory.py 一类的建表与冒烟脚本。本文没有执行 docker compose up -d，没有跑 pytest，没有复现任何召回率。凡涉及「效果」的句子，一律按作者自述读。

04 · 怎么用

一条 npm install 对三个容器，先算你要付的是哪种成本

A 的起步几乎零运维：npm install ai-persona-sdk，源码检出则是 npm install 加 npm run build，要求 Node.js ≥ 20，另需 OpenAI API key 或带 Bedrock 权限的 AWS 凭据；用 SQLite 适配器才要装 better-sqlite3。代码里先 getPersona("atlas")，再用 createCharacterMemoryRuntime({ extractor, embeddings, store }) 装配记忆运行时，store 可选 InMemory、JsonFile 或 SQLite，然后 createPersonaRuntime 接上 runtime.respond({ conversationId, message })。一次 respond 顺带完成召回、生成、回合写入与关系状态推进，response.trace 里带着 recalled memory IDs。

B 的起步是另一量级。README 要求 Python ≥ 3.10 与 Docker Compose，顺序是 cp .env.example .env 填好密码与 LLM key、docker compose up -d 起 Neo4j / PostgreSQL / Redis，再 python -m venv .venv && . .venv/bin/activate、pip install -e .、psql ... -f scripts/init_db.sql 建表，最后 uvicorn graphmemory.main:app --host 127.0.0.1 --port 8000。写入与检索是 curl -s -X POST localhost:8000/api/v1/memory/add 和 /search，手动跑一轮衰减是 /decay；接 agent 走 mcp_server.py 的 stdio MCP，配 GRAPHMEMORY_BASE_URL 与 GRAPHMEMORY_AGENT_ID。

成本差别里藏着最容易踩空的一处：graphmemory 的 README 有一节明确写「未包含」，把桌面小组件、QQ / NapCat 等 IM 适配（含「每轮自动记忆注入」钩子）、私有提示词 / 人设都划在仓库之外。也就是说 B 根本不替你管人设，也不替你把记忆塞回每一轮对话，那层胶水要自己写。A 恰好相反，人设卡和交付元数据是包里自带的，但记忆能不能跨会话留住，全看你选哪档 store、给不给 provider 凭据。

判断表如下，A 是 persona-ai-sdk，B 是 graphmemory：

  • 要角色长期不崩人设、记住和用户处到哪一步（客服、陪伴、游戏 NPC、固定品牌口吻）——选 A。人格卡、memorySeeds、三段关系状态就是为身份连续性做的；代价是接受「旧状态会被 supersede」这套覆盖语义。
  • 要回答「这条事实当时成立吗、后来改了没」——选 B。双时态是这里唯一把有效时间与记录时间拆成两个字段的数据模型，episodes 只追加账本还能回溯原话；代价是那套衰减与召回只是作者自述。
  • 只能起一个进程、不想运维数据库——选 A，In-memory 或 Atomic JSON 就够用。B 的 quick start 直接写进 Neo4j + PostgreSQL + Redis 三件套，还要填 LLM key 才抽得出事实。
  • 数据要按时间审计、要跨年级的「当时 / 现在」两套口径——选 B。TTL 分级与十档时间梯度是为这种场景设计的；代价是 Python ≥ 3.10 与 Docker Compose。
  • 身份和事实都要记——两个可以叠：A 写 character state、B 写 fact_state，不冲突。但别指望自动打通，B 明说人设与每轮注入钩子不在仓库里。只想要方法论就都别装，读 A 的 ARCHITECTURE.md 和 B 的 DESIGN_ZH.md 比养三容器便宜。

一个务实提醒：两边都不承诺开箱即用。A 的 README 徽章 alt 写 1.0.2、徽章图却是 1.0.3；getPersona 遇到未知 ID 会回落到 Atlas 而不报错——写错角色 ID 不会失败，只会换一个角色继续聊。装之前先按 /contents 对一遍文件。

05 · 冷思考

8 天攒 200 星、零 issue，量不出「记对没记对」

先质疑星标。两个仓库都建在 2026 年 10 月 30 / 31 日，到核对日不满两周，187 星配 0 订阅者、0 未关闭 issue，201 星也是 0 订阅、0 未关闭 issue，fork 分别只有 2 和 5。这个分布更像发布期的一次曝光，不是生产环境跑出来的验证。B 的 pushed_at 停在发布当天 14:00，比 created_at 只晚约一小时，updated_at 却到了 11 月 7 日——一个自称带后台衰减与 TTL 清理循环的系统，源码停在首次提交那一刻，此后动的是元数据。

再质疑文档本身。DESIGN_ZH.md 有 28853 字节，写着五命题两坑、44 个测试、桌面悬浮球、start.ps1 与三容器架构图。可 api.github.com 列出来的根目录只有 11 项，tests/、ball.py、那份 ARCHITECTURE.md 都不在；文档开头自己注明「原始设计 / 开发记录，保留其推导过程供参考」，README 的「未包含」一节又把桌面小组件、IM 适配（含每轮自动记忆注入钩子）、私有人设划到仓库外。演示视频 67 秒里最像「有记忆」的那一下自动注入，恰恰是 clone 下来拿不到的。引用阈值前，先分清哪句写的是当前代码、哪句是当时的设想。

第三处质疑是那些自述机制没有可复核的分母。六变量 S / D / R / E / C / I 各占多少权重、θ 怎么定、十档时间梯度的边界由谁校准，README 只给公式和档位，没给数据集、没给对照实验；「遗忘是降级不是删除」是设计选择，不是被测量过的效果。A 那边四路打分怎么加权、token 预算裁掉多少 recall 才不伤角色一致性，ARCHITECTURE.md 也没给数字。两边都把机制写得比证据详细。

第四处是「二选一」这个问法本身。A 的 8 张卡被 README 定性为「product defaults rather than canonical memory records」，B 明说人设不在仓库里——一个把人设做成包内默认值，一个推给部署侧。硬问「哪个记忆更强」，等于拿角色一致性和时间可回溯性比大小，没有共同分母。

所以判断不落在哪个星多。存身份，就接受 A 那套可覆盖、按预算打包、随时可能被 supersede 的记录，它不承诺历史版本，换来一条 npm install 就能起步的轻量；存命题，就接受 B 那套双时态账本、十档时间梯度和三个容器，换来「当时说了什么」随时可翻，代价是人设和每轮注入的胶水自己写。最不该做的是把「它记得我是谁」和「它记得这件事哪天成立」并成一个指标去打分。如果只做一件事，我会在写入事实那一刻强制带上「这条是什么时候知道的」——这个字段两边都替不了你判断，缺了它，再精巧的衰减模型也只是把一段没有时间的信息存得更久一点。
