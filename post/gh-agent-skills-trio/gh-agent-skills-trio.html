SKILL · 开源项目

188344星最小规范、313835星完整方法论：按层选

313,835 星、27,919 fork，superpowers 最热却非最该先装。官方 skills 仓 188,344 星、spec 87 字节；游戏工作室仓 36,301 星、49 agent 全套编排。三种粒度，按改写哪层选。

01 · 这件事

三个仓库都在给编码 agent 装工作方法，给的却是三种粒度

anthropics/skills 2025 年 9 月 22 日建库，到 2026 年 11 月 7 日是 188,344 星、22,213 个 fork、1,149 个订阅者、1,488 个未关闭 issue，Python，5,502 KB，最后一次 push 在 11 月 6 日 22 点 32 分。它的 description 只有一句：Public repository for Agent Skills。全仓只挂了一个 topic，agent-skills。

obra/superpowers 晚半个月，2025 年 10 月 9 日建库，313,835 星、27,919 个 fork、1,141 个订阅者、342 个未关闭 issue，MIT，Shell，8,099 KB，11 月 3 日 23 点 24 分最后 push。description 把话说得更满：An agentic skills framework & software development methodology that works——一套能用的框架加开发方法论。

第三个最晚也最小。Donchitos/Claude-Code-Game-Studios 2026 年 2 月 12 日建库，36,301 星、4,779 个 fork、247 个订阅者、94 个未关闭 issue，MIT，Shell，4,406 KB，最后一次 push 停在 10 月 19 日，是三者里唯一超过半个月没动的。description 自述 49 AI agents, 72 workflow skills，说是把 Claude Code 变成一整个游戏工作室。

三条都在积压队列的 agent-skills 一族，评分 92、90、88，所以这篇是横评，一次消耗三条。但把仓库数完会发现，它们卖的根本不是同一种东西：一个给最小可读规范，一个给完整方法论，一个给垂直场景的全套编排。粒度的差别，最终会落到「装了之后 agent 到底哪里变了」这句话上。

02 · 核心机制

一个规定文件格式，一个改写流程，一个替换组织

anthropics/skills 把「一个 skill 是什么」压到了最小。template/SKILL.md 只有 140 字节：YAML frontmatter 里 name 和 description 两行，正文一行 # Insert instructions below。spec/agent-skills-spec.md 更短，87 字节，内容只是一句「规范已搬到 agentskills.io/specification」。README 的定义也克制：skill 是「文件夹加指令、脚本、资源」，Claude 按 description 动态决定何时加载，每个技能自成一个目录、里面放一份 SKILL.md。它规定的是文件长什么样，不是 agent 该怎么干活。

所以装 A 之后，agent 的默认行为几乎没变。README 给的做法是 /plugin install document-skills@anthropic-agent-skills，装完「提一下就触发」——你问「用 PDF skill 抽出表单字段」，它才去读那份 SKILL.md。更值得注意的是 Disclaimer：这些技能「仅供演示与教育」，「你在 Claude 里拿到的实现和行为可能与示例不同」，关键任务务必自行测试。官方自己没把这套东西当成生产方法论。

superpowers 反过来，它管的正是「agent 该怎么干活」。README 第一句就说它建在「一组可组合的 skills」加「一些确保 agent 真的会用它们的初始指令」之上，hooks/session-start 那份 4,421 字节的脚本从会话一开始就注入。skills/ 下 15 个目录没有一个是领域知识，全是流程：brainstorming、writing-plans、test-driven-development、systematic-debugging、subagent-driven-development、verification-before-completion。装了之后行为是按 README 那四步被强制改写的：看到你要做东西，它不直接写代码，先退一步问清目标；把 spec 从对话里抠出来分块给你签；签完才生成一份细到「没品味、没判断力、讨厌测试的初级工程师」也能照做的实施计划，强调红绿 TDD、YAGNI、DRY；你说 go，才启动子 agent 逐项执行、自查、review，能连着自主跑几个小时不偏计划。它把「先想清楚再动手」写成了一条 agent 必须走完的状态机。

Claude-Code-Game-Studios 改的是更上一层：组织形式。.claude/agents/ 实测 49 个 .md 定义文件，按 README 的说法分导演、部门主管、专家三层，各有职责、升级路径和质量门；.claude/hooks/ 配套的 15 个 hook 在每次会话自动跑提交、推送、读写、资源与注册表的校验；settings.json 8,361 字节里写了权限规则，自动放行测试、拦住 force push、rm -rf 和读 .env；74 个 slash command 从 /start、/setup-engine 到 /dev-story、/qa-plan 排成一整套。它替换的不是 agent 的知识，是把一个通用助手换成了有层级、有审批、有强制校验的工作室。

把三个摆成一条轴就清楚了：A 只给文件格式，agent 想用才读；B 给流程约束，agent 一开机就得照走；C 给组织编排，连「谁能改什么」都替你定好了。粒度越粗，默认行为被改写越多，能搬到你别的项目里的部分就越少。

03 · 关键细节与数据

188,344 星的那个最薄，36,301 星的那个最厚

先把三组的硬数字摊平。anthropics/skills：188,344 星、22,213 fork、1,149 订阅、1,488 未关闭 issue、2025-09-22 建库、2026-11-06 22:32 最后 push、API 的 license 字段为 null、Python、5,502 KB、topics 1 个。obra/superpowers：313,835 星、27,919 fork、1,141 订阅、342 未关闭 issue、2025-10-09 建库、2026-11-03 23:24 最后 push、MIT、Shell、8,099 KB、topics 8 个。Donchitos/Claude-Code-Game-Studios：36,301 星、4,779 fork、247 订阅、94 未关闭 issue、2026-02-12 建库、2026-10-19 最后 push、MIT、Shell、4,406 KB、topics 12 个。三者 default_branch 都是 main，homepage 都为空。

再看「厚度」和星标完全不成正比。A 的 skills/ 下是 19 个示例技能目录（doc-coauthoring、mcp-builder、skill-creator、pdf、pptx、xlsx 这类），规范 87 字节、模板 140 字节，全仓 5,502 KB；B 是 15 个流程 skill、hooks/ 4 个文件（hooks.json 424 字节、session-start 4,421 字节、run-hook.cmd 3,577 字节、hooks-cursor.json 137 字节）、根目录 11 个宿主适配目录，8,099 KB；C 是 .claude/agents/ 49 个定义文件、.claude/skills/ 74 个目录、README 徽章写 15 hooks / 14 rules，却只有 4,406 KB，是三者里体积最小、编排最密的一个。星最多、体积最小的官方仓，恰恰是装了之后改变最少的那个。

有两处口径必须挑明。第一处是 C 的技能数：API 的 description 自述 72 workflow skills，README 顶部却写「49 agents. 74 skills.」、徽章也标 74，而 .claude/skills/ 目录实测正是 74 个。同一个仓库，三处数字里两处是 74、一处还停在 72，说明 description 没跟着仓库一起改。第二处是 A 的许可证：GitHub API 给 anthropics/skills 的 license 是 null，README 只说「仓里很多技能是 Apache 2.0」，另配了一份 46,162 字节的 THIRD_PARTY_NOTICES.md。抄进闭源产品前，得逐目录确认，而不是看仓库顶上一个协议。

最后是热度口径。选题池的 Trending 周榜给 C 标了本周增 6,018 星、给 A 标了 3,159 星；但 GitHub API 没有「本周新增星」这个字段，这两个数无法从仓库或接口复核，本文只当作选题时的热度标注，不进任何实测结论。B 甚至没进这周的增量榜，星标却是三者里最高的 313,835。

04 · 怎么用

先决定要改写到哪一层，再选安装命令

A 最轻。Claude Code 里 /plugin marketplace add anthropics/skills 注册市场，再 /plugin install document-skills@anthropic-agent-skills 或 /plugin install example-skills@anthropic-agent-skills 装其中一组；装完不用配置，提到就触发。它的正确用法其实偏「读」：照 template/SKILL.md 写自己的第一份 SKILL.md，或翻 skills/ 下 19 个样本找写法，而不是指望它替你管项目。

B 按宿主分别装。Claude Code 走 /plugin install superpowers@claude-plugins-official，或 /plugin marketplace add obra/superpowers-marketplace 后 /plugin install superpowers@superpowers-marketplace；Antigravity 是 agy plugin install https://github.com/obra/superpowers。README 明说「多宿主要分别安装」，根目录那 11 个适配目录就是代价。装完 session-start 生效，下一次会话它就会先问你目标而不是先写代码。

C 不是插件，是项目模板。git clone https://github.com/Donchitos/Claude-Code-Game-Studios.git my-game，然后必须在项目根目录打开 Claude Code——在 src/ 这类子目录启动会跳过 hooks。依赖 Python 3（读 project.yaml）、Bash（跑 hooks，Windows 靠 Git for Windows）、Node.js 22+ 的 npm install -g @anthropic-ai/claude-code，jq 可选；自动化分 minimal / guided / autonomous 三档。

判断表如下，A 是 anthropics/skills，B 是 obra/superpowers，C 是 Claude-Code-Game-Studios：

  • 只想搞懂 skill 是什么、写一份自己的 SKILL.md，或给团队定一个最小文件规范——选 A。87 字节的规范加 140 字节的模板就是全部，装完不绑架 agent 的默认行为；代价是 README 自己声明仅供演示，别拿它当生产流程。
  • 想让 agent 每次开工都先澄清需求、写计划、走红绿 TDD、完成前自查——选 B。它是三者里唯一把「先想清楚再动手」做成强制状态的，15 个 skill 全是流程；代价是改一行 bug 也得走一遍流程，且每个宿主都要单独装。
  • 在做游戏、需要导演/主管/专家分工、质量门和提交前强制校验——选 C。49 个角色、15 个 hook、74 条命令、权限规则一起给全，是唯一交付「组织」的；代价是只服务 Claude Code 这一个宿主、只在游戏这一条场景里自洽。
  • 只想要规范又想要流程——A 和 B 可以叠：用 A 的模板写自定义 skill，交给 B 的 session-start 去触发。C 则别叠加，它自带一整套 rules 和 settings.json，混进来只会两套规则打架。反过来，三者都别装的情形也存在：你只需要读 A 的 spec 和 B 的 writing-skills，把方法抄进自己的 AGENTS.md，比养 hook 和 49 个角色便宜。

一个务实提醒：三者都不改模型，改的是模型开机时读到的那摞文本。A 是 140 字节的模板，B 是会话开始注入的初始指令，C 是 8,361 字节的 settings.json 加 15 个常驻 hook。装得越重，故障面越大：C 少装 Python 或 jq，README 说 hooks 会「优雅降级」，但你就失去了校验。

05 · 冷思考

188,344 星量的是谁在定义这个词，不是装了之后改变多少

先质疑星标。三者 313,835 / 188,344 / 36,301 星，差距近一个数量级，可订阅率几乎贴在一起：superpowers 1,141 除以 313,835 约 0.36%，anthropics/skills 1,149 除以 188,344 约 0.61%，Claude-Code-Game-Studios 247 除以 36,301 约 0.68%。三边都是「先收藏」的量级，官方仓赢在名字和分发，不赢在机制。更直白的反差是：星最多的 anthropics/skills，README 自己写着「仅供演示与教育」「实际行为可能不同」，是三者里最不打算改变你 agent 的一个。把 18 万星读成「官方方法论最值得装」，正好读反了。

再质疑「装了之后行为变了」这件事本身。A 几乎不变，连官方都不保证一致；B 把 brainstorm、签 spec、写 plan、红绿 TDD、子 agent 执行变成一条不能跳的状态机，README 得意地说 agent 能「自主跑几个小时不偏计划」，可反过来，偏不了计划也意味着临场改主意变难；C 更彻底，49 个角色、15 个 hook、权限规则一起接管，连 git commit -m "push + pull" 这种提交信息都会被规则拦下。粒度越粗，agent 越听话，你越难绕开它。C 的 README 甚至专门留了一章「Does it produce games, or documents?」——把工作室流程铺满之后，产出的是游戏还是一堆设计文档，作者自己都得出来答辩。

第三处质疑在自述的可靠性。C 的 description 写 72、README 写 74、目录实测 74，一个仓库里三个口径对不齐；A 的 API license 是 null，只有「很多技能是 Apache 2.0」这种模糊说法，配 46,162 字节的第三方声明文件；所谓「本周增 6,018 / 3,159 星」只来自选题池周榜，API 根本没有周增字段。这些数字没有一个是这次实测出来的，把它们当硬指标排序，等于拿标注当测量。唯一能站稳的，是 stars、forks、created_at 这类接口直接给的字段，和 /contents/ 数出来的 49、74、19、15。

第四处是「不装配套工具会怎样」。B 的 session-start 不注入、C 的 Python 3 或 Bash 缺一样，前者就退回普通 agent、后者 hooks 直接降级；A 更干脆，它本来就只是几份能读的 Markdown。三个仓库真正交付的都是文本，不是运行时，行为的改变全靠宿主愿不愿意在开机时把它们读进去。换一个不认这套 hook 或插件市场的宿主，重装一遍是小事，规则根本不生效才是常态。

所以判断不是「哪个星多装哪个」，而是「你肯把 agent 的默认行为交出去多少」。只想统一文件格式、别的一概不动，选 A；肯把开工流程交给一套强制方法论，选 B；本来就在一个明确场景里、连组织分工都想一并接管，选 C。最该先做的不是装，是先写清楚你要 agent 改的是哪一层：改文件层就用 140 字节的模板，改流程层才上 session-start，改组织层再接受 49 个角色——顺序反了，你会先花一小时配 hook，再发现要的只是一份能照抄的 SKILL.md。
