12,405 星、三个命令：简洁的代价是七成测试

12,405 星，1,829 个文件里 1,283 个在 tests/。Worktrunk 把 git worktree 收成三个命令，让多个 AI agent 并行改代码。但完整树说明：简洁是界面，复杂度留在快照与 Breaking 里。

01 · 这件事

12,405 星，一个把 worktree 当分支用的 CLI

Worktrunk 卖的不是新能力，是把 git 自带的 worktree 命令变短。仓库 2025-10-17 创建，2026-11-11 核对时 12,405 星、488 fork，主语言 Rust，最近一次推送在 11-10。

它面向的场景很具体：Claude Code、Codex 这类 agent 能长时间无人值守跑任务，README 说一个人可以同时管 5 到 10 个以上。git 的 worktree 给每个 agent 一个独立目录，彼此不覆盖改动。

原生命令的问题是要把分支名打三遍。先执行 git worktree add -b feat ../repo.feat，再切目录，两步都带着同一个名字。

Worktrunk 把这一串收成 wt switch feat，目录路径由模板算出来，人只记分支名。

02 · 核心机制

按分支名寻址，路径不再由人记

整套设计只有一个支点：worktree 用分支名寻址，物理路径由配置模板生成。接受分支名的命令也接受该 worktree 所在的路径，人不用记目录在哪。

README 把四个高频动作和原生 git 做了对照，这里照搬成表。注意「新建并启动 Claude」在原生 git 里是三步，Worktrunk 用 -x 把启动命令挂在切换之后。

任务Worktrunk原生 git
切换 worktreewt switch featcd ../repo.feat
新建并启动 Claudewt switch -c -x claude featworktree add、cd、claude 三步
清理wt removeworktree remove、branch -d 两步
带状态列出wt listgit worktree list（只有路径）

再往上是可选层，README 列了十项。它们共享同一个思路：把「多个 agent 同时改代码」派生出来的杂活收进 wt 的子命令，而不是让人自己写脚本串。

  • hooks：创建、合并前后跑命令，可装依赖、起服务
  • LLM 提交信息：按 diff 生成 commit message
  • 交互式 picker：带 CI 状态与 diff、log、PR 预览
  • PR 直达：wt switch pr:123 跳到对应分支
  • 分端口：hash_port 给每个 worktree 一个唯一端口

其中最能省时间的是复制忽略文件，对应 wt step copy-ignored。它让十个 worktree 共用构建缓存目录 target 与 node_modules，不必重新构建。

这个能力有文件系统门槛：只在 APFS、btrfs、XFS 上成立，Windows 的 NTFS 不在名单里。

还有个前置条件容易被跳过：命令要能改变当前目录，必须装 shell 集成。安装说明里 wt config shell install 和主程序是并列的一步，不是可选项。

04 · 怎么用

先装 shell 集成，再决定要不要上 hooks

最短路径是安装、集成、三个命令，其余都按需再加。发布页给了 18 个资产，其中 5 个是平台二进制包，覆盖 macOS 两种架构、Windows x64、Linux 两种 musl 架构。

渠道命令适用
Homebrewbrew install worktrunkmacOS / Linux
Cargocargo install worktrunk需 Rust 1.98 起
Wingetwinget install max-sixty.worktrunkWindows
必做一步wt config shell install命令才能切换目录

Windows 有个命名坑：wt 默认是 Windows Terminal 的命令，所以 Winget 额外装成 git-wt，集成也要用这个名字，或者去系统设置里关掉终端别名。

并行 agent 的写法是每行一个任务，-x 后跟要启动的程序，-- 后面是传给它的提示词。README 给了三条并列示例：加认证、修分页 bug、补 API 测试。

  • 建 worktree 并切过去：wt switch --create feature-auth
  • 看所有工作区状态：wt list
  • 本地合并并清理：wt merge main
  • 完成后删除：wt remove

并行开三个 agent 时，README 的写法是三行 wt switch -x claude -c <分支> -- '<提示词>'，每条建一个独立 worktree 并把提示词透传进去。目录隔离由 git 保证，Worktrunk 只负责把这三行变短。

先别急着配 hooks。它是可选层，且 v0.81.0 刚改了前台 hook 的输入方式；先把三个命令跑顺，再按文档加 post-start hooks 去装依赖、起服务。

还有一个容易误判的点：wt list 默认表格里的符号是状态压缩，--full 才展开每分支的 CI 状态与 AI 摘要。第一次用不要把隐藏列当成数据缺失。

05 · 冷思考

0.81 还没到 1.0，简洁的账单在升级里

这个工具最该问的不是好不好用，而是跟不跟得上。154 个 tag 从 0.1.0 排到 v0.81.0，最新一版发布说明 19,761 字符，里面出现 13 处 Breaking、挂了 92 个 PR 链接。

一版里改了 hook 的 stdin 约定、模板引擎换到 MiniJinja 3、系统配置路径每平台只认一个、Nushell 集成要求 0.113 以上。把 hooks 写进团队脚本的人，每次升级都得重新验一遍。

贡献者结构也值得看。88 位贡献者合计 5,420 次提交，作者 max-sixty 一人 4,132 次，占 76.2%；机器人账号 1,169 次，占 21.6%；前三名合占 97.5%。

  • 作者本人：4,132 次提交，76.2%
  • 机器人账号：1,169 次，21.6%
  • 前三名合计：97.5%，其余 85 位分摊不到 2.5%
  • 定位反差：为「并行」设计的工具，维护却是单点加自动化

这不是缺陷，个人项目大多如此；但要把它写进团队流程，就得接受作者一人的节奏决定你的升级节奏。README 那句「5 到 10 个并行 agent」同样是场景假设，仓库没有给出并发规模或冲突率的实测。

许可证那处偏差还连着一个现实问题：企业合规扫描若按 API 字段走，这个 MIT OR Apache-2.0 的仓库会被归入「许可未知」而卡住。作者选择双许可没错，只是机器没读懂。用之前最好手动确认一遍 LICENSE 文件，别让扫描器替你下结论。

再算一笔账：154 个 tag 摊在 2025-10-17 至今的约 13 个月里，平均每月十来个版本。星标和推送都很热，但 热度是别人的，升级成本是自己的。

还有那个 NOASSERTION。它提醒一件事：机器读到的字段和人读到的文件未必是同一份事实。把 worktree 收成三个命令，成本没有消失，只是从命令行搬到了 1,274 份快照和 13 处 Breaking 里。

所以我的判断是：单人同时跑三五个 agent，它值得装；要嵌进多人共用的 CI 或脚本，先锁版本、把 Breaking 清单当发布说明读，别把「简洁」当成「稳定」。
