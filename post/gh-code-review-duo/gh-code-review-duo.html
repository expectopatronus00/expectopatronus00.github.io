5.6万星对1.4万星：一个审差异，一个验漏洞

56,261 星对 14,354 星，阿里与 OpenAI 的官方审查工具都在 11 月 25 日推送。前者把审哪些文件、评论放哪一行交给工程代码，后者把裁定、出补丁和验修复拆成独立工作流；两份文档都写明了误差边界，却没人替你签收结论。

01 这件事

两个大厂的官方审查工具在同一天活跃，却不在回答同一个问题：一个扫代码差异，一个验漏洞真伪。

截至 2026-11-25，alibaba/open-code-review 有 56,261 星、4,641 fork，2026-05-18 创建，主语言 Go，Apache-2.0，当天仍有推送；openai/codex-security 有 14,354 星、1,140 fork，2026-07-13 创建，主语言 TypeScript，同为 Apache-2.0，也在当天推送。

两条候选是 11-16 同批入池的 code-review 族，评分 89 与 87。入池超过七天后按规范复核热度，两家都仍在当天推送，星标未见衰减，因此保留原分，这篇横评一次消耗两条积压。

接口形态也不同：阿里把审查做成一个可换模型端点的命令行工具，OpenAI 把命令行、SDK 和 Codex 插件做成同一套安全工作流。别按「谁替代谁」读这篇。

02 核心机制

OCR 用确定性工程锁住「审哪些、评论放哪里」，Codex Security 用工作流锁住「从证据到结论」的每一步。

阿里的设计把不能出错的步骤交给工程代码：精确挑文件、把相关文件打包成独立上下文的子任务、按文件特征匹配规则，再用外置的定位与反思模块校正评论位置和内容。模型负责动态决策与读上下文。

仓库里能看到这套机制的体量：规则文档目录有 70 份 Markdown，共 356,697 字节；根目录规则文件把「改供应商注册表必须同步四语文档、必须有回归测试」写成硬条件。README 的 10 种语言指基准覆盖，不是规则文档总数。

环节open-code-reviewcodex-security
入口命令行 / Agent Skill / 插件命令行 / TypeScript SDK / Codex 插件
审查范围工作区、分支区间、单提交、整文件仓库、指定路径、提交差异、工作区改动
结论颗粒度行级审查评论，结构化输出发现项加源码证据、覆盖限制
后续动作明确不做自动修复生成补丁、验证既有修复

OpenAI 那条线把动作拆得更细：扫描、差异扫描、复扫、裁定既有发现、依赖告警调查、出补丁、验修复各是一步。修复验证只返回三种结果——已修复、仍有漏洞、证据不足。

插件目录有 20 个技能，评测目录 7 套，扫描器导入指南 22 份。工作流文档特别说明三种接法不是一回事：装完整插件才有安全技能；命令行生成的只是操作指引；命令行的接口只暴露只读的查询工具。

03 关键细节与数据

一个把低召回写进基准说明，一个把漏报划成普通缺陷；限制条件都写在自家文档里。

阿里的 README 给出一套自建基准：50 个开源仓库、200 个真实 PR、10 种语言、80 多位资深工程师标注出 1,505 个真问题。结论是同一模型下精度和 F1 更高，token 约为通用 agent 的九分之一，召回更低属于主动取舍。

基准指标README 口径
样本50 仓库 / 200 PR / 10 语言
标注量1,505 个真问题 / 80+ 标注工程师
精度与 F1高于通用 agent，未给绝对数
成本与召回约九分之一 token，召回主动调低

这组数出自项目自述，数据集托管在第三方平台，仓库内没有可复跑的评分脚本，本文按自报数据处理。路线图又补了一刀：更高召回的 Ultra 模式仍列在 2026 下半年计划里，当前版本追求的是少误报。

OpenAI 没有在 README 顶一个分数，而是把评测框架摊开：依赖可达性、发现裁定、密钥发现、时间预算、工作流路由等套件列在评测说明里，模型评测默认不跑且消耗配置账号的用量。

文档也有自己的缺口：评测总览列出 6 套，目录里实际有 7 份套件说明；插件版本是 0.1.95，命令行与引用文件写 0.11.0。更实在的一条是旧插件 0.1.32 曾漏掉改动的 Perl 文件，命令行 0.3.0 才修。

04 怎么用

先确定你要的是行级评论还是漏洞闭环，再选工具；两条路径的账号和成本结构完全不同。

OCR 有两种执行模式。原生模式由工具自己调模型，需要配好供应商与密钥；委托模式只做文件选择、规则解析和上下文打包，让宿主 agent 用自己的订阅跑分析，不需要单独的模型密钥，但订阅不是 API 凭证。

场景选谁理由
常规 PR 行级评论OCR定位与规则匹配由工程代码约束
只有订阅、没有 API 密钥OCR 委托模式用宿主 agent 的模型和额度
判断一个发现是否成立codex-security有裁定、证据和修复验证步骤
汇总第三方扫描器结果codex-security22 份导入指南与多种导出格式
把扫描接进 CI 并控成本codex-security示例工作流给出每次 5 美元上限

上手命令不长，但两边各有三四个动作要记，按用途摆开更清楚：

门槛要提前算清：OpenAI 的命令行要求 Node 22.13 以上且限定 22、24、26 版本，另需 Python 3.10 以上；示例 Action 设定每次约 5 美元上限，超出仍可能继续计费，且默认只报告发现、不让任务失败。

05 冷思考

两家卖的都不是「审得准」，而是把误差边界写进文档，让你自己决定签收哪一份证据。

阿里的宣传口径里有一句「内部跑两年、发现几百万缺陷」，公开仓库 2026-05-18 才创建，这段内部历史无法从仓库复核；自建基准的标注质量也只能信项目自述。星标高不等于独立评测多。

OpenAI 的边界更冷：安全政策明写漏报、误报和错误扫描结果算普通缺陷，提示注入或模型滥用已有权限不构成漏洞；深度扫描的 worker 只读，但不是离线隔离环境，继承的接口权限照样在。

所以两家的输出都该当证据包，不该当判决书。OCR 的路线图把「无人复核的自动修复」列为明确不做；Codex 的验证结果可以是证据不足，扫描说明也提醒零发现仍可能带着排除项。
