01 · 这件事

两万星、一次提交，README 先否认自己是产品

deepseek-ai/dsh-superagent-prototype 2026 年 10 月 31 日 09:32 UTC 建库，11 月 9 日核对时是 21555 星、2580 个 fork、164 个订阅者；TypeScript，MIT，默认分支 main，未归档，主页为空，最后一次 push 是 11 月 3 日 09:29 UTC。仓库描述只有一行 Towards a More Autonomous Agent System。反差落在提交记录上：commits 接口只返回 1 条，8c32a9dc5d，2026-10-31T12:05:39Z，署名 DeepSeek Harness Team，消息是 feat: add the dsh-superagent research prototype；releases 与 tags 都是空数组，issue、discussion、wiki 三个入口全部关闭。一个两万星仓库的全部历史，就是一次「把原型加进来」的提交。

这条在选题池里躺了 8 天，是积压最久的一条。按超期复核的规矩重新查过热度：星标仍在两万量级、11 月 9 日还有更新、11 月初刚 push 过，没有衰减，所以照写。但真正决定这篇怎么写的是 README 第一段：Research prototype for reference only, not an official DeepSeek product. 后面跟着三句更硬的——代码从团队日常开发里长出来，「much of the engineering done by coding agents」；把它当研究代码而不是生产可用软件，可能有 bug，编码风格与工程实践可能不一致；以及最要紧的一句：为发布做过改编，所以它既不等于内部版本，也不等于文章 Exploring Super-agent Design: Towards a More Autonomous Agent System 里描述的实现，「Some designs discussed in the article are directions for future development and are not implemented in this prototype」。文章里讲的一部分能力，这个仓库里没有。

所以这不是一次产品发布。它是把一套「agent 该怎么自处」的规则公开出来：什么条件下它才允许开工、什么时候必须闭嘴、什么时候必须把话交回给人。docs/000-philosophy.md 把核心原则写成一句话——Take as little human attention as possible, and give as much value as possible。本文不测它能不能替你改代码，只把这套规则拆到文件级，看看「克制」到底落在哪些地方。

02 · 核心机制

先判断「能不能开工」，再谈「怎么干」

定位写在 package.json 的 description 里：A proactive agent for one GitHub repository, as a DSH (DeepSeek Harness) bundle——它监听 GitHub，可选监听飞书；被允许的人派活后开一个工单，在自己的 agent session 与目录里干活，再回到原对话里交付，比如一个 PR；另有一个 web panel 只显示「需要人」的那些事。它不是聊天框里的助手，是常驻在一个仓库上的角色。

docs/001-domain.md 给了一条主链：Source 产生 Trigger，落到 Thread，交给 Eval 评估；Eval 接受才创建 Ticket 并附上一份 Mandate（授权），Assignment 把工单派给 Executor，结果经 Channel 写回原对话。文档附了中英对照术语表：来源、触发、线程、关联、渠道、策略、评估、准入、研判、决定、授权、工单、派工、订阅、扇出、执行器。值得注意的是 Executor 被明确划在领域之外，一个「人」也不是领域概念，只是 Trigger 上带的一个 actor 标识。它宁可多造几个抽象，也不让「谁」和「怎么执行」混进授权判断。

授权规则集中在 docs/002-authorization.md。第一条就划清边界：主机强制执行允许名单、规则与 Mandate，消息、评论、被引用的文档都只是决策输入，改不了权限。消息走两条路——新请求进 Eval，已有工单订阅的 Thread 上的消息作为上下文直接扇出给工单，不经过准入、也不给新权限。强度分三档 explicit / inferred / not admitted：在名单上的人直接 @ 才算明确请求；名单外的人默认被忽略；机器人即使在 Source 的 bot 名单里，最多产生推断候选，永远不能提明确请求，也不能停掉工单。

三档 accept mode 是整套设计的阀门：off 不收推断候选，observe（默认）会研判推断候选，但正面结论只记录成一条标了「would accept」的 ignore，什么都不接受，auto 才真的接单；明确请求在三种模式下都有效。文档给的次序是「Start in observe and switch to auto after reviewing the recorded Decisions」。连「停」都不交给执行器自己判断：A person saying "stop" in a Thread is an ordinary Trigger, and Eval decides stop. An Executor cannot declare that a person asked it to stop.；只有面板上的停止是一次命令。策略是有版本号的，改版本会丢弃运行中的 Eval、把触发重新排队，但不会立刻撤销已经开出去的 Mandate。

001 里还有一张 Rejected concepts 表，列了十来条「明确不做」的设计：不把人建成实体、不跨 Source 映射身份、不给 Eval 加 waiting 状态、不允许「append to Ticket」这种决定、不让工单状态跟着 DSH Session 走、不让执行器从报告的自由文本里推断「在等人」。哲学文档里对应的设计原则也只有四条：少概念、少设置、面板只显示需要人的东西、文档按编号顺序读。这套东西是做减法做出来的，不是把能力堆齐。

03 · 关键细节与数据

源码和测试几乎一样重，最严的闸门却写在提示词里

先用 git/trees/main?recursive=1 把整仓数一遍：truncated: false，236 个节点里 216 个 blob、20 个目录，逐字节累加 2,601,300 字节；根目录 18 项，10 个文件 8 个目录。分布很说明问题：src/ 111 个文件 1,081,932 字节，tests/ 65 个文件 1,066,322 字节——测试代码的字节数约等于源码的 98.6%。全仓最大的单文件是 pnpm-lock.yaml 172,084 字节，接着两个都是测试：tests/runtime.spec.ts 141,990 字节、tests/core-engine.spec.ts 106,908 字节；docs/ 9 篇共 185,852 字节，其中 007-architecture.md 单篇就 70,507 字节，占掉三分之一还多。而 README.md 只有 2,571 字节。一个自称「研究代码、非生产可用」的仓库，测试与源码几乎 1:1。

依赖口径更能说明它是什么。package.json 里 version 0.1.0、private: true，运行时 dependencies 只有 2 个（proper-lockfile 4.1.2、zod 4.4.3），但 peerDependencies 23 个、devDependencies 36 个，几乎全是 @deepseek-ai/dsh-* 的 0.2.1-alpha.2。engines 要求 node ^22.19.0 || >=24.0.0 与 dsh ^0.2.1-alpha.2，包管理器锁在 pnpm@11.7.0；dsh.bundle.patch 指向 cordis.patch.yml。换句话说它不能独立跑，是挂在 DeepSeek Harness 上的一块 bundle，整套宿主依赖还停在 alpha。prompts/ 15 个文件 49,853 字节、skills/ 只有 2 个文件（github 与 feishu 各一）共 5,325 字节，也印证了「能力靠提示词与技能描述，不靠堆插件」。

docs/003-execution.md 把执行侧写得很细：每个 Ticket 一个名为 worker-<ticket id> 的 Executor Session 和一个以工单短名命名的目录，默认落在 <stateDir>/work；首次派工前若目录不存在，用 sh 跑一次 prepare 命令，超时 10 分钟，典型做法是用 git worktree 开一份检出，失败即工单失败且不自动重试。worker 与 router 两个 preset 都把前台 shell 命令在 5 秒后转后台，子 agent 用 standard preset 是 60 秒；每轮后台工作最多 30 分钟，到点杀掉并报 waiting。出站消息的重试从 5 秒起、按倍数递增到 300，Input 投递从 2 秒起、翻倍到一分钟；连续三次失败才上报为系统问题。

最该停下来看的是合并规则。文档原话：Auto-merge is governed by the Delivery requirements prompt. The host has no merge-specific decision logic. 默认指令只允许在这个 PR 是为该工单开的、状态 ready、必需审批覆盖 head commit、且增删合计少于 200 行时启用 auto-merge；推新 revision 前要撤回；执行器默认不以 agent 账号启用 auto-merge，得另给一个有合并权限账号的 CLI。作者还补了一句：真要强制审批，请去 branch protection 里设，并勾掉过期审批。决定能否自动合并的，是一段可编辑的自然语言，不是主机里的权限检查。同一篇文档还写明 Executor Sessions run commands without approval as the operator's OS user，并自己承认 These wrappers and directories establish defaults, not a security boundary. A worker can still execute a program by absolute path.

04 · 怎么用

它不给你安装脚本，让你叫自己的 coding agent 读 SETUP.md

README 的 Setup 段落只有一句指令：对你的编码 agent 说 Read SETUP.md in this repository and set up dsh-superagent with me.。SETUP.md 本身是写给 agent 的操作规程，不是给人看的清单：第一条要求动手前只读这份文件和 000-philosophy.md、跑一次 probe，收齐答案前不许读别的；一次只问一个具体问题，每条消息少于 300 词，附一个能一个词接受的推荐答案和一句为什么要问；先把九个答案收齐，再发一条不超过 300 词的完整计划，等操作者确认才执行；绝不在聊天里要密钥——创建账号、CLI 登录、填 app secret 这类必须本人动手的事，打包成一条消息给出精确命令，让你在自己终端跑。安装流程本身也在执行「少占注意力」这条原则。

前置条件不含糊：Node.js 22.19+ 或 24+、pnpm、git 2.32+、tmux、Python 3.8+、GitHub CLI 2.48+、版本落在 engines.dsh 范围内的 DeepSeek Harness，以及一个配好的模型 provider。probe 命令是 node -v; pnpm -v; git --version; tmux -V; python3 --version; gh --version | head -1; dsh --version，再加 gh api user --jq .login 拿操作者自己的 login 当推荐值。缺的东西列进计划，不拿来提问。

九个问题分三组，顺序对应领域模型：Sources 从哪来（GitHub only 还是也接飞书、目标仓库 owner/name、专用 agent 账号、飞书哪些群）；Policy 谁能派活（GitHub 上哪些 login，默认只有操作者本人；飞书谁可以）；Execution 拿到工单后做什么（从哪个本地克隆检出、commit 署名是谁、要不要 auto-merge，默认否）。有合理默认值的一律不问，直接写进计划：profile superagent、端口 3082、状态目录 <home>/.dsh/state/superagent、每小时一次自检、分支前缀 agent/、accept mode observe、飞书只读 @ 且开私信。验证方式是从名单内账号在 issue 里评论 @<agent login> <request>，约一分钟后 overview 出现一个 Ticket；面板入口叫 Superagent。交接时给操作者三条规矩：start narrow、tune for less noise、own what it says。

这里有个容易踩空的点：默认 observe 意味着装完之后，所有「主动」工作只被记录、不执行。想让它真动手，得先翻一遍记下来的 Decisions，确认它「本来会做什么」看着对，再把模式切到 auto。这跟多数 agent 工具装完就能跑的预期正好相反。

05 · 冷思考

两万星是「DeepSeek」四个字的重量，不是这套规则的验收结果

先质疑最大的那个数字。21555 星配 2580 个 fork，可提交只有 1 次、release 与 tag 皆为 0，连 issue 区都没开——所以 open_issues_count: 0 不是「没人遇到问题」，是没地方提。README 把话说得比多数项目都绝：不是官方产品、不是生产可用、与内部版本不同、文章里一部分设计压根没实现。把它读成「DeepSeek 开源了超级智能体」，第一屏就是反证。星标买的是对招牌和 super-agent 这个词的想象，不是这套东西被持续维护过的证据。

再算个人开发者的账。0.1.0、private: true、23 个 alpha 版本的 peer 依赖、必须挂在 DeepSeek Harness 上；再加 tmux、专用 GitHub 账号、可选的飞书机器人、一个模型 provider。不装这一整套配套工具，它就只是一个 2.6 MB 的源码快照，什么也跑不起来。而装上之后，为了「该说话时才说话」，你要维护 3 档 strength、3 档 accept mode、7 种 Ticket stage、5 类 resume 前的 revalidation，外加 9 篇编号文档里最厚的那篇 7 万字节架构说明。这套复杂度要有团队规模才摊得平：一个人一个仓库，光把 002-authorization.md 读完再配 Policy，就比自己动手改代码贵。

第三处是真要接生产仓库的人才会在意的。作者自己写明执行器以操作者的 OS 用户身份无审批跑命令，并承认 wrapper 与目录「不是安全边界」，worker 仍可用绝对路径执行程序；auto-merge 的闸门写在 Delivery requirements 提示词里，主机「没有专门的合并决策逻辑」，连 200 行阈值也是提示词文本。也就是说「谁能开自动合并」最终取决于一段能被编辑、也可能被改写的自然语言，而不是代码里的权限校验。文档让你真要强制审批就去 branch protection 里设——这句建议本身，已经说明边界在哪。这类项目最该被读的从来不是能力清单，是作者承认自己没做到什么。

所以值不值得看，不看两万星。如果你要研究的是怎么把「agent 什么时候不许动」写成可版本化、可复验的授权，而不是又一份提示词模板，那张 Rejected concepts 清单、默认 observe 的阀门、以及测试与源码几乎等量的 111 对 65 个文件，是一份边界写得比能力更清楚的样本；如果你要的是今天装上、明天替自己合并 PR 的工具，README 第一段已经替你回答了。先把「它在什么条件下才允许开工」写清楚，再谈让它开工——这句话比这个仓库本身更值得抄走。
