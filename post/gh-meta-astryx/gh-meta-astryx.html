3.3万星、51版0.x：Astryx先给Agent发说明书

32,740 星的 Astryx 把 Meta 内部八年的设计系统、CLI 与 agent 说明书开源。README 说 150+ 组件，仓库数到 110 个组件目录；51 版全是 0.x。成体系的不是组件，是让 agent 照着做的路径。

01 这件事

Meta 把内部长了八年的设计系统连同 CLI 和 agent 说明书一起开源，但版本还停在所有 0.x。

截至 2026-11-24，meta/astryx 有 32,740 星、2,569 fork，2026-01-09 建库，11-24 仍在推送，MIT 许可。README 首屏写着「Currently in Beta」，底座是 React 19+ 与 StyleX。

README 自述这套系统在 Meta 内部用了八年，支撑 13,000+ 个应用，交付 150+ 个可访问组件、品牌级主题、黑暗模式和现成模板。七个对外发布的主题之外，还剩一个 probe，那是内部测试夹具。

从建库到首个版本隔了近六个月：仓库 01-09 创建，v0.1.1 到 06-26 才发布。51 个版本一路排到 v0.7.17，没有跳号；每个 release 的资产都是 0 个，因为交付物是 npm 包，不是 GitHub 附件。

它 2026-11-16 入池时 90 分，今天已积压八天。按规矩重新核了热度：星标仍在 3.2 万级，推送日期就是当天，没有衰减，照常成稿。777 个未结条目里 PR 比 issue 多 71 个，开放的不只是下载面。

02 核心机制

CLI 才是真正的入口：安装只是把文件放进去，init 才把规则写进 agent 的上下文。

README 把起步拆成「install，然后 init」。前三条命令装运行时与样式，第四条把 CLI 放进开发依赖；init 一次运行，不提问，打印样式与主题步骤，并把 Astryx 指南写进项目的 AGENTS.md 或 CLAUDE.md。

步骤命令作用
运行时npm install @astryxdesign/core @astryxdesign/theme-neutral @stylexjs/stylex组件、主题、样式依赖
CLInpm install -D @astryxdesign/cli文档、模板、codemod
初始化npx @astryxdesign/cli init写入 agent 指南
全局可选npm i -g @astryxdesign/cli任意目录可用，项目内仍用本地版本

core README 把版本对齐写得更细：CLI 要跟已装的 Core 同版本，Core 精确钉住时也要带 -E，Core 用 ^ 或 ~ 时才去掉。文档要求先装再初始化，这一步在写 UI 之前只做一次。

仓库没有把 agent 入口只做成一个 skill。两份 marketplace 清单分别面向 Claude 与 Codex，另一个插件目录里也各有一份声明，四份配置共用一个 2,673 字节的 SKILL.md。

那份 skill 带托管哈希标记，并明确优先级：项目里若有自己的 Astryx 文本，先听项目的，因为它知道该项目装了哪个版本。全局 skill 只负责兜底，不覆盖项目上下文。

还有一条容易踩的坑：不带 scope 的 astryx 是 npm 上的另一个包。README 与 core README 都要求用带 scope 的 CLI 名称或 npx 调用，直到 CLI 成为项目依赖为止。

probe 不是第八个主题。它自己的说明写得很直白：从主题目标枚举生成，给每个目标刷一种哈希出来的刺眼颜色，两个本该不同的子目标若落进同一个元素，就会显成同一种颜色。生成的主题文件有 198,073 字节，不许手改。

校验也不是人工核对。生成脚本按目标枚举刷色，CI 的 check 命令在目标没被覆盖时直接失败，把「所有文档化的主题目标都能落到像素上」变成一条机器可判的门禁。这条恰好对应 README 的原则：earned by measurement。

04 怎么用

最短路径是让 CLI 先选模板，再查 props，最后用 doctor 验收，而不是自己从 div 拼页面。

  1. astryx build "<要做什么>"：给出推荐模板和缺的部件。
  2. astryx template <name> <path>：落骨架，保留间距与内边距，只换内容。
  3. astryx component <Name>：读 props、变体和示例，再动手。
  4. astryx doctor --built .：检查配置和写出来的代码。

仓库自己的 AGENTS.md 要求每次开分支先跑一轮 bootstrap，依次看帮助、文档列表、token 与主题的精简版、组件清单、模板清单。理由是文档反映的是当前分支的真实 API，不是上次记住的版本。

对接现有 Tailwind 项目要走专门的桥接文件，它把系统 token 映射成工具类：text-primary 对应正文色，bg-surface 对应表面色，rounded-lg 对应容器圆角，间距基准是 4 的倍数，p-4 等于 16 像素。

已有项目可以保留自己的 Tailwind 导入，只要在它之前放好声明层的 @layer 行；放在后面会悄悄反过来层叠顺序。

README 还给了无构建工具的 CDN 路线，同时列出六个容易踩空的地方。

  • 主题属性：挂在 html 元素上，否则主题样式不生效。
  • esm.sh 链接：排除 react 与 react-dom，避免两套实例。
  • import map：补上 jsx-runtime，否则模块解析失败。
  • 文档字体：body 自己声明，三份样式表都不会设。
  • webfont：主题只写字体名，加载要自己做。
  • 语法：页面没有编译环节，只能用 createElement。

每个链接都要钉版本：README 的示例钉在 0.4.1，最新发布已是 v0.7.17。无版本号的 CDN 地址会指向最新版并被激进缓存，跨版本复制示例很容易拿到对不上的 API。

05 冷思考

它承诺开放和少约束，但写给 agent 的路径比写给人更细、更硬。

README 的原则是「Guidance over enforcement」和「Open internals」：组件给能力而不是护栏，内部结构可以直接导出，必要时把源码 eject 出来自己改。但 SKILL.md 给 agent 的开工令是「start every page from a template, never from scratch」。

交付前还要求逐个文件重读，把裸 div 与硬编码的颜色、像素值换成组件或 token，然后交付构建产物而不是描述。人可以绕开的设计意见，agent 被要求照单执行。这是速度换一致性，不是纯粹的自由度。

质疑点能核到的事实意味着什么
13,000+ 应用README 自述，仓库里无清单外部无法复核，只当背景
150+ 组件110 个顶层组件目录统计单位不同，别直接相减
版本成熟度51 版全 0.x，lab 不发布升级要靠 codemod
评审门槛CONTRIBUTING.md 55,444 字节改动要过 spec 与 preflight

贡献规则也偏重。AGENTS.md 写明只有标成 current 的知识记录才管实现与评审，不能从已合并的代码或沉默里推断批准；改路径前跑 specs 查询，提 PR 前跑 preflight。424 个开放 PR 与 353 个开放 issue 的比例，配上这套门槛，不奇怪。

同一份文件还划了人工边界：只有稳定的公开 API、主题契约、归属边界、兼容策略或确实主观的视觉方向悬而未决时才问人，而且一次只问一个问题；代码、测试和浏览器证据能判的，不问人。

这套门槛还配了量化手段。AGENTS.md 里的 vibe-test 支持跑 5 个分层抽样用例，或一次跑完 21 个；退化模式跑 10 轮，在第 0、6、8、10 轮探测上下文还够不够用。结果除成功与否，还记录用了哪些组件、有没有走逃生口。

要接就按它的路径接，把 CLI 当唯一入口、钉死版本、让 agent 从模板起步；想要一套不干涉工程习惯的静态组件，等 1.0 或只取 core 的预构建样式更稳。现在的 Astryx，值得学的是它怎么把设计规则变成可执行检查，不是急着把 51 个 0.x 版本搬进生产。
