2.2 万星、8 个技能：EGM 的「零上下文」有前提

22,357 星的 elephant-goldfish-model 要大象带上下文起草、金鱼不看对话独立评审，8 个技能覆盖从头脑风暴到漂移检查。README 把隔离说成硬规则，自己的文档却承认宿主指令仍会进场。

expectopatronus 2026-11-24 约 6 分钟阅读 原创 · AI 编程

01 这件事

Google 名下的 elephant-goldfish-model 把「设计」和「评审」拆给两个 agent：一个带全量上下文起草，一个不带先前对话独立挑错。截至 11-24，仓库 22,357 星、1,649 fork，11-23 仍在推送。

它 2026-09-13 建库，许可证 Apache-2.0，主语言 Python，未结条目 163 个。README 首行是一句口号：Design with an elephant, review with a goldfish。页尾却写着「这不是 Google 官方支持的产品」。

字段实测值字段实测值
星标 / fork22,357 / 1,649创建 / 推送09-13 / 11-23
许可证 / 语言Apache-2.0 / Python未结条目163（97 issue + 66 PR）
Release2 个，最新 v0.1.1官网egm.dev

11-14 入池时它拿到 95 分，是 pending 里最高的一条。入池第 10 天已超 7 天线，复核时星标仍在增长、推送停在昨天，热度未衰减，按原分成稿。

  • Elephant：拿着项目背景、需求和先前决定，探索问题并起草规格
  • Goldfish：只看文档与其引用的源码，不看先前对话，找隐含假设与实现风险
  • You：拍板取舍、批准设计，再决定要不要实现

三个角色里，只有「你」拥有决定权；两个 agent 一个只写、一个只挑。

02 核心机制

它解决的是「同一条推理链自己审自己」：起草者带上下文，评审者被强制隔离，最后把结论写进仓库里的设计文档。规格先落地，代码后写。

角色拿到的上下文职责
Elephant项目、需求、先前决定探索问题、起草规格
Goldfish文档与引用源码，无先前对话找缺失假设、含糊需求、实现风险
You真正要紧的目标与约束解决取舍、批准设计、决定建什么

评审不是一个 prompt，而是一条五阶段流水线，步号从 5 起——前四步属于头脑风暴与起草：

步骤评审动作依据的规范文件
Step 5拉远看简单性、YAGNI、复用zoom-out-standard.md
Step 6 naive 读者测自洽与背景缺失文档自身
Step 7挑系统设计、规模瓶颈、失效模式feature-spec-standard.md
Step 8复审前两步新增内容zoom-out-standard.md
Step 9核对路径、函数签名、测试用例implementation-readiness-standard.md

更早的 brainstorm 会让 Elephant 访谈出核心假设，再派 7 组 Goldfish 去否决它，结果写进 concepts_brief.md。草稿 design_draft.md 逐节停顿，等人在对话里反馈。

关键在于隔离是硬性的。README 明确写：评审需要新的子 agent 上下文，宿主若创建不了，EGM 就停在那里，不会退化成同一个上下文里假装换人。

所有长文档写进侧栏或工作区文件，不往聊天流里倒；01 到 04 阶段约定只写规格与评审产物，不碰生产代码——但架构文档注明，这条只是约定，没有机制强制。

「先写规格、再评审、最后才准写代码」是这套流程的全部主张，也是它最容易被跳过的一步。

03 关键细节与数据

README 列 8 个技能、架构文档列 8 个评审人格，但目录里实际躺着 10 份 persona 文件——三处数字各有各的口径。按名字逐一比对才不会数错。

README 的 Choose a skill 表给了 8 个可单独调用的技能：

技能用途
egm-brainstorm验证想法，写概念简报
egm-draft把简报或笔记变成设计文档
egm-resolve逐条处理评审意见
egm-bootstrap为已有代码库建/补文档
egm-lite小改动、修订、重构的快速通道
egm-review五阶段评审
egm-review-loop按配置跑一组评审者
egm-drift-report比对文档与当前源码的漂移

但 agents/ 目录里躺着 10 个 persona 文件，比架构文档列的角色多两个。

  • 评审者：comprehension、design_critic、implementation_readiness、inventive_catalyst
  • 视角与整合：structural、style、synthesizer、zoom_out
  • 另两个：bootstrap_orchestrator、codebase_details

架构文档只列 8 个角色名，还把 codebase_details 写成 Codebase Auditor、structural 写成 Structural Validator，名字和文件名对不上。

版本口径也对不齐。GitHub 只有 2 个 Release，包内清单走的却是另一套版本号：

版本发布时间资产 / 说明
v0.1.111-063 个资产：Claude 包、OpenAI 包、SHA256SUMS

v0.1.1 的 release 说明写得很直白：ZIP 的校验和与构建产物对得上，但「这些发布 ZIP 的原生端到端验证」仍挂在 issue #60 上没做完。

能下载、能校验、和「装上去真能跑完整流程」是三件事，这份 release note 自己把它们分开了。

04 怎么用

装整包，别只复制 skills 目录——技能在运行时会读 agents/ 和 resources/document_standards/，拆开装必然坏。三条主路径都是两行命令：

  • Antigravity CLI：agy plugin install https://github.com/google/elephant-goldfish-model
  • Claude Code：claude plugin marketplace add google/elephant-goldfish-model 后 claude plugin install egm@egm
  • Codex CLI：codex plugin marketplace add google/elephant-goldfish-model 后 codex plugin add egm@egm

装完要开新会话。最省事的入口是拿现有文档试 60 秒评审，不必先写规格：

  • 审已有设计：/egm:egm-review docs/designs/webhooks.md
  • 查文档漂移：/egm:egm-drift-report docs/designs/

Codex 没有 /egm: 前缀，要从技能选择器里选对应技能。Antigravity 1.4.10 会把不带前缀的名字补全，1.4.8 不会，所以 README 建议一律带前缀。

不是每个宿主都跑得动。支持的判定标准只有一条：brainstorm、draft、review 三步能端到端跑通。

宿主状态边界
Antigravity CLI / Claude Code / Codex安装与端到端通过评审者隔离证据更窄
Claude Cowork / ChatGPT Work安装可用云端验证缺口，#105 / #106
omp / Muse安装可用社区验证或非原生 persona
Antigravity 独立 IDE不支持缺 invoke_subagent 工具

产物默认写在工作目录，也可以加一行 EGM artifact directory: .dev/docs 改到别处；路径指到工作目录外时，EGM 会先问一次，无人在场的 headless 运行则退回工作目录。

「装得上」只解决第一关，能不能真的隔离出评审者，要看当前会话暴露了什么工具。

05 冷思考

README 反复强调 Goldfish 看不到先前对话，但文档自己承认：新的会话上下文，不等于宿主把指令文件也一起藏起来。这正是「零上下文」最容易被误读的地方。

harnesses.md 写得很清楚：Codex 的 fork_context: false 和 fork_turns: "none" 只隔离父轮次，不证明项目或用户指令被排除。

issue #237 报告 Codex CLI 0.166.0 把项目和用户的 AGENTS.md、Antigravity CLI 把 AGENTS.md 与 GEMINI.md 送进了评审者上下文。

仓库把这称为「宿主指令泄漏」，和父对话轮次泄漏分开记。TESTING.md 的测试记录也只有父轮隔离证据，指令文件排除这一项没测。

  • Muse 1.4.14 无法按名字生成 persona，评审者全走通用 subagent 兜底
  • omp 社区只验证 7 个技能、9 个 persona，端到端用例没跑
  • Cowork 的评审跑到第 7 阶段被用量上限打断，最终产物未验证

贡献门槛也不低。AI_POLICY.md 要求：超过 100 行非测试代码或改动 3 个以上核心文件，先开 Feature Inquiry Issue，再提一份用 EGM 自己写的设计文档 PR，最后才收实现 PR；纯自动生成的贡献不收。

163 个未结条目里 66 个是 PR，占了四成——对一个两岁的仓库来说，这更像是贡献流程在自我消化。

它真正值钱的不是八个小工具，而是把「让另一个 agent 重新读一遍」变成必须满足的前提：没有新上下文，就停下来。可宿主给得出的是新会话，不是真空。判断很简单：想要有人挑刺，先确认你的环境真能派出一个没被项目规则喂饱的评审者；否则这套流程只在纸面上换了双眼睛。
