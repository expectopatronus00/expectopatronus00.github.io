# 每日自动化的推送方案调研

> 2026-10-28 · 基于当前仓库实际状态（121 篇文章、近 30 天 22 次提交、无 `.github/`）

## 一、先拆词：「推送」其实是三件事

这个词在本项目里对应三个完全不同的技术问题，混在一起谈一定会选错方案：

| 说法 | 实际含义 | 技术手段 | 现状 |
| --- | --- | --- | --- |
| 内容推送 | 文章 commit 到 `main`，GitHub Pages 自动上线 | `git push` | ✅ `auto-publish.cjs` 已串上 |
| 状态推送 | 今天发了什么、评分多少、失败在哪，告诉我 | Webhook / Bot / 邮件 | ❌ 完全没有 |
| 读者推送 | 新文章送到订阅者眼前 | RSS → IM / 邮件 | ⚠️ 有 `feed.xml`，没分发 |

**结论先行**：内容推送已经自动了，缺的是「谁在每天固定时间按下按钮」和「按完怎么告诉我」。读者的分发是独立议题，优先级排在后面。

## 二、现状盘点：链路是通的，触发是断的

| 环节 | 工具 | 状态 | 断点 |
| --- | --- | --- | --- |
| 采集（公开源） | `source-radar.cjs` 读浏览器历史 sqlite + `inbox.txt` | 可脚本化 | 需手动运行 |
| 采集（登录态） | agent 用内置浏览器刷抖音收藏 / 小红书探索 | 只能 agent 做 | 需人喊一句 |
| 评分 | `skills/source-radar/preferences.md` 规则 + agent 判断 | 只能 agent 做 | 需人喊一句 |
| 正文生成 | `generate.js` / `wx-post-quick.cjs` | 可脚本化（模板）+ agent 润色 | 需人喊一句 |
| 一致性 | `repo-lint.cjs --fix` | ✅ 已串进 `auto-publish` | — |
| 索引 | `build-index.cjs` 生成 feed / sitemap | 可脚本化 | **`auto-publish` 没调用它** |
| 发布 | `git push origin HEAD:main` | ✅ 已串进 `auto-publish` | — |
| 部署校验 | `.tools/check-deploy.cjs` | 存在但不在流程里 | 靠人肉看 |
| 通知 | 无 | ❌ | — |

两处硬伤值得先修：

1. **`auto-publish.cjs` 只跑 `repo-lint`，不跑 `build-index`**。也就是说走自动发布时 `feed.xml` / `sitemap.xml` 是旧的，RSS 订阅者看不到新文章。
2. **没有失败可见性**。`git push` 失败时只打印一行提示，人不盯着终端就不知道今天断更了。

## 三、约束条件：这些决定了哪些事不能放到云端

| 约束 | 影响 |
| --- | --- |
| 抖音收藏 / 小红书探索流需要登录态，会话在本地内置浏览器 | 采集环节**必须在本机**，GitHub Actions 拿不到 |
| 两大平台反爬严格，机房 IP 更容易被拦 | 云端采集成功率远低于本地住宅 IP |
| 仓库无构建、纯静态 | 云端 CI 能做的事很少（只有校验和提交） |
| 评分与写作需要 LLM 判断 | 云端跑要自己管 API Key 和账单 |
| 个人项目，不想养服务器 | 排除自建 n8n / 定时服务器 |

一句话：**能自动化的部分要拆成「有登录态的本地段」和「纯确定性的云端段」，硬塞进一个地方都会失败。**

## 四、五种方案对比

| 方案 | 覆盖环节 | 优点 | 硬伤 | 结论 |
| --- | --- | --- | --- | --- |
| **A. 本地 agent 定时任务**<br>（WorkBuddy 自动化，每天定点唤起） | 全链路 | 唯一能拿到登录态；不用管 API Key；评分闸门原样保留 | 依赖本机开机；失败要能看到 | **主链路** |
| B. 系统计划任务 + 无头 CLI | 采集到发布 | 脱离客户端 | 本机没有可用的 agent CLI（`codebuddy` / `claude` 均不在 PATH）；登录态与无头浏览器共享仍是难题 | 备选，暂不投入 |
| C. GitHub Actions 全自动 | 生成到发布 | 完全无人值守、免费额度够 | 抓不到抖音/小红书；需要 LLM API Key；正文质量无人把关 | **只能做校验，不能做采集** |
| D. 混合：本地采集 → 云端生成发布 | 全链路 | 兼顾登录态与无人值守 | 两段之间要传状态（候选清单、封面图），复杂度陡增；只解决「本机不开机」一个场景 | 出差模式再考虑 |
| E. n8n / 集简云 / HiFlow | 通知、RSS 转发 | 零代码 | 采集段还是做不了；多一个平台要维护 | 只用于分发，不用于生产 |

## 五、推荐架构：三层，各管一段

```
09:00  本机 agent（定时唤起）
       └─ source-radar → 评分闸门(≥75) → 生成 → repo-lint → build-index → git push
                                                    │
                                                    └─ notify.cjs ──► Telegram / Bark / 邮件
10:30  GitHub Actions（纯确定性，不碰内容）
       └─ lint + feed 校验 + 线上 200 检查 ──► 失败或断更 N 天 ──► 同一条通知通道
```

三条设计原则：

1. **内容生产留在本地，质量校验放到云端。** 云端只回答「站点是不是好的」，不回答「今天写什么」。
2. **通知只有一个出口。** 所有环节都调 `scripts/notify.cjs`，换渠道只改一个文件。
3. **自动跑到「待发布」，人工保留一键否决权。** 转载类内容有版权与准确性风险，全自动直发迟早出事故。

## 六、落地清单（按文件）

| 文件 | 作用 | 工作量 |
| --- | --- | --- |
| `scripts/notify.cjs` | 统一通知出口，读 `NOTIFY_WEBHOOK` / `TG_BOT_TOKEN` 环境变量，无配置则静默跳过 | 小 |
| `scripts/daily-run.cjs` | 把 `repo-lint --fix` → `build-index` → `git push` → `notify` 串成确定性的一段 | 小 |
| `auto-publish.cjs` 补一行 | 在 `repo-lint` 之后调用 `build-index`，修掉 RSS 不更新的问题 | 极小 |
| `.github/workflows/health.yml` | 每日 UTC 02:30（北京 10:30）跑校验 + 线上探活，异常发通知 | 小 |
| `package.json` | 加 `"daily": "node scripts/daily-run.cjs"` | 极小 |
| `.env.example` + `.gitignore` | 密钥不入库 | 极小 |
| 定时任务配置 | 每天 09:00 唤起 agent 执行 `skills/source-radar/SKILL.md` 全流程 | 一次性 |

## 七、风险与红线

| 风险 | 触发条件 | 缓解 |
| --- | --- | --- |
| 登录态过期，采集为空 | 内置浏览器会话失效 | 候选数 < 3 时**只告警不发布**，禁止空跑生成垃圾文章 |
| 反爬限流 | 同一会话重复刷 | 一天一轮，失败退化为浏览器历史 + 收件箱 |
| GitHub Actions 定时任务被停 | 公开仓库 60 天无提交活动自动禁用 | 健康检查本身发通知，通知里带「工作流可能已停」的提示；或每 50 天手动 touch |
| cron 时区错位 | GitHub cron 用 UTC | 注释里写清换算，别照抄别人的表达式 |
| 密钥泄露 | 把 token 写进仓库 | 本地 `.env`（已 gitignore）+ GitHub Secrets |
| 内容质量滑坡 | 追求日更硬凑选题 | 保留 ≥75 分闸门；单日上限 3 篇；每周人工抽检 1 篇 |
| 版权与准确性 | 转载未标注原文 | 沿用现有规则：必须有具体原文链接，标题不做夸张化 |

## 八、分阶段路线

**Phase 0（半天）— 先把「看得见」做出来**
`notify.cjs` + 修 `build-index` 缺口 + 定时任务跑「只挑不发」。
产出：每天 09:00 收到一条日报，内容是今天候选、评分、建议发哪几篇。零风险。

**Phase 1（一周）— 自动到草稿，人工一键发**
agent 生成完停在本地，日报里附文章链接预览。你回一句「发」，才走 `git push`。
产出：每天节省 30–40 分钟采集与整理，发布节奏仍由人控制。

**Phase 2（一个月）— 全自动 + 抽检**
质量稳定后放开自动发布，同时上 GitHub Actions 健康检查兜底。
产出：真正的「每日自动推送」，人只处理异常。

**Phase 3（可选）— 读者分发**
`feed.xml` 已就绪，接 Telegram Channel 或每周邮件摘要即可。公众号最后做（需要认证服务号，收益最低）。

## 九、明确不建议做的三件事

1. **不要在 GitHub Actions 里抓抖音 / 小红书。** IP 与登录态双杀，写出来也是天天红叉。
2. **不要为了「自动」删掉评分闸门。** 闸门是这个项目质量的唯一来源，去掉它日更就变成日灌水。
3. **不要自建 RSS 服务器或邮件服务器。** 静态 `feed.xml` 够用，分发交给现成服务，维护成本差一个数量级。

## 十、待确认

- 通知渠道优先级：Telegram / Bark / 邮件 / 飞书机器人，选一个先跑通。
- 日更的固定时间点（建议 09:00，避开凌晨的平台限流高峰）。
- 单日发布上限（建议 3 篇，超过则顺延到次日待定清单）。
